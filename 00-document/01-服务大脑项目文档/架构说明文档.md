## 一、文档目的与范围

本文描述「服务大脑 Agent 服务」的总体架构、关键决策、模块划分、数据设计、部署形态与演进路线，用于指导实现、评审与运维。

**范围**：本工程（`service_brain_agent`）的 Agent 侧全部组件；GSI 业务系统、ASR 与录音链路仅描述交互边界，不在本文设计范围内。

**不在本文范围**：业务系统的表结构与页面设计；模型训练与微调；商业合同与报价。

## 二、架构总览

### 2.1 分层视图

```
┌──────────────────────────────────────────────────────────────────────┐
│ 调用方：GSI 业务系统（工单 / 录音 / 知识 / 权限 / 前台）                  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HMAC-SHA256 五头签名 · 13 个 /v1/* 接口

│ ① 接入层                                                             │

├──────────────────────────────────────────────────────────────────────┤
│ ③ 能力层                                                             │
│  规则引擎 │ 语义判定器 │ 混合召回器 │ RRF 融合 │ 精排 │ 生成器        │

├──────────────────────────────────────────────────────────────────────┤

│  schema ai_knowledge：切片 / 向量 / 发布单元 / 会话 / 台账             │

├──────────────────────────────────────────────────────────────────────┤
```

### 2.2 运行视图（容器拓扑）

```
                       ┌─────────────────────────┐
       GSI ─── HTTPS ──►│  反向代理 / ALB（可选）   │
                       └───────────┬─────────────┘
                                   │ 不改写路径、不丢 DELETE 正文
                       ┌───────────▼─────────────┐
                       │ service-brain-app       │  单镜像单容器
                       │ FastAPI :8002           │  前端产物 /ui 同源托管
                       └───┬──────────┬──────────┘
            内网 HTTP      │          │      HTTPS（可走 VPC 终端节点）
        ┌──────────────────▼──┐   ┌───▼──────────────────────┐
        │ service-brain-ollama│   │ AWS Bedrock              │
        │ /api/embed  11434   │   │ OpenAI 系列对话模型        │
        ├─────────────────────┤   │ （model_id 配置化）        │
        │ service-brain-rerank│   └──────────────────────────┘
        │ /v1/rerank  8080    │
        └──────────┬──────────┘
                   │ 同网络
        ┌──────────▼──────────┐
        │ service-brain-      │  PostgreSQL 17 + pgvector
        │ postgres   5432     │  宿主发布 39990
        └─────────────────────┘
```

要点：

- 应用、模型服务、数据库同属一个外部网络（`APP_NETWORK`），按容器名互访，不额外暴露端口；
- 对话模型是**唯一出网依赖**，通过 Bedrock 的 HTTPS 端点调用；语料侧的向量化与重排全部内网闭环；
- 数据卷持久化 PostgreSQL、Ollama 模型、rerank GGUF，重建容器不丢数据。

### 2.3 三条主数据流

**(a) 知识入库**：GSI 提交解析 → 任务落库（`queued`）→ 执行器拉取文件、校验、解析 → 切块 + 页图 → 产物回传 GSI → GSI 校对后提交正式切片 → 向量化 + 版本落库 → 原子切换 `revision`。

**(b) 检索问答**：GSI 提问（含 `allowed_snapshots`）→ 会话校验（`session_version`）→ 图执行（改写 → 召回 → 融合 → 精排 → 预算装配 → 生成）→ 引用校验 → 原子写会话 → 返回答案 + 引用；超时则落请求台账，供 #13 查询。

**(c) 质检判定**：GSI 提交通话转写与工单元数据 → 预处理（分段、摘要、说话人归一）→ 四类判定并行（硬规则 / 语义 / 知识一致性 / 工单一致性）→ 汇聚计分 → 判定表落库 → 报告聚合（SQL）→ 模型生成文字解读。

## 三、架构原则

| # | 原则 | 具体含义 |
| --- | --- | --- |
| P1 | 能力内聚、契约外置 | 对外只认 13 个 `/v1` 契约；内部实现可替换 |
| P2 | 证据优先 | 无证据即"未判定"，不允许模型自由发挥 |
| P3 | 数字归 SQL、文字归模型 | 报告与计分数字全部来自数据库聚合 |
| P4 | 权限在数据层生效 | 白名单下推为 SQL 条件，禁止结果后过滤 |
| P5 | 失败可降级、状态可查询 | 任何长链路都能查到"卡在哪、还要不要等" |
| P6 | 版本不可变 | 发布单元 `revision` 单调，切换原子，旧版可回退 |
| P7 | 单库单栈、最小依赖 | 一个 PostgreSQL 承载业务与向量；不引入额外中间件 |
| P8 | 命名与许可合规 | 基座称「自研基座」；依赖限定 OSI 认可许可 |

## 四、架构决策记录（ADR）

> 格式：结论 → 理由与权衡 → 已否决备选 → 适用与失效条件

### D1 定位：Agent 层增强而非重建业务系统

- **结论**：本期只交付可被 GSI 调用的 Agent 服务，业务事实与权限留在 GSI。
- **理由**：既有系统已承载工单/录音/知识/权限，重建成本高且风险不可控；接口化交付可并行推进、可独立验收。
- **否决备选**：① 重做一体化质检平台（工期与风险不可接受）；② 直接在 GSI 内嵌模型调用（耦合业务与模型，无法独立演进）。
- **适用条件**：GSI 具备按契约下发数据与白名单的能力。若 GSI 关键数据无法出域，则需改为同域部署并重估。

### D2 编排：LangGraph 显式状态图

- **结论**：用 LangGraph StateGraph 编排，节点单一职责、条件分支与并行汇聚显式声明。
- **理由**：质检与问答天然是"分支 + 并行 + 回退 + 可查询"的流程；状态图可单测每节点、可导出结构、可落库恢复。LangChain 负责模型与检索组件复用。
- **否决备选**：① AgentExecutor 自动循环（可控性差、成本不可控、难以审计）；② 纯代码 if/else 链（无状态、无法恢复、难测试）。
- **适用条件**：流程节点数在 10 个量级内。若扩展到多智能体协作，需评估是否引入 supervisor 模式。

### D3 对话模型：AWS Bedrock 托管的 OpenAI 系列

- **结论**：对话模型经 AWS Bedrock 调用 OpenAI 系列（ChatGPT 类）模型，`model_id`、区域、超时、配额全部走配置。
- **理由**：不承担 GPU 运维；Bedrock 提供企业级配额、审计与网络接入方式；模型升级由云侧完成，应用侧只改配置。
- **否决备选**：① 自建对话模型推理（显存与运维成本高，迭代慢）；② 直连模型厂商公有 API（数据路径与合规审核复杂，且无统一配额治理）。
- **适用条件**：客户网络允许访问 Bedrock 端点（公网或 VPC 终端节点）。若要求语料完全不出网，则本决策失效，需改为全私有化对话模型。

### D4 向量化与重排：私有化部署

- **结论**：embedding 用 bge-m3（1024 维、8K 上下文、多语言），rerank 用 bge-reranker-v2-m3，均为容器化内网部署。
- **理由**：知识语料含客户业务细节，不宜逐条送外部 API；私有化可批量化、可调参、成本可预测；两种模型均支持中英混排。
- **否决备选**：① 公有云 embedding/rerank API（数据出境与逐条计费）；② 只做向量不做精排（"相似但答非所问"无法收敛）。
- **适用条件**：内网具备推理资源（CPU 可跑 Q8 量化，GPU 可选）。若并发评分需求上量，需扩副本或上 GPU。

### D5 向量存储：PostgreSQL + pgvector 单库合流

- **结论**：业务表与向量表同库，切片表 `kb_chunk` 承载元数据与向量，HNSW 余弦索引。
- **理由**：白名单过滤、版本切换、去重计数都需要与关系数据做 JOIN；同库可在一个事务内完成"切换 + 过滤 + 排序"，避免跨库一致性问题；少一套中间件的运维成本。
- **否决备选**：① 独立向量数据库（多一套一致性边界与运维面，过滤需跨库回表）；② 内存向量索引（重启丢失、无法多实例）。
- **适用条件**：切片总量在千万级以内、QPS 在百级以内。超过则需评估分区、只读副本或引入专用向量库。

### D6 判定分工：规则引擎与模型各司其职

- **结论**：硬性规则（枚举、正则、阈值、字段必填、时长/静音）由规则引擎判定；语义类交模型；知识/工单一致性由"召回 + 模型比对"完成。
- **理由**：硬规则用模型既慢又不可解释，且结论不稳定；模型只做它擅长的事，同时保留"未判定"这一合法结论。
- **否决备选**：① 全模型判定（成本高、不稳定、无法解释扣分）；② 全规则判定（语义类无法覆盖）。
- **适用条件**：规则以六段式（名称/适用范围/判定条件/合格标准/不合格判定/备注）维护。若规则表达超出五类判定方式，需扩展规则 DSL。

### D7 生成形态：非流式 + 请求台账

- **结论**：`chat/completions` 非流式；`stream=true` 返回 `UNSUPPORTED_STREAM`；超时转入请求台账，经 #13 查询结果。
- **理由**：GSI 侧以请求-响应集成，不需要逐字输出；非流式便于原子落库与计费口径统一；台账解决"超时后结果去哪了"。
- **否决备选**：① SSE 流式（跨系统连接保持、断线重连与落库一致性复杂）；② 纯同步阻塞等待（超时即丢结果）。
- **适用条件**：单次生成在 60 秒预算内。若业务要求先给部分答案，需新增流式契约并重估。

### D8 权限：白名单下推

- **结论**：`allowed_snapshots` 转为检索 SQL 条件（或临时表 JOIN），空白名单直接空命中，超上限 413。
- **理由**：先全库召回再隐藏会导致"越权内容进入模型上下文"，既是泄露风险也会污染答案；下推后越权切块根本不参与排序。
- **否决备选**：① 结果后置过滤（泄露与污染风险）；② 为每个组合建独立 collection（组合爆炸）。
- **适用条件**：白名单粒度到"快照"。若需细到切片级 ACL，需在切片表增加权限列并扩大索引成本。

### D9 报告：数字聚合与文字生成分离

- **结论**：所有统计数字由 SQL 聚合产出，模型只生成解读与建议文字，且提示词中显式禁止输出数字。
- **理由**：模型算数不可靠且不可复现；报告要能对账，数字必须可追溯到查询。
- **否决备选**：① 让模型读原始判定记录自行汇总（口径漂移、不可审计）；② 纯模板拼接（缺少针对性解读）。
- **适用条件**：指标口径由业务先定义。口径变更需同步更新聚合 SQL 与模板。

### D10 数据隔离：同库独立 schema + 独立账号

- **结论**：Agent 业务对象落 `ai_knowledge` schema；Agent 使用独立账号，按 schema 最小授权；GSI 账号不能访问该 schema。
- **理由**：共用实例降低部署与备份成本；schema 边界足以满足逻辑隔离与授权审计。
- **否决备选**：① 独立实例（成本翻倍，跨库联查困难）；② 同 schema 加前缀（授权粒度不足，误操作风险高）。
- **适用条件**：客户接受同实例多 schema。若要求物理隔离（如等保测评要求），需改为独立实例并重估。

### D11 版本：发布单元 revision + 原子切换

- **结论**：每次正式发布生成新 `revision`，新版本切片就绪后在一个事务内切换 `active_revision`，旧版本保留供回退。
- **理由**：知识更新过程中检索不能命中半成品；乱序事件（旧 revision 迟到）必须被拒（`STALE_REVISION`）；回退要能一键完成。
- **否决备选**：① 原地更新切片（更新窗口内结果不一致）；② 每次发布新建全量表（空间膨胀）。
- **适用条件**：发布以"批次"为单位。若要求切片级热更新，需引入双写与可见性位标记。

### D12 命名与许可合规

- **结论**：交付文档与界面文案中，自研中后台框架统一称「自研基座」，不出现存在商标或授权争议的第三方框架名称；技术选型限定为国际通用开源组件（MIT / Apache-2.0 / BSD / LGPL）与甲方指定云服务。
- **理由**：客户法务对商标与授权状态敏感；品牌名出现在交付物即构成审查风险。
- **否决备选**：① 保留品牌名并附许可证说明（许可合规不等于客户接受）；② 连 FastAPI / SQLAlchemy / PostgreSQL 等国际公认组件一并隐去（文档失去实施指导意义）。
- **适用条件**：面向该跨国药企的全部交付文档。若客户书面确认接受具名，可重新评估。

## 五、接入层设计

### 5.1 双路由体系

| 路由 | 前缀 | 鉴权 | 用途 | 是否进审计 |
| --- | --- | --- | --- | --- |
| 对外契约 | `/v1/*` | HMAC-SHA256 五头 | GSI 集成（13 接口） | 否 |
| 内部管理 | `/api/v1/*` | JWT + RBAC | 规则、知识、会话、报告的管理与查询 | 是 |
| 应用级 | `/docs`、`/redoc`、`/openapi.json`、`/healthz` | 无 | 文档与健康检查 | 否 |

**关键约束**：`/v1` 必须挂独立 router，不引入 JWT 依赖，也不经过操作日志路由类；反向代理禁止改写路径（签名原文含原始路径），禁止丢弃 `DELETE` 正文。

### 5.2 签名校验流程

```
请求 → 取五头(client_id / timestamp / nonce / signature / 版本)
     → 校验 client_id 白名单
     → 校验 timestamp 在 ±5 分钟内
     → 校验 nonce 未被登记（持久化原子插入，保留至 timestamp+5min）
     → 按原始路径 + 查询串 + 原始 body 字节 SHA-256 重算签名
     → 比对（常量时间）
     → 通过：注入身份上下文；失败：401/409 统一错误体
```

不排序 JSON、不重新序列化、不修改路径——这是签名可复现的前提。

### 5.3 幂等与幂等台账

| 台账 | 键 | 冲突语义 | 落点 |
| --- | --- | --- | --- |
| 解析任务 | `job_id` | 同 ID 同正文返回首次结果；异正文 409 | `ai_idempotency` |
| 索引事件 | `event_id` | 同上，另叠加 `revision` 单调校验 | `ai_idempotency` |
| 生成请求 | `request_id` | 同上；超时后供 #13 查询 | `ai_idempotency` + `ai_request_log` |

实现方式：唯一索引 + 插入冲突检测（`ON CONFLICT DO NOTHING`），正文摘要存 `body_hash`，避免大字段重复存储。

### 5.4 统一错误体

```json
{ "error": { "code": "SCOPE_TOO_LARGE", "message": "allowed_snapshots 超过上限", "retryable": false } }
```

错误码分四族：鉴权类（401/409 重放）、参数类（400/413/422）、状态类（404/409 版本或并发）、系统类（429/500/503）。`retryable` 决定 GSI 是否重试，避免"重试放大故障"。

## 六、编排层设计（LangGraph）

### 6.1 三张状态图

**(a) 解析图**

```
受理校验 → 拉取与限额校验 → 解析（页图/文本）→ 切块与产物组装 → 落库
                │                    │
                └─失败→ failed(带 error_code) ←┘
```

**(b) 问答图**

```
校验会话版本 → 查询改写 → 混合召回(向量+关键词) → RRF 融合 → 精排
                                                        │
                       召回为空 ─────────────────────────┴→ 返回 no_evidence
                                                        │
                        装配上下文(token 预算) → 生成 → 引用校验 → 原子写会话
                                                        │
                                                  超时 → 请求台账（可查询）
```

**(c) 质检图（并行汇聚）**

```
预处理(分段/摘要/说话人归一)
   ├── 硬规则判定（规则引擎，不调模型）
   ├── 语义判定（模型 + 证据抽取）
   ├── 知识一致性（召回 + 模型比对）
   └── 工单一致性（字段比对 + 模型解释）
            └── 汇聚计分 → 判定落库 → 报告片段
```

### 6.2 节点职责

| 图 | 节点 | 职责 | 依赖 | 超时预算 |

### 6.3 图状态字段

```text
request_id / job_id / session_id / tenant_id / user_id / allowed_snapshots
query / rewritten_queries / retrieved / fused / reranked / contexts / citations
answer / no_evidence / degraded / errors[] / token_usage / started_at / deadline
```

状态在节点间传递，关键节点落库（`ai_request_log` / `ai_parse_job`），支持重启后判定"继续或失败"。

### 6.4 失败降级矩阵

| 故障 | 影响节点 | 降级动作 | 对外表现 |
| --- | --- | --- | --- |
| rerank 服务不可用 | 精排 | 跳过精排，用 RRF 顺序，标记 `degraded` | 正常返回，响应含降级标记 |
| embedding 服务不可用 | 混合召回 | 只走关键词通道，标记 `degraded` | 正常返回，命中率下降 |
| 对话模型超配额 | 生成 / 语义判定 | 切备选 `model_id`；仍失败则该类"未判定" | 问答返回 503 可重试；质检降级为缺类 |
| 对话模型超时 | 生成 | 转请求台账，返回可查询的 `request_id` | 202/约定码 + #13 查询 |
| 单类判定异常 | 质检汇聚 | 该类记为"未判定"，其余照常计分 | 结果含 `undetermined[]` |
| 数据库不可用 | 全部 | 快速失败 | 503，不产生半成品 |

## 七、能力层设计

### 7.1 规则引擎

- **规则模型**：名称、分类（硬/弱/语义/分析）、适用范围（项目/业务线/团队/渠道）、触发条件、判定方式、分值、知识依据、示例、优先级、生效时间、版本。
- **判定方式五种**：关键词、正则、枚举集合、字段校验（必填/类型/范围）、度量阈值（静音秒数、通话时长、邮件时间差）。
- **执行**：按适用范围与优先级筛出规则集 → 逐条执行 → 产出 `RuleResult{rule_id, pass, score, evidence, reason}`。
- **不变量**：规则引擎不调用模型；同一输入同一版本规则集结果必须一致（可单测）。

### 7.2 语义判定器

- 输入：对话片段（按 token 预算切片）+ 规则判定标准 + 可选知识条目。
- 输出：受约束 JSON（结论、分值档、证据片段列表、理由、置信度）。
- 约束：证据为空 → 结论为"未判定"；置信度低于阈值 → "未判定"；JSON 解析失败 → "未判定"（不重试到无限）。
- 稳定性：低温（0~0.2）、固定 seed（若模型支持）、固定提示词版本。

### 7.3 混合召回与排序

```
query ─┬─► 向量召回（pgvector HNSW，余弦，top_k=50，白名单下推）
       └─► 关键词召回（全文/trigram，top_k=50，白名单下推）
                    │
              RRF 融合（k=60，按排名而非分数，规避量纲差异）
                    │
              rerank 精排（交叉编码器，top_n=8）
                    │
              阈值过滤（低于阈值的切块不进入上下文）
```

**为什么用 RRF**：向量分与关键词分量纲不可比，RRF 只用排名，融合稳定且无需调权重。

### 7.4 生成与引用

- 上下文装配：按"标题 → 片段 → 条目 ID → 切块 ID"注入，严格控制 token 预算，超预算按分数降序截断并保留首尾。
- 生成约束：只依据给定上下文作答；上下文不足时输出"无依据"；引用以 `[1]` 标记，映射到 `chunk_id`。
- 引用校验：生成后逐条校验引用编号在本次 `contexts` 内且 `chunk_id` 存在；不通过即剔除并标记 `citation_invalid`。

### 7.5 计分与报告聚合

- 维度：服务规范、业务准确性、问题解决、沟通体验、合规风险、工单规范性（权重可配置）。
- 计分：规则分值累加 + 维度归一；硬规则可配置"一票否决"维度（如身份验证未执行）。
- 报告聚合：全部统计走 SQL（覆盖率、分布、Top-N、趋势）；模型只写解读段落；报告落库快照，保证同一周期重复查看结果一致。

## 八、模型接入层

### 8.1 三类适配器

| 适配器 | 端点形态 | 关键配置 | 失败语义 |
| --- | --- | --- | --- |
| ChatModel | AWS Bedrock（OpenAI 系列） | `model_id`、`region`、`max_tokens`、`temperature`、`timeout`、配额并发 | 可重试错误重试 2 次；配额/鉴权错误直接降级到备选模型 |
| Embedding | 内网 `POST /api/embed`（bge-m3） | `base_url`、`model`、`batch_size`、维度校验 | 失败即降级为关键词通道 |
| Rerank | 内网 `POST /v1/rerank`（bge-reranker-v2-m3） | `base_url`、`top_n`、超时 | 失败即跳过精排 |

### 8.2 统一约束

1. **超时**：每类调用有独立超时，且不超过所属节点的预算；
2. **并发**：按信号量限流，避免把配额打穿；
3. **结构化**：对话输出优先用 JSON Schema / 函数调用，退化时才正则兜底；
4. **可观测**：记录模型标识、耗时、token 用量、降级事件；
5. **可替换**：模型标识全部来自配置，代码不含具体模型名常量。

### 8.3 成本与容量控制

- 上下文按预算装配（默认召回 8 条精排结果，超预算截断）；
- 语义判定按"规则"维度并发，避免整篇长文重复送模型；
- 相同 `content_hash` 的切块不重复向量化；
- 高成本节点（语义判定、生成）设置每日预算告警。

## 十一、安全与合规

| 域 | 措施 |
| --- | --- |

## 十三、非功能设计

### 13.1 性能预算

| 链路 | 预算 | 保障手段 |
| --- | --- | --- |
| 检索（不含生成） | P95 ≤ 800 ms | HNSW 参数调优、白名单下推减少候选、精排 `top_n` 收敛 |

| 索引请求 | ≤ 60 s | 分批提交、去重跳过、批量 embedding |
| 解析任务 | 异步 | 任务队列 + 状态机，前端轮询 |

### 13.2 容量估算（假设值，需实测校准）

| 项 | 假设 | 推算 |
| --- | --- | --- |
| 日质检通话 | 2 000 通 | 每通 4 类判定，约 6 次模型调用 → 1.2 万次/日 |
| 知识规模 | 5 000 条目，平均 12 切片 | 6 万切块，1024 维约 0.25 GB 向量 |
| 并发会话 | 50 | 单实例异步可承载，关键是模型配额 |
| 报告 | 日/周/月三层 | 预聚合 + 快照，避免每次实时算 |

### 13.3 可用性与恢复

- 单实例 + 快速重启（容器健康检查失败自动重建）；
- 任务表状态机带心跳与超时判定，重启后把超时任务标记失败并允许重试；
- 幂等与防重放依赖数据库，重启不失效。

### 13.4 扩展性

| 压力点 | 扩展方式 |
| --- | --- |
| 检索 QPS | 应用无状态横向扩副本；pgvector 读副本（需评估一致性） |

| 模型并发 | 嵌入/重排多副本 + 队列；Bedrock 配额申请 |
| 判定吞吐 | 判定任务按队列并行，限制单通并发以保护配额 |
