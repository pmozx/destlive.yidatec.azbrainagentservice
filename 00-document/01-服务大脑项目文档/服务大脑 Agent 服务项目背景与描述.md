## 二、项目由来

### 2.1 上游方案

亿达信息（YIDATEC）为阿斯利康（AZ）IT 服务台设计的《YD-AZ 服务大脑 AI 质检整体架构解决方案》，提出了一套从数据接入、智能分析、结果输出到管理闭环的完整质量管控蓝图：

| 项 | 内容 |
| --- | --- |
| 客户方 | 阿斯利康（AZ）IT 服务台 |
| 交付方 | 亿达信息（YIDATEC） |
| 方案版本 | v1.3（初版）/ v2.1（整体方案更新） |
| 原定周期 | 2025-05-20 ~ 2026-05-19 |
| 评估方式 | SAPD：自动化评估 60% + 人工评估 40% |
| 方案形态 | 六层能力架构（数据输入 → 基础处理 → 规则与 AI 评估 → 结果生成 → 运营管理 → 决策改进） |

方案本身是**平台级蓝图**，落地的难点不在页面与表结构，而在两个"智能内核"：

1. **判定内核**——四类规则（强规则 / 弱规则语义 / 知识一致性 / 工单一致性）如何既配置化又可解释；
2. **知识内核**——知识按业务单元重组后，如何在高召回率下完成"坐席回答 vs 标准答案"的比对。

### 2.2 本项目的定位

**本项目不是重做服务大脑业务系统，而是对既有业务系统做 AI Agent 赋能。**

业务系统（下称 GSI）已经承载工单、录音、知识条目、规则配置、报表与权限；本项目交付的是**一个可被 GSI 调用的 Agent 服务**，把"解析—索引—检索—判定—生成"的智能能力以稳定接口和可解释结果的形式嵌进去。

用一句话概括：

> 业务与权限留在 GSI，知识与判定交给 Agent；Agent 不持有业务事实，只提供带证据的智能结论。

### 2.3 与"直接调用大模型"的区别

| 维度 | 直接调大模型 | 本项目（Agent 服务） |
| --- | --- | --- |
| 知识时效 | 依赖模型训练记忆，过期不可控 | 知识入库→索引→版本切换，条条可溯源 |
| 判定一致性 | 同问不同答，无法复盘 | 规则配置化 + 温度受控 + 判定留痕 |
| 可解释性 | 只有结论 | 结论 + 命中规则 + 证据片段 + 引用来源 |
| 权限 | 无法控制到人 | 白名单快照下推到检索条件，越权零命中 |
| 成本 | 每次全量上下文 | 检索后按需拼装，token 可控 |
| 监管 | 说不清依据 | 全链路台账（任务/事件/请求三类幂等台账） |

## 三、业务现状与核心痛点

依据《质检需求说明书 v1.0》《知识样例 Q&A》《中文质检要求样例》三份材料，现状可归纳为五个痛点：

| # | 痛点 | 现状证据 | 业务后果 |
| --- | --- | --- | --- |
| P1 | 质检覆盖率靠人工抽检 | 传统人工抽检不足 30%；目标 >90% | 大量通话未进入质量视野，问题沉淀不下来 |
| P2 | 质检标准因人而异 | 60 条左右的规则靠人工理解执行，同一通话不同质检员结论不同 | 员工不服气，申诉成本高，绩效依据弱 |
| P3 | 知识按"应用"建库，检索不到完整上下文 | 知识样例中每个应用一个 Sheet（如 EA-Wecom），按编号式 Q&A 组织；同一业务主题分散在多个应用下 | 坐席找知识困难，AI 召回不全，直接影响"知识一致性"判定准确率（目标 >80%） |
| P4 | 知识生命周期缺失 | 样例中存在"已不适用 FAQ"清单（10 条过期条目） | 过期知识仍被引用，产生"用过期信息回答"类缺陷 |
| P5 | 结果只是分数，不产出管理动作 | 报告为单通/员工/团队/Findings 四层设计，但生成依赖人工汇总 | 管理层看到分数看不到根因，培训与流程优化缺依据 |

补充的结构性问题：**规则与知识分属两套语言**。规则样例统一采用「规则名称 / 适用范围 / 判定条件 / 合格标准 / 不合格判定 / 备注」六段式，而知识条目采用「编号 / 问题 / 答案 / 是否升级 / 更新日期」五元式，两者之间没有机器可读的关联，导致"知识一致性判定"只能靠人读。

## 四、建设思路

### 4.1 三条主线

```
   ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
   │  知识可信     │ ──► │  判定可解释   │ ──► │  结果可运营   │
   │  入库即索引   │     │  规则+模型分工 │     │  报告→动作    │
   └──────────────┘     └──────────────┘     └──────────────┘
```

1. **知识可信**：知识条目解析 → 切块 → 向量化 → 发布单元版本化 → 原子切换。过期知识以"停用/删除"事件下架，检索不到即不引用。
2. **判定可解释**：硬规则交给规则引擎（可配置、可枚举、可单测），语义判定交给大模型（受约束输出 + 证据片段），两者结果在同一张判定表中合并计分。
3. **结果可运营**：报告数字由 SQL 聚合产出、文字由模型生成，避免"模型编数字"；Findings 从缺陷聚类产生，带责任人与跟踪状态。

### 4.2 技术路线（本期确定）

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 编排 | LangChain 1.3 + LangGraph | 多节点显式状态图：可中断、可回溯、可单测每个节点 |
| 对话模型 | AWS 上的 ChatGPT 类模型（Amazon Bedrock 托管的 OpenAI 系列） | 不自建对话推理；模型随 Bedrock 版本升级，`model_id` 走配置不写死 |
| 向量化 | 私有化部署的 embedding 模型（bge-m3，1024 维，8K 上下文，多语言） | 语料不出内网；维度与库表、索引绑定 |
| 重排序 | 私有化部署的 rerank 模型（bge-reranker-v2-m3） | 召回后精排，解决"向量相似但答非所问" |
| 向量存储 | PostgreSQL 17 + pgvector（HNSW 余弦） | 业务表与向量表单库合流，靠 schema 与账号隔离 |
| 应用 | FastAPI（异步）+ 自研基座 + APScheduler | 单镜像单容器，前端同源托管 |

### 4.3 为什么是 Agent 而不是"一条 Prompt 链"

质检与问答的判定路径本身是**分支 + 回退**的：

- 硬规则命中"未做身份验证"时，语义判定不必再评估"解答准确性"（前置不成立）；
- 知识召回为空时不生成答案，直接返回"无依据"，而不是让模型自由发挥；
- 生成超时不丢请求，转入结果查询；
- 同一通通话的四类判定需要并行执行再汇总，任一类失败要能降级为"该类未判定"而不是整体失败。

这类"条件分支 + 并行汇聚 + 失败降级 + 状态可查询"的结构，用状态图表达最直接，因此选 LangGraph 做编排骨架，LangChain 提供模型与检索组件。

## 五、项目目标

### 5.1 业务目标

| # | 目标 | 度量 |
| --- | --- | --- |
| B1 | 质检从抽检走向高覆盖 | 质检覆盖率 > 90% |
| B2 | 统一判定尺度 | 同一通话双人复核结论一致率显著提升，人工复核比例 < 10% |
| B3 | 缩短结果产出周期 | 通话结束后自动进入判定队列，无需人工汇总 |
| B4 | 沉淀共性管理问题 | 每周期产出可跟踪的 Findings，缺陷聚类可归因到团队/知识条目 |
| B5 | 支撑员工成长 | 员工报告从"缺陷清单"升级为 L1–L5 能力地图 |

### 5.2 管理目标

1. **规则可配置**：业务与质检团队不依赖算法工程师维护规则；
2. **知识可复用**：按业务单元组织，公共层 / 业务层 / 应用细节层三层共存；
3. **结果可追溯**：任一结论可回溯到录音片段、转写文本、命中规则、引用的知识条目；
4. **输出可管理**：单通 → 员工 → 团队/项目 → Findings 四层报告口径统一。

### 5.3 AI 目标

| # | 目标 | 边界 |
| --- | --- | --- |
| A1 | 复杂语义判断（理解准确性、情绪安抚、推诿、解决完整性） | 输出必须带证据片段，不给证据即视为未判定 |
| A2 | 知识一致性校验（坐席回答 vs 知识条目） | 召回为空时返回"无依据"，禁止臆断 |
| A3 | 报告解读与建议生成 | 数字一律来自 SQL 聚合，模型只做文字解读 |
| A4 | 缺陷聚类与根因归纳 | 聚类结果需可人工合并/拆分，不锁死 |

**明确不由 Agent 承担的部分**（与上游方案一致）：字段非空校验、固定话术精确匹配、身份验证是否执行、静音/抢话时长判定、强依赖精确条件的扣分——这些由规则引擎或 SQL 判定，可解释性优先于"看起来智能"。

### 5.4 工程目标

| # | 目标 | 度量 |
| --- | --- | --- |
| E1 | 接口契约稳定 | 对外 13 个 `/v1/*` 接口，签名/幂等/错误码齐备，GSI 可独立联调 |
| E2 | 数据隔离 | 业务表与向量表同库不同 schema，账号按 schema 最小授权 |
| E3 | 可运维 | 全链路请求台账、任务状态可查、部署一键、回滚可执行 |
| E4 | 可演进 | 模型可替换（对话模型走配置、向量/重排走同协议端点） |

## 七、项目范围

### 7.1 在范围内

- Agent 服务的全部后端能力（解析、索引、检索、问答、判定、报告生成、台账）；
- 对外接口契约的实现与联调（13 个 `/v1/*` 接口）；
- 知识与判定所需的数据模型与迁移（独立 schema）；
- 部署编排（容器、模型服务、数据库）、上线检查单与运维说明；
- 规则配置项的定义与校验（规则内容由业务侧维护）。

### 7.2 不在范围内

| 项 | 归属 | 说明 |
| --- | --- | --- |
| 工单、录音、ASR、CTI 等业务数据生产 | GSI / 既有系统 | Agent 只消费，不生产业务事实 |
| 权限计算（部门/项目/指定人） | GSI | Agent 只接受白名单快照并在检索时下推 |
| 知识业务状态与审批发布 | GSI | Agent 只接收"正式切片" |
| 座席工作台、知识中心管理页面 | GSI / 前端团队 | 本期不做 UI（管理台沿用自研基座既有页面） |
| 点赞点踩、答案反馈采集 | GSI | Agent 保持 `session_id`/`message_id` 稳定供其关联 |
| 种子文档收集、50 题测试集、UAT 组织与培训 | 运营/验收 | 不计入开发工时 |
| 模型训练与微调 | 模型提供方 | 本期只做提示工程与检索调优 |

### 7.3 边界口径

> Agent 的产出是"带证据的判定与建议"，不是"最终绩效结论"。任何影响员工绩效的结论必须经人工复核确认，Agent 输出保留 `review_status` 供 GSI 侧走复核与申诉流程。

## 十、关键假设与约束

### 10.1 硬前提（不满足则整体顺延）

| # | 前提 | 影响 |
| --- | --- | --- |
| 1 | 第一周内取得 Bedrock 模型访问权限与 `model_id` 清单 | 判定与生成链路无法定稿 |
| 2 | 确认共享密钥、`client_id` 与签名口径 | 联调无法启动 |
| 3 | 索引请求的切片规模与 60 秒超时口径冻结 | 索引与联调需返工 |
| 4 | `pages` 页图是否必须确认 | 解析产物结构变更 |
| 5 | embedding 维度（1024）与向量表、索引绑定后不再变更 | 变更需全量重建索引 |

### 10.2 约束

| # | 约束 | 应对 |
| --- | --- | --- |
| C1 | 客户为跨国药企，交付文档不得出现存在商标/授权争议的第三方中后台框架名称 | 基座统一称「自研基座」，只列国际通用开源组件与甲方指定云服务 |
| C2 | 通话录音、工单、知识语料涉及个人信息与商业信息 | 私有化向量化/重排；送模型前做字段级最小化与脱敏；不落原文日志 |
| C3 | 非流式生成，单次最长 60 秒 | 请求台账 + 超时结果查询接口，超时不丢请求 |
| C4 | 单人开发，12 周 / 52 人日 | 任务颗粒度 ≤3 人日；裁剪顺序预先约定 |
| C5 | 中文为主、含英文与多 BU 术语 | embedding 需支持多语言；检索保留关键词通道兜底 |

| 判据 | 通过标准 |
| --- | --- |
| 功能 | 13 个 `/v1/*` 接口与契约逐字段一致；四类判定均可产出结论或明确的"未判定"原因 |

## 十二、术语与缩写

| 术语 | 含义 |
| --- | --- |
| GSI | 既有服务大脑业务系统（本项目的调用方与数据源） |
| Agent | 本项目的 AI 智能体服务，由 LangGraph 编排的多节点流程 |
| 自研基座 | 本项目使用的自研中后台开发框架（RBAC、JWT+Redis 会话、系统管理、任务调度、对象存储、代码生成等） |
| 发布单元 | 知识的可检索版本容器，携带 `publication_id` 与单调递增 `revision` |
| 快照（snapshot） | 某次发布的可检索切片集合标识，白名单以快照为粒度 |
| 白名单下推 | 把 GSI 给定的 `allowed_snapshots` 转为检索 SQL 条件，避免"先全库后隐藏" |
| RRF | Reciprocal Rank Fusion，多路召回结果融合排序 |
| rerank | 召回后的精排，用交叉编码器评估问句与切块的相关性 |
| Findings | 从缺陷聚类得到的管理发现，含根因、影响范围与建议动作 |
| SAPD | 上游方案的评估方式：自动化评估 60% + 人工评估 40% |
