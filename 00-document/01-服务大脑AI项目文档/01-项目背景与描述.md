## 二、项目由来

### 2.1 上游方案

亿达信息（YIDATEC）为阿斯利康（AZ）IT 服务台设计的《YD-AZ 服务大脑 AI 质检整体架构解决方案》，提出了一套从数据接入、智能分析、结果输出到管理闭环的完整质量管控蓝图：

| 项 | 内容 |
| --- | --- |
| 客户方 | 阿斯利康（AZ）IT 服务台 |
| 交付方 | 亿达信息（YIDATEC） |
| 方案版本 | v1.3（初版）/ v2.1（整体方案更新） |
| 评估方式 | SAPD：自动化评估 60% + 人工评估 40% |
| 方案形态 | 六层能力架构（数据输入 → 基础处理 → 规则与 AI 评估 → 结果生成 → 运营管理 → 决策改进） |

方案本身是**平台级蓝图**，落地的难点不在页面与表结构，而在两个"智能内核"：

1. **判定内核**——四类规则（强规则 / 弱规则语义 / 知识一致性 / 工单一致性）如何既配置化又可解释；
2. **知识内核**——知识按业务单元重组后，如何在高召回率下完成"坐席回答 vs 标准答案"的比对。

### 2.2 本项目的定位

**本项目不是重做服务大脑业务系统，而是对既有业务系统做 AI 赋能。**

业务系统（下称 GSI，即「服务大脑」既有系统）已经承载工单、录音、知识条目、规则配置、报表与权限；本项目交付的是**一个可被 GSI 调用的 AI 服务**，围绕两个核心模块扩展：

| 核心模块 | 模块码 | 一句话职责 |
| --- | --- | --- |
| 知识平台 | `kb` | 文档/FAQ 解析、正式切片存储与向量化、按权限检索、问答生成、会话与历史、重复检测与合并预览 |
| 语音质检 | `voice` | 通话转写文本的硬规则 / 语义 / 知识一致性 / 工单一致性四类判定、计分、四层报告与 Findings |

> 业务与权限事实留在 GSI，知识与判定交给 AI；AI 不持有业务事实，只提供带证据的智能结论。

工程上，AI 服务与 GSI **共用同一个 PostgreSQL 数据库**（`service_brain`）：GSI 的 93 张业务表与 AI 侧新增表同库同 schema（`public`），AI 表一律使用 `sbp_ai_[模块名]_[业务名]` 前缀命名实现隔离（详见 `04-项目模块说明与表结构设计.md`）。

### 2.3 与"直接调用大模型"的区别

| 维度 | 直接调大模型 | 本项目（AI 服务） |
| --- | --- | --- |
| 知识时效 | 依赖模型训练记忆，过期不可控 | 知识入库→索引→版本切换，条条可溯源 |
| 判定一致性 | 同问不同答，无法复盘 | 规则配置化 + 温度受控 + 判定留痕 |
| 可解释性 | 只有结论 | 结论 + 命中规则 + 证据片段 + 引用来源 |
| 权限 | 无法控制到人 | 按签名身份实时计算授权，越权零命中 |
| 成本 | 每次全量上下文 | 检索后按需拼装，token 可控 |
| 监管 | 说不清依据 | 全链路审计（统一接口日志 + 幂等台账 + 安全头校验留痕） |

## 三、业务现状与核心痛点

依据《质检需求说明书 v1.0》《知识样例 Q&A》《中文质检要求样例》，现状可归纳为五个痛点：

| # | 痛点 | 现状证据 | 业务后果 |
| --- | --- | --- | --- |
| P1 | 质检覆盖率靠人工抽检 | 传统人工抽检不足 30%；目标 >90% | 大量通话未进入质量视野，问题沉淀不下来 |
| P2 | 质检标准因人而异 | 约 60 条规则靠人工理解执行，同一通话不同质检员结论不同 | 员工不服气，申诉成本高，绩效依据弱 |
| P3 | 知识按"应用"建库，检索不到完整上下文 | 知识样例中每个应用一个 Sheet，按编号式 Q&A 组织；同一业务主题分散在多个应用下 | 坐席找知识困难，AI 召回不全，直接影响"知识一致性"判定准确率（目标 >80%） |
| P4 | 知识生命周期缺失 | 样例中存在"已不适用 FAQ"清单（10 条过期条目） | 过期知识仍被引用，产生"用过期信息回答"类缺陷 |
| P5 | 结果只是分数，不产出管理动作 | 报告为单通/员工/团队/Findings 四层设计，但生成依赖人工汇总 | 管理层看到分数看不到根因，培训与流程优化缺依据 |

补充的结构性问题：**规则与知识分属两套语言**。规则样例统一采用「规则名称 / 适用范围 / 判定条件 / 合格标准 / 不合格判定 / 备注」六段式，而知识条目采用「编号 / 问题 / 答案 / 是否升级 / 更新日期」五元式，两者之间没有机器可读的关联，导致"知识一致性判定"只能靠人读。

## 四、建设思路

### 4.1 三条主线

```
   ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
   │  知识可信     │ ──► │  判定可解释   │ ──► │  结果可运营   │
   │  入库即索引   │     │  规则+模型分工 │     │  报告→动作    │
   └──────────────┘     └──────────────┘     └──────────────┘
```

1. **知识可信**：知识条目解析 → 分片 → 向量化 → 发布单元版本化 → 原子切换。停用/删除事件下架，检索不到即不引用。
2. **判定可解释**：硬规则交给规则引擎（可配置、可枚举、可单测），语义判定交给对话模型（受约束输出 + 证据片段），两者结果在同一张判定表中合并计分。
3. **结果可运营**：报告数字由 SQL 聚合产出、文字由模型生成，避免"模型编数字"；Findings 从缺陷聚类产生，带责任人与跟踪状态。

### 4.2 技术路线（本期确定）

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 编排 | LangChain 1.3 + LangGraph（StateGraph） | 多节点显式状态图：可中断、可回溯、可单测每个节点；工程已集成 |
| 对话模型 | **ChatGPT 5.6**（经 OpenAI 兼容端点接入，`LLM_MODEL` 配置化） | 用于文档解析辅助、AI 对话生成、语义判定、报告解读；不自建推理，模型标识不写死在代码 |
| 向量化 | 私有化部署的 embedding 模型（bge-m3，1024 维，8K 上下文，多语言） | 语料不出内网；维度与库表、索引绑定（工程已集成，支持 openai / ollama 协议） |
| 重排序 | 私有化部署的 rerank 模型（bge-reranker-v2-m3） | 召回后精排，解决"向量相似但答非所问"（工程已集成） |
| 向量存储 | PostgreSQL + pgvector（HNSW 余弦） | 与 GSI 业务表**共用 service_brain 库、同 public schema**，靠 `sbp_ai_` 前缀与账号授权隔离 |
| 应用 | FastAPI（异步）+ 自研基座 | 单镜像单容器；统一接口日志审计（`sbp_ai_system_api_log`）已具备，将扩展以支撑对接接口的 HTTP 安全头校验 |

### 4.3 为什么是 Agent 而不是"一条 Prompt 链"

质检与问答的判定路径本身是**分支 + 回退**的：

- 硬规则命中"未做身份验证"时，语义判定不必再评估"解答准确性"（前置不成立）；
- 知识召回为空时不生成答案，直接返回"无依据"，而不是让模型自由发挥；
- 生成超时不丢请求，转入结果查询台账；
- 同一通通话的四类判定需要并行执行再汇总，任一类失败要能降级为"该类未判定"而不是整体失败。

这类"条件分支 + 并行汇聚 + 失败降级 + 状态可查询"的结构，用状态图表达最直接，因此选 LangGraph 做编排骨架，LangChain 提供模型与检索组件。

## 五、项目目标

### 5.1 业务目标

| # | 目标 | 度量 |
| --- | --- | --- |
| B1 | 质检从抽检走向高覆盖 | 质检覆盖率 > 90% |
| B2 | 统一判定尺度 | 同一通话双人复核结论一致率显著提升，人工复核比例 < 10% |
| B3 | 缩短结果产出周期 | 通话结束后自动进入判定队列，无需人工汇总 |
| B4 | 沉淀共性管理问题 | 每周期产出可跟踪的 Findings，缺陷聚类可归因到团队/知识条目 |
| B5 | 支撑员工成长 | 员工报告从"缺陷清单"升级为 L1–L5 能力地图 |

### 5.2 管理目标

1. **规则可配置**：业务与质检团队不依赖算法工程师维护规则；
2. **知识可复用**：按业务单元组织，公共层 / 业务层 / 应用细节层三层共存；
3. **结果可追溯**：任一结论可回溯到录音片段、转写文本、命中规则、引用的知识条目；
4. **输出可管理**：单通 → 员工 → 团队/项目 → Findings 四层报告口径统一。

### 5.3 AI 目标

| # | 目标 | 边界 |
| --- | --- | --- |
| A1 | 复杂语义判断（理解准确性、情绪安抚、推诿、解决完整性） | 输出必须带证据片段，不给证据即视为未判定 |
| A2 | 知识一致性校验（坐席回答 vs 知识条目） | 召回为空时返回"无依据"，禁止臆断 |
| A3 | 报告解读与建议生成 | 数字一律来自 SQL 聚合，模型只做文字解读 |
| A4 | 缺陷聚类与根因归纳 | 聚类结果需可人工合并/拆分，不锁死 |

**明确不由 AI 承担的部分**（与上游方案一致）：字段非空校验、固定话术精确匹配、身份验证是否执行、静音/抢话时长判定、强依赖精确条件的扣分——这些由规则引擎或 SQL 判定，可解释性优先于"看起来智能"。

### 5.4 工程目标

| # | 目标 | 度量 |
| --- | --- | --- |
| E1 | 接口契约稳定 | 对外 20 个 `/v1/*` 接口（v2.1 契约），签名/幂等/错误码齐备，GSI 可独立联调 |
| E2 | 数据共库规范 | 与 GSI 共用 `service_brain` 库；AI 表全部 `sbp_ai_` 前缀，Alembic 与 GSI Flyway 分治互不干扰 |
| E3 | 审计合规 | 对接接口全部纳入统一日志审计，安全头校验结果留痕，被拒请求可查 |
| E4 | 可运维 | 全链路请求台账、任务状态可查、部署一键、回滚可执行 |
| E5 | 可演进 | 模型可替换（对话模型走配置、向量/重排走同协议端点） |

## 七、项目范围

### 7.1 在范围内

- AI 服务的全部后端能力（解析、索引、检索、问答、会话、重复治理、判定、报告生成、审计台账）；
- 对外接口契约的实现与联调（v2.1 的 20 个 `/v1/*` 接口，含 #16–#20 重复治理）；
- `sbp_ai_*` 表结构设计与迁移（与 GSI 共库，Alembic 管理）；
- 日志审计扩展：对接接口纳入审计 + HTTP 安全头校验留痕；
- 部署编排（容器、模型服务、数据库）、上线检查单与运维说明；
- 规则配置项的定义与校验（规则内容由业务侧维护）。

### 7.2 不在范围内

| 项 | 归属 | 说明 |
| --- | --- | --- |
| 工单、录音、ASR、CTI 等业务数据生产 | GSI / 既有系统 | AI 只消费，不生产业务事实；转写文本由 GSI 提供 |
| 权限计算（部门/项目/指定人） | GSI | AI 按签名身份**只读查询 7 张指定共享表**实时计算授权（v2.1 契约），不自行推断权限规则 |
| 知识业务状态与审批发布 | GSI | AI 只接收审批通过后的"正式切片集合" |
| 座席工作台、知识中心管理页面 | GSI / 前端团队 | 本期不做业务 UI（管理台沿用自研基座既有页面） |
| 点赞点踩、答案反馈采集 | GSI | AI 保持 `session_id`/`message_id` 稳定供其关联 |
| 种子文档收集、50 题测试集、UAT 组织与培训 | 运营/验收 | 不计入开发工时 |
| 模型训练与微调 | 模型提供方 | 本期只做提示工程与检索调优 |

### 7.3 边界口径

> AI 的产出是"带证据的判定与建议"，不是"最终绩效结论"。任何影响员工绩效的结论必须经人工复核确认，AI 输出保留 `review_status` 供 GSI 侧走复核与申诉流程。

## 十、关键假设与约束

### 10.1 硬前提（不满足则整体顺延）

| # | 前提 | 影响 |
| --- | --- | --- |
| 1 | 取得 ChatGPT 5.6 的 OpenAI 兼容端点地址、密钥与配额 | 解析、对话、判定链路无法定稿 |
| 2 | 确认共享密钥、`client_id` 与签名口径（四头 X-AI-*） | 联调无法启动 |
| 3 | DBA 在 service_brain 库为 AI 开通独立账号，并对 7 张共享表授予只读权限 | 授权计算不可用，全量问答 503 |
| 4 | 索引请求的切片规模与 60 秒超时口径冻结 | 索引与联调需返工 |
| 5 | embedding 维度（1024）与向量表、索引绑定后不再变更 | 变更需全量重建索引 |

### 10.2 约束

| # | 约束 | 应对 |
| --- | --- | --- |
| C1 | 客户为跨国药企，交付文档不得出现存在商标/授权争议的第三方中后台框架名称 | 基座统一称「自研基座」，只列国际通用开源组件与甲方指定云服务 |

## 十二、术语与缩写

| 术语 | 含义 |
| --- | --- |
| GSI | 既有服务大脑业务系统（本项目的调用方与数据源），93 张 `sbp_*` 表 |
| AI 服务 / Agent | 本项目交付的智能体服务，由 LangGraph 编排的多节点流程 |
| 自研基座 | 本项目使用的自研中后台开发框架（RBAC、JWT 会话、系统管理、任务调度、接口日志审计等） |
| 四头签名 | 对接接口的 HMAC-SHA256 鉴权：`X-AI-Client` / `X-AI-Timestamp` / `X-AI-Nonce` / `X-AI-Signature` |
| authorization | v2.1 契约的授权对象 `{scope_id, issued_at, expires_at(≤120s)}`，AI 据此查共享表计算实时权限 |
| 共享表 | GSI 只读开放给 AI 的 7 张表（org / org_member / audience_team / audience_team_member / user / km_doc_publication / km_doc_record） |
| 发布单元 | 知识的可检索版本容器，携带 `publication_id` 与单调递增 `revision` |
| 六元组证据 | 引用溯源的最小单位：resource / publication / record / version / revision / chunk |
| RRF | Reciprocal Rank Fusion，多路召回结果融合排序 |
| rerank | 召回后的精排，用交叉编码器评估问句与分片的相关性 |
| Findings | 从缺陷聚类得到的管理发现，含根因、影响范围与建议动作 |
| SAPD | 上游方案的评估方式：自动化评估 60% + 人工评估 40% |
