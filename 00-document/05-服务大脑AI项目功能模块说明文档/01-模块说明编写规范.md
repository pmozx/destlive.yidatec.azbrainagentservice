# 01 · 模块说明编写规范

> 本规范约束 `05-服务大脑AI项目功能模块说明文档/` 下**所有**模块说明文档。
> 目标：任何人写出的模块文档结构一致、颗粒度一致、可核对，读者换模块不用换阅读方式。
> 版本 v1.0（2026-11-02）· 与 `00-document/README.md` §二命名规范配套使用，冲突时以本规范为准。

---

## 一、适用范围与「已完成」判定

### 1.1 适用对象

只写**已实现并跑得起来**的功能模块。判定四条件（缺一不写，避免文档描述一个不存在的系统）：

| # | 条件 | 核对方法 |
| --- | --- | --- |
| ① | 代码已合入且应用能启动 | `python -c "from app import create_app; create_app()"` 通过 |
| ② | 表已能建出 | 启动建表日志有该表 |
| ③ | 端点已注册且返回真实数据 | OpenAPI 里能查到，且有非 skeleton 的实现 |
| ④ | 有测试或可复现实测 | `tests/` 有对应用例，或文档里附一次实测记录 |

**不写**的三类内容：仅有表没有读写方的（写进所属模块「已知限制」）、纯 skeleton 端点（在接口清单里标 `骨架`）、已删除模块（只在 `04` 报告里留档）。

### 1.2 与其它文档的分工

| 内容 | 归属 | 在本目录的处理方式 |
| --- | --- | --- |
| 架构分层、ADR、模块规划 | `01-…需求与架构文档` | 只引用，不重述设计动机 |
| 通用编码/建表/错误处理规范 | `03-…开发规范文档` | 只引用规则号（如「见规范 R4」） |
| 缺陷清单、整改批次、验收证据 | `04-…开发过程文档` | 只引用编号（如「见 P1-6」） |
| 当前实现细节 | **本目录** | 完整描述 |

> 一条判断标准：**这段话半年后若代码变了会不会失效？** 会失效的是实现说明（写本目录），不会失效的是设计原理（写 `01`）。

## 二、命名与编号

### 2.1 对象命名

| 对象 | 规则 | 正例 | 反例 |
| --- | --- | --- | --- |
| 模块目录 | `NN-<业务模块名>`，`NN` 从 `02` 起，连续不跳号；用业务语言，多子模块用 `-` 连接 | `02-日志审计与接入追踪`、`03-知识库` | `02-system`、`03-api_log`、`04-知识库模块（新版）` |
| 模块内正文 | 固定四份固定名，编号含义全局固定 | `02-数据模型与表关系.md` | `02-表设计.md`、`02.1-数据模型.md` |
| 模块索引 | 固定 `README.md` | — | `00-总览.md` |
| 附录（可选） | 确有需要才加，`05-<主题>.md` 起编，须在模块 README 登记 | `05-历史迁移说明.md` | `99-杂项.md` |

**四份正文的编号语义（不得调换）**：

| 编号 | 文件名 | 语义锚点 |
| --- | --- | --- |
| `01` | 业务功能说明 | 行为：谁、为什么、做了什么、算不算成功 |
| `02` | 数据模型与表关系 | 数据：表、字段、键、表间引用 |
| `03` | 接口清单 | 契约：怎么调、返回什么、错在哪 |
| `04` | 实现与运维说明 | 实现：代码在哪、为什么、怎么配、怎么查 |

### 2.2 文内引用写法

| 场景 | 写法 | 示例 |
| --- | --- | --- |
| 代码位置 | `` `相对仓库根的路径:起止行` `` | `app/core/router_class.py:300-326` |
| 数据表 | 全名，首次出现给中文释义 | `sbp_ai_system_api_log`（接口审计日志） |
| 列名 | 反引号，`表.列` 消歧 | `sbp_ai_system_api_log.request_id` |
| 同模块文档 | 文件名 | `02-数据模型与表关系.md` §4 |
| 跨模块/跨目录 | `目录号-文档号` 或 `模块号/文档号` | `05-02/02`、`03-01` |
| 配置项 | 反引号 + 默认值 | `API_LOG_RETENTION_DAYS`（默认 90） |
| 错误码 | 反引号大写 | `IDEMPOTENCY_CONFLICT`（409） |

代码行号必须写**区间**并标注核对日期（文首版本行统一声明），避免单点行号漂移后无法判断。

## 三、五份文档各写什么

### 3.1 `README.md`（模块总览）——建议 80~150 行

必须包含、按此顺序：

1. **一句话定位**：这个模块解决谁的什么问题（一句，不超过 40 字）。
2. **边界**：做什么 / 明确不做什么（各 3~5 条），杜绝"顺带描述别的模块"。
3. **能力地图**：按"用户视角的能力"分组，不是按代码目录分组。
4. **表速查**：表名 / 中文名 / 角色（明细/台账/配置）/ 写入方 / 保留策略，一行一表。
5. **接口速查**：方法 + 路径 + 一句话用途，指向 `03-接口清单.md`。
6. **代码地图**：目录 → 职责（一段代码只出现一次，避免与 `04` 重复，此处只给导航级）。
7. **术语表**：本模块专有词（状态值、缩写、内部叫法），每条一句。
8. **文档导航**：四份正文各一句话职责。

不写：字段清单、SQL、完整请求示例、排障步骤（都在正文）。

### 3.2 `01-业务功能说明.md`——建议 150~300 行

| 章节 | 必写内容 |
| --- | --- |
| 1 定位与边界 | 业务价值（回答哪几个现实问题）、上游/下游系统、与相邻模块的职责切分 |
| 2 角色与场景 | 角色（运维/开发/对接方/审计）× 场景 × 触发入口（页面或接口） |
| 3 功能清单 | `F1…Fn` 编号表：功能名 / 触发方式 / 前置条件 / 主要输出 / 对应端点 / 对应表 |
| 4 业务流程 | 每条主流程一张时序（mermaid `sequenceDiagram` 或编号步骤），覆盖正常、失败、并发三类路径 |
| 5 状态与判定 | 所有枚举取值表 + 判定规则（谁赋予、何时变更、如何互斥）；**这是全目录唯一的取值定义处** |
| 6 数据保留与清理 | 表 → 保留期 → 清理触发者（启动/手动/无）→ 删除语义（物理/逻辑） |
| 7 非功能约束 | 性能（是否阻塞请求、批量上限）、安全（脱敏/摘要/不落明文）、容量（截断阈值） |
| 8 已知限制 | 明确"现在做不到什么"，每条给影响与临时绕法 |

写法要求：**用行为语言**（"请求进入后先判断…"），不用数据结构语言（"该表有 16 个字段"属于 `02`）。流程里出现的表名必须能在 `02` 找到。

### 3.3 `02-数据模型与表关系.md`——建议 200~400 行（**本规范最重要的一份**）

强制章节与写法见 §五。核心要求：**读者只看这一份，就能自己写出正确的 JOIN / 排查断链**。

### 3.4 `03-接口清单.md`——建议 150~350 行

| 章节 | 必写内容 |
| --- | --- |
| 1 全局约定 | 前缀、鉴权方式、响应包装结构、分页参数与返回结构、时间与时区格式、错误响应结构 |
| 2 端点台账 | 一张总表：序号 / 方法 / 完整路径 / 用途 / 权限 / 是否写操作 / 是否幂等 |
| 3 逐端点 | 请求参数表（名/位置/类型/必填/约束/说明）、响应字段表（只列业务字段，公共字段引用 §1）、至少 1 个真实示例、错误码表 |
| 4 前端/调用方映射 | 哪个前端函数/页面调哪个端点（后端没有前端就写"无"） |
| 5 调用顺序建议 | 排障或联调时的推荐调用链（如"列表 → 详情 → 追踪"） |

要求：每行列名与 `02` 的字段字典同名；枚举取值与 `01` §5 一致；错误码必须是代码里真实存在的（引用 `app/contract/errors.py` 或业务异常定义）。

### 3.5 `04-实现与运维说明.md`——建议 150~300 行

| 章节 | 必写内容 |
| --- | --- |
| 1 代码地图 | 文件 → 职责 → 关键函数（带行号）；标注"谁被谁调用" |
| 2 关键实现决策 | 3~6 条：为什么这样做、替代方案是什么、代价是什么（这是最有价值的部分） |
| 3 配置项 | 名 / 默认值 / 生效范围 / 调错的后果（不是抄 description） |
| 4 生命周期 | 启动做了什么、关停做了什么、失败时是否阻断 |
| 5 排障手册 | 症状 → 排查顺序（具体 SQL/接口）→ 可能原因 → 处置动作 |
| 6 运维操作 | 清理、补数、临时关闭、回滚 |
| 7 测试覆盖 | 用例文件 + 覆盖了哪些行为 + **哪些行为没覆盖** |
| 8 已知问题与演进 | 引用 `04-03` 报告编号，写清"当前行为 + 计划"；未实现能力集中在此 |

排障手册是验收重点：每条必须是"照着做就能定位"，不能写"检查配置是否正确"这种空话。

## 五、数据模型章节的强制写法

这一节是本规范的核心。以下六个表格**一个都不能少**，格式固定。

### 5.1 表清单（模块概览）

| 表名 | 中文名 | 角色 | 主键 | 唯一键 | 写入方 | 读取方 | 保留策略 |
| --- | --- | --- | --- | --- | --- | --- | --- |

- **角色**只能取：`明细`（一事一行，只追加）、`台账`（技术状态机，可更新/删除）、`配置`（低频变更）、`缓存`（可重建）。
- **写入方**写到"模块.函数"级别，不写"系统写入"。
- **保留策略**写清：永久 / N 天（谁清理）/ 墓碑永久。

### 5.2 字段字典

| 列名 | PG 类型 | 可空 | 默认 | 含义 | 取值 / 约束 |
| --- | --- | --- | --- | --- | --- |

七条硬要求：

1. **类型按数据库口径写**：`String(64)` 写 `varchar(64)`，`BigInteger` 写 `bigint`，`JSONB` 写 `jsonb`，`DateTime(timezone=True)` 写 `timestamptz`。不要照抄 SQLAlchemy 表达式。
2. **默认值**写实际生效值（Python 侧 `default=` 与数据库 `server_default` 要区分，注明"应用侧默认"或"库默认"）。
3. **JSONB 列必须展开子结构**：单独一张小表列出 key / 类型 / 取值域 / 是否必现，并说明"缺键"与"值为 null"的区别。
4. **枚举列罗列全部取值 + 含义 + 由谁写入**，值定义在本表内，不写"见代码"。
5. **金额/时长/ID 类列写明单位与来源**（如 `process_time` 是字符串 `"12.3ms"`，不是数值，不能做 SQL 求和——这类坑必须写出来）。
6. **冗余列必须标注"与哪一列同源"**（如 `username` 在 HMAC 调用下等于 `client_id`）。
7. **继承来的公共列**（`id/uuid/created_time/updated_time`）单独一小节说明语义；**删除行为必须单独写清**——本项目同一库里有两种删除语义（`api_log`/`chunk` 物理删、`revision` 留 `status='archived'` 墓碑行），读者最容易写错的恰恰是"这条记录删了之后还在不在"。凡涉及删除的模块，必须显式回答"行还在吗、怎么查、能恢复吗"。

### 5.3 键与索引

| 类型 | 名称 | 列 | 用途 | 是否被查询实际命中 |
| --- | --- | --- | --- | --- |

"是否被命中"一列很关键：把"建了但没用的索引"标出来（写 `未命中：无对应查询`），这是后续优化的输入。

### 5.4 关联关系总表（核心中的核心）

| 编号 | 源（表.列） | 目标（表.列） | 关系语义 | 基数 | 约束方式 | 一致性保障 | 断链后果 |
| --- | --- | --- | --- | --- | --- | --- | --- |

- **基数**用 `1:1` / `1:0..1` / `1:N` / `N:M`，并注明"在什么条件下"（例：`api_log.request_id : nonce.request_id = 1:N`，因为一次首用可对应多条审计 = 首次 + 若干次重放）。
- **约束方式**只能是：`物理外键` / `唯一约束` / `应用层约定` / `无`。当前项目四张表**均为"无物理外键"**，写 `无（应用层约定）`。
- **一致性保障**写具体机制：唯一约束名、单条 upsert、状态机、前缀匹配规则、不做校验。
- **断链后果**写清"查不到会怎样"（例：追踪页缺一段、清理任务失效、重复执行）。这一列直接决定排障顺序。

### 5.5 逐条关系说明（R1…Rn）

每条固定四段：**语义**（业务上是什么关系）→ **实现**（代码在哪写这个值）→ **查询**（怎么把两张表对上，给可执行 SQL 或 ORM 片段）→ **边界**（什么时候对不上、对不上是否正常）。

特别要求：**多态关联必须单独说明匹配规则**。例如 `idempotency.biz_id` 同时承载 `job_id/request_id/event_id`，按 `request_id` 追踪时用"精确匹配 + `request_id-` 前缀"，必须写清前缀的来源与遗漏场景。

### 5.6 写入与读取矩阵

| 表 | 写入方（模块.函数） | 事务边界 | 读取方 | 一致性要求 |
| --- | --- | --- | --- | --- |

- **事务边界**必须写：请求级事务 / 独立会话立即提交 / 延迟任务（响应后）。
- 同一张表存在多写入路径时必须全部列出（这是双写缺陷的高发点）。

### 5.7 生命周期与清理

| 表 | 有效期 | 起算点 | 清理触发 | 删除语义 | 例外 |
| --- | --- | --- | --- | --- | --- |

必须区分"记录过期（不可再用）"与"记录被删除（行消失）"，以及"墓碑永不清理"这类例外。

## 六、动笔前的代码盘点清单

**禁止凭印象写文档**。按此清单用工具盘一遍，把结果直接填进对应表格：

```bash
# 1. 表清单与模型文件（找 __tablename__）
grep -rn "__tablename__" app/modules/<域>/ --include="*.py"

# 2. 物理外键（当前项目预期为空）
grep -rn "ForeignKey" app/modules/<域>/

# 3. 端点（找 APIRouter 与 route_class）
grep -rn "APIRouter(\|@.*Router\.\(get\|post\|put\|patch\|delete\)" app/modules/<域>/

# 4. 写入方（找 model 类名被谁实例化 / add）
grep -rn "<ModelName>" app/ | grep -v "model.py\|models.py\|crud.py"

# 5. 配置项（找 settings.<前缀>）
grep -rn "settings\.<PREFIX>" app/ | grep -v "config/setting"

# 6. 测试覆盖
grep -rln "<域>\|<表名>" tests/
```

盘点结论写进 `04-实现与运维说明.md` §1，别人可复核。

## 八、正反例

### 8.1 功能描述

```markdown
❌ 本模块实现了 api_log 的 CRUD，包含 list/detail/delete/clean 四个接口，
   并通过 ApiLogRoute 采集日志，使用 JSONB 存储 security_check。

✅ 运维想知道"昨天 GSI 调 #05 为什么失败"：打开「接入调用追踪」，
   默认只看 /v1，按时间倒序；点开某条能看到四头校验明细与被拒原因（failure_code）；
   若怀疑同一个请求被重复提交，点「追踪」输入 request_id，一次带出调用、nonce、
   幂等、结果四条记录（R1–R4）。（对应端点 03-接口清单 F2/F7）
```

### 8.2 字段说明

```markdown
❌ | process_time | String(20) | 处理耗时 |
   （读者会写 ORDER BY process_time 或 SUM，结果是字符串排序）

✅ | process_time | varchar(20) | 是 | 否 | 处理耗时，形如 `"12.3ms"` | 字符串，由 `f"{(perf_counter()-start)*1000:.1f}ms"` 生成；
   做耗时统计须先 `CAST(REPLACE(process_time,'ms','') AS numeric)`，或改用 `created_time` 差值 |
```

### 8.3 表间关系

```markdown
❌ api_log.request_id 关联 nonce 表。

✅ | 编号 | 源（表.列） | 目标（表.列） | 关系语义 | 基数 | 约束方式 | 一致性保障 | 断链后果 |
   | --- | --- | --- | --- | --- | --- | --- | --- |
   | R1 | api_log.request_id | nonce.request_id | 审计行 → 首用登记 | 1:N（重放只加审计行） | 无（应用层约定） | nonce 唯一键是 (client_id, nonce)，request_id 允许为空 | 追踪时 nonce 段为空；该请求未走到登记步骤，属正常 |

   R1 补充：重放会新增 api_log 行但不新增 nonce 行，因此一条 nonce 可对应 N 条审计。
```

### 8.4 已知限制

```markdown
❌ 结果台账暂不支持部分场景。

✅ 结果台账（sbp_ai_system_request_log）**当前没有任何写入方**：表结构、CRUD、
   页面标签页均已就绪，但契约层尚未在生成类接口里登记 running/succeeded 状态，
   因此「近 N 小时 · 在途请求」恒为 0。#15 超时结果查询上线时补写入方，
   在此之前不要基于该表做容量规划。（关联 04-03 报告 §1.3「能力现状」与 §二 C 组）
```
