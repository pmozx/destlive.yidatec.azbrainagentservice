### 1.4 调用关系（谁被谁调用）

```
/v1 路由  app/modules_api/kb/{parse,knowledge,chat,duplicate}/controller.py
            ├─ base.deps：验签 / nonce / 幂等 / 回放（统一依赖，不写在各业务包里）
            └─ service.py（契约投影 + 错误码映射）
                 └─ app/modules/kb/*/service.py（领域）
                      ├─ */crud.py（SQL）
                      ├─ retrieval/service.py（授权 + 召回）
                      └─ GSI: modules_gsi/km/doc_publication/service.py（授权集合、团队名）

/api/v1/kb 路由  app/modules/kb/*/controller.py 或 admin_controller.py
            └─ 同一个 kb 领域 service（管理端出入口）
```

**单向依赖**：`modules_api.kb → modules_api.base → modules.kb → modules_gsi`。反向不存在——`base` 与 `kb` 都不被领域层 import，领域异常由契约层翻译。

## 二、关键实现决策

### 2.1 向量化必须在事务之前完成

`KbEntryService._build_chunk_rows` 先调 embedding 服务拿到全部向量，再在 `async with session.begin()` 里整批写。替代方案是「边写边向量化、失败回滚」，代价是向量服务超时会让数据库持有事务几十秒（`EMBEDDING_TIMEOUT=60`），长事务既锁行又占用连接。当前做法的代价是「向量化成功但写库失败时白算一次」，可接受，因为写库失败是真正的 500，调用方必须重试。

配套的是**全量替换 + CAS 指针切换**：新版切片整批写入新 `record_id`，指针用 `advance()`（带 `current_revision` 条件）切换。这样「读到的永远是完整的一版」，不会出现半新半旧。

### 2.2 授权先于召回，且授权集合只算一次

`retrieval/service.py::authorized_publication_ids` 被三处共用：契约 #07、管理端检索调试、问答（含历史可见性判定）。检索 SQL 一律带 `publication_id IN (...)`，而不是查完再过滤。

为什么不「先查后过滤」：① 越权内容会进入候选窗口，挤掉合法命中（20 条候选被别人的知识占满）；② 过滤在 Python 侧做，向量距离排序已经失去意义。代价是授权集合本身可能很大（上千个 ID），SQL 里 `IN` 列表会有解析开销——当前量级可接受，再大就需要授权表落库 + JOIN。

### 2.3 精排窗口就是返回条数上限（默认 6）

`SEARCH_RERANK_WINDOW=6` 同时是「送精排的候选上限」和「该通道的返回条数上限」。这不是偷懒，是实测推导：CPU 上 bge-reranker 与条数严格线性（1 条 1.6s、6 条 6.1s、20 条 18.9s），窗口给到 20 会必然耗尽 `SEARCH_RERANK_TIMEOUT=8s` 再降级，等于白付一次尾段耗时。

两层闸门：绝对下限 `KB_RERANK_MIN_SCORE=0.3`，相对下限 `top1 × KB_RERANK_RELATIVE_RATIO=0.6`，取两者较大值。相对闸门必须在 0–1 空间算——`RERANK_SCORE_IS_LOGIT=true` 时若直接乘比例会反向（logit 可为负）。

### 2.4 迟到丢弃：行锁 + 状态快照

生成可能要 90 秒，期间会话可能被删除或清空。`KbChatService._assert_turn_alive` 在写回前 `SELECT ... FOR UPDATE` 重读会话，比对「开始时快照的状态」与「现在的状态」：`deleted` 或 `active→cleared` 即判 `TURN_DISCARDED`，不写任何行。

替代方案「生成前加锁」会让整个生成期间持锁，删除请求要等 90 秒；「写回时不检查」会把已删会话写活，违反 #13「清空后旧回答不可见」。当前方案只在毫秒级的写回窗口内持锁。

### 2.5 治理快照自包含 + `scope_digest` 排除易变字段

`dup_result.groups` 存的是**契约投影全文**（含 `items`），所以翻页/详情/预览不依赖当时的库状态，只依赖快照 + 重新校验的来源摘要。翻页时 GSI 会重新签发 `scope`（`scope_id` 和两个时间戳都变了），因此比对用 `scope_digest`——对「resources + drafts 内容 + kinds + score_profile」取摘要，**刻意排除** `scope_id`/`issued_at`/`expires_at`。

治理行用 `group_key`（类型 + 排序后成员身份的摘要）而不是 `result_id` 做键：结果是 30 分钟的，人工结论要跨版本延续；成员一变就是另一个 `group_key`，结论不会被张冠李戴。

### 2.6 解析失败是「任务失败」，不是「请求失败」

#01 只在 202 之前做**请求级**错误（文件拉不下来、超 10MB、后缀不支持），一旦受理，后续任何失败都是任务态：`status=failed` + `error_code=PARSE_FAILED` + HTTP 200。

这条边界必须守住，否则 GSI 无法区分「任务没受理（该改参数）」与「受理了但文档有问题（该人工看）」。#02 的响应结构就是为此设计的：成功带 `result`，失败带 `error_code`，两者互斥。

### 2.7 关键词 GIN 索引不在模型里声明

`ensure_keyword_index()` 在启动期幂等补建 `gin_trgm_ops` 索引，而不是写进 `KbChunkModel.__table_args__`。原因：`create_missing_tables` 对已存在的表一律跳过，写进模型也只对新库生效；更严重的是索引建不出来（缺 `pg_trgm` 扩展、权限不足）会把整张表的 DDL 一起带崩。存量库走 `sql/v1.6_keyword_search_index.sql`（`CONCURRENTLY` 人工建，避免锁表）。

### 2.8 幂等回放前先校验业务行还在

幂等台账保留 90 天（`CONTRACT_IDEMPOTENCY_TTL_DAYS`），而任务行可能被清库/迁库带走。不校验时，同 `job_id` 重提会命中 `succeeded` 台账直接回放首次 202，而 `#02` 永远 404——调用方看到的「受理成功」与业务事实完全脱钩，且脚本侧会空转到超时。

因此 `deps.idempotent_guard(scope, verify_existing=...)` 支持业务存活校验：回放前先查任务行，不存在就 `release` 掉台账、按首次请求重新受理（打一条 `幂等回放目标已不存在` 警告）。`parse` 域已接上（`controller._parse_job_exists`），`request` / `event` 域暂不传，保持原语义。`tests/contract/client.py::wait_parse_job` 也相应把非 200 当作终止条件，避免 404 后继续轮询到 600s。

### 2.9 管理端没有 scope：用 `publication_ids` 反查

契约 #16/#17/#19 的比对依据是 GSI 随请求签发的 `scope.resources`（`record_id` + `content_hash`）。管理台没有这个上下文，所以四个新端点把「比谁」降级成 `publication_ids`（留空=全部生效），由 `dup_result/scope.py::build_scope_from_store` 在库里反查当前生效快照，拼出**结构完全一致**的 `ScopeData` 再交给同一个 `dup_result` 引擎。

这样做的好处是检测算法、快照、物化、预览全链路一行不改；代价是「范围」与「内容」同源，一旦传了不存在的 `publication_id` 就必须 400（不能静默少比），否则页面会看到一份「看起来很干净」的假结果。

### 2.10 管理端整单删除改为逻辑删

原实现走 `crud.delete_cascade` 物理删发布单元+版本+切片，与契约 03.4 的语义不一致：同一条知识在两个入口的「删除后果」不同，排查时容易误判。现在 `KbPublicationService.delete` 只置 `status=deleted`（重复调用幂等），检索 SQL、治理范围生成、`effective_pointers` 都硬过滤 `status=active`，因此**删除即不可召回**；行、版本、切片保留，`GET /detail` 仍可追溯到「为什么消失」。

物理删函数保留但无页面入口，只供内部脚本处理真正需要腾空间的场景（如误导入的脏数据）。

### 2.11 GSI 的 `timestamp(6)` 不做时区换算

GSI 业务表的时间列是 `timestamp(6)`（无时区，落库即业务本地时间），本侧自有表是 `timestamptz`（UTC 存、展示时转本地）。两者共用一个 `format_datetime` 会让 GSI 时间凭空 +8 小时——同一页上「GSI 更新时间」与「本侧创建时间」因此对不上，排障时容易误判成「GSI 没更新」。

所以 `modules_gsi/base.py::format_gsi_datetime` 直接 `strftime("%Y-%m-%d %H:%M:%S")`，schema 里该列类型是 `str` 而不是 `datetime`（避免 Pydantic 再序列化成 ISO 8601 + `Z`）。代价是前端拿到的不是 ISO 格式，排序与格式化只能按字符串处理——当前只有展示场景，可接受。

替代方案「在 SQL 里 `AT TIME ZONE` 转成带时区」被否掉：GSI 的列没有时区语义，硬套一个时区等于替对方声明业务口径。

### 2.12 关联表只有两个数字 → LEFT JOIN + Pydantic 派生有效性

`sbp_sys_audience_team_member` 只有 `team_id` / `user_id`，`sbp_km_doc_publication` 只有 `team` 编码。页面要回答「这个成员在哪个团队、还生效吗」，必须联表；但用 INNER JOIN 会把两类**最需要排查**的行藏起来：团队已删/停用、`team` 存的是历史名称。

因此联表一律 `LEFT JOIN`，并在输出 Schema 的 `model_validator(mode="after")` 里派生 `team_matched` / `team_valid` / `user_exists` / `user_valid`：

- `team_matched = team_status is not None`（编码命中受众团队表）
- `team_valid = team_matched and team_status == "1" and team_deleted == 0`

派生放在 Schema 而不是 service：同一份判断被「用户与组织关系页」的团队下钻、发布关系页、`user-teams` 统计三处用到，放 service 会重复三遍；放 Schema 后 service 只负责拼 JOIN，前端也不允许自己再算一遍。

### 2.13 步骤台账：一步一行，失败必落行，续跑只靠快照

`sbp_ai_kb_parse_step` 一次执行、一步一行（`job_id + attempt + step`），不是日志：页面要回答「卡在哪、为什么失败、能不能从这步继续」，而日志只存在于运维能看到的地方。

三条约束决定了它的形状：

- **失败必落行**：`_track_step` 是上下文管理器，`except` 里先写 `failed` + `error_code` 再 `raise`。若改成「调用方自己 `try/except` 记一笔」，早晚会漏掉某一步——而漏的那一步正好就是用户来问的那一步。
- **非致命失败也要落行**：`artifacts`（产物归档）与 `pages`（页图）失败只记 `failed` + `warnings`，任务继续。`fatal` 列写的是「该步失败会不会中断任务」，不是「该步失败了没」。
- **续跑快照只存能活过进程的东西**：`output` 里放 `extract` 的 `text/page_map/warnings`、`faq`/`chunk` 的 `chunks`。解析器对象（`ParsedDocument.images`、`ChunkedDocument`）是内存对象，事后再拿不回来，所以 `artifacts`、`chunk` 两步在 `_resume_point` 里被强制回退到 `extract`——**宁可多跑一次解析，也不给一个「看起来续跑了、其实产物是半截」的结果**。

`_resume_point` 的回退规则是递进的：先取上一轮第一处 `failed`/`running` 的步骤（`running` 也算——进程被杀时没人会写 `failed`），再往前退到「前序步骤上一轮全部 `succeeded`/`skipped`」的位置（`skipped` 也算走完，否则非 PDF 任务因 `pages` 永远 `skipped` 而只能全量重跑）。

### 2.14 attempt 乐观锁：重跑不杀旧协程

重跑是 `attempt+1` + 回 `queued` + 起新的后台任务，旧协程根本没被取消（`BackgroundTasks` 没有句柄可杀），它随时可能复活接着写库。

因此所有状态与产物写入都带 `WHERE uuid=? AND attempt=?`（`crud.update_if_attempt`、`KbParseJobService._update`），`rowcount=0` 就当本次执行已被接管：`complete` 返回 `False` 后流水线直接报「本次执行已被新的执行接管，产物未落库」，而不是默默写一份旧产物盖掉新一轮的结果。

为什么不用「先读 attempt 再判断」：读到的值在 `UPDATE` 提交前就可能过期，只有条件写在 `WHERE` 里才由数据库保证互斥。

### 2.15 追踪（trace）与指标表分工，不合并

问答的可观测性由两层组成，**各答一个问题**：

| 层次 | 回答 | 存储 | 保留 |
| --- | --- | --- | --- |
| LangSmith trace（`app/core/observability/`） | 「这一轮发生了什么」：run 树、每步耗时、模型输入输出、token | 外部 SaaS | 由平台定 |
| 指标表 `sbp_ai_kb_chat_turn_metric` | 「一段时间质量与成本怎么变」：按天/模型/模式/提示词聚合 | 自有库 | 人工裁剪 |

两者用 `trace_id` 对齐（`ChatTurnMeter` 在 `trace_id` 为空时自动取 `current_trace_id()`）。不把指标塞进 `chat_message`：消息表要逐条投影给 #10/#15，加观测列会让契约投影长出第二套语义；也不把 trace 当指标用：SaaS 不可用、或未开追踪的环境就没有任何质量底账。

三条实现约束：

- **开关只看配置**：`AI_TRACE_ENABLE=false` 时装饰器直通原函数（不建 run、不加 callback），业务侧不各自判开关；未配 `AI_TRACE_API_KEY` 时**失败关闭**并在启动日志告警——「以为在采集、其实没有」比不采集更危险。
- **配置必须在首次调 LangChain 前写 env**：`langsmith.get_env_var` 带 `lru_cache`，晚写不生效；启动期 `configure_tracing()` 是唯一写入点，并 `cache_clear()` 兼容测试/热重载。
- **脱敏是开关**：`AI_TRACE_MASK_CONTENT=true` 时写死 `LANGSMITH_HIDE_INPUTS/OUTPUTS/METADATA`，只留 run 树、耗时、token 与数值口径；关闭意味着问题、检索切片、模型回答会原样进外部 SaaS，需环境负责人确认合规。

为什么用 `traceable` 而不是 `create_agent`/`StateGraph`：单轮 RAG 是「一次检索 → 一次生成」的直出，没有分支决策，套 agent 循环只会多一层消息协议与一批必须丢弃的中间帧（规范 L24）。需要多步决策时再换 `StateGraph`，节点名与 `RUN_TURN/RUN_RETRIEVE/RUN_GENERATE` 对齐即可。

### 2.16 证据正文（`content`）与引用片段（`quote`）是两个字段

`ChatEvidence` 同时携带两个值：`content` 是切片正文全文，只进模型上下文；`quote` 是截断到 `KB_SNIPPET_CHARS` 的前缀，只进 `citations`（契约要求 `quote` 是切片正文的逐字子串，可回查校验）。

为什么必须分开：此前两者是同一个值（都取截断后的文本），模型每条证据只能看到 160 字，而 `KB_CONTEXT_MAX_CHARS` 号称 6000——**上下文预算形同虚设**，长切片的后半段永远进不了模型。反过来把 `quote` 放开到全文又会把整段正文塞进 `chat_message.citations`（#10/#15 逐条下发，响应体会骤增）。

`KB_SNIPPET_CHARS` 从此只管「引用展示长度」，不再决定「模型能看多少」；后者由 `recall_block` 按 `KB_CONTEXT_MAX_CHARS` 累计，且以**整条证据**为粒度截断——半条证据既不能引用也不该占上下文。

### 2.17 灰区二判：结构化输出，默认关，失败不升级

条数闸（`KB_GRADE_MIN_CHUNKS`）与精排闸（`KB_RERANK_MIN_SCORE`）之间有一段灰区：条数够、但最高相关度偏低（例如 0.4 分的关键词重叠）。此时让模型判一次「现有资料是否足以回答」比直接答或直接拒都稳。

三条约束：

- **默认关**（`KB_GRADE_JUDGE_ENABLE=false`）：判定是多一次模型调用，就多一次延迟与费用，按环境开启；
- **只在灰区调用**：`top_score < KB_GRADE_JUDGE_TOP_SCORE`（默认 0.55）才判，高分一次都不花；
- **失败不升级**：上游异常、超时（`KB_GRADE_JUDGE_TIMEOUT`）、结构不可解析一律返回「够答」——判定是增强，不是门禁；质检挂了而拒答，等于把可用系统降级成不可用。

结论用 `with_structured_output(SufficiencyVerdict)` 拿（布尔 + 缺什么），不让模型自由发挥一段话再正则解析。判为不足时复用现有拒答分支（清空 `evidences` → 走 `no_evidence` 路径），**SSE 帧序一行不改**；判定与提示词共用 `recall_block` 同一份文本，避免「模型看到的」与「质检判过的」不是同一批资料。

### 2.18 指标怎么被读：只读投影，不在消息接口里混写

指标写侧（`meter.py`）一直有，但此前**没有任何读出口**——`02` §3.11 那 23 列只能进库查。现在补的是两个**只读**端点（§三 `3.10`）与前端对齐逻辑，`chat_message` 的输出契约一行未动。

四条实现约束：

- **不并进消息响应**：`KbChatMessageOutSchema` 是逐条投影给 GSI 的审计证据（正文 + 引用八元组 + 依赖三元组），指标是可自由加列的观测数据；两套混进同一个响应，任何一侧加字段都会改动另一侧的契约。页面按 `assistant_message_id` 在**前端对齐**。
- **汇总必须 JOIN 会话表**：概览卡要与列表页同一筛选口径（会话 ID / 用户 / 标题 / 状态只存在于 `chat_session`），而指标表只有 `session_id`。`KbChatTurnMetricCRUD.summary` 用 `select(count/sum/avg).select_from(metric).join(session)`；反过来「先查会话 id 再 `IN`」的参数个数会随会话量线性膨胀。聚合用 `func.sum(case(...))` 而非 `count().filter(...)`，前者在 MySQL / PG 上语义一致。
- **汇总不继承 `BaseQueryParam`**：继承会白送一个 `created_time` 时间范围，而过滤落在**会话表**上——页面传「今天」会被误读为「今天跑的轮次」，与列表的「今天建的会话」不是同一件事，概览卡与列表就会对不上。
- **出口一律显式 `to_out`**：`crud.page(...)` 的 `out_schema` 会 `model_validate` 并静默取默认值（会话列表曾因此返回空串），所以 `admin_service` 逐行手写映射；`KbChatTurnMetricOutSchema` 也不继承 `BaseSchema`（本表无 `uuid`/`updated_time`，继承只会恒定多两个 `null`）。

前端（`views/module_kb/chatRecord`）两侧对齐的口径：

- 概览卡走 `summary`，与 `useTable` 的 query 同源；`useTable` 的 `search/reset` 内部直接 `load()`，因此解构改名后在本地包一层，`reset` 必须**先** `await` 会话列表重置再拉概览（否则读到旧 query）。
- 抽屉一次拉本会话全部指标（100/页 翻至 `has_next=false`，上限 10 页）：两套分页强行对齐反而会错位。
- 失败轮（`assistant_message_id` 为空）只插入**当前页时间窗**内的那几条，跨页由抽屉顶部 alert 的 `failed_turns` 计数兜底，并明说「分页按消息计；失败轮不占消息分页」。
- 列表概览与抽屉概览用两个 ref（`listStats` / `sessionStats`），否则关掉抽屉后列表数字会被单会话值覆盖。

### 2.19 GSI 关系页收成一页：以用户为主体 + 关系走 EXISTS

原「组织与成员 / 用户 / 团队与成员」三页各自用一张关系表分页，`total` 是**关系条数**：同一个人挂三个组织就在列表里出现三行，翻页会把一个人切成两半，也没法回答「这个人一共在几个团队」。现在收成一页（`views/module_gsi/relations`），列表只读 `GET /gsi/sys/user/list`，组织与团队降级成筛选维度：

- **一人一行**：`org_id(+include_sub)` 与 `team_id` 都用 `EXISTS` 子查询，不 join 关系表，`total` 回到「人数」；两个 `count` 用标量子查询带出，行内直接显示 `组织 N / 团队 M`，省掉每行一次详情请求。
- **含下级只在后端展开**：`SbpSysOrgService.subtree_ids` 读 `(id, parent_id)` 两列做 BFS，自引用丢弃、互指成环靠 `visited` 截断，与 `_build_tree` 同一套容错；前端只传 `org_id + include_sub`，不自己算子树。
- **组织与团队互斥**：两个条件同时生效时「这人为什么出现」说不清，所以选组织就清团队、选团队就清组织（左栏切换维度同样清空）；左栏默认落在**受众团队**（排到组织树左侧），因为知识可见性只由 `group_code` 决定，组织只回答「人在哪个部门」。
- **列表按字段分列**：账号 / 中文名 / 英文名 / 删除状态各占一列，不再把账号与已删除标签塞进「用户」合并单元格 —— 排查「账号对不上人」「已删账号仍挂团队」时这些字段要能单独看、单独复制。
- **团队列表只保留浏览**：受众团队改用 6 列小表格（团队ID / 团队编码 / 团队名称 / 负责人 / 状态 / 团队有效），点行即下钻；`group_code` / `group_name` / `status` / `deleted` 四个查询条件先隐藏，接口能力保留（团队量有限，翻页足够）。
- **代价**：`page-with-org` / `page-with-team` 仍留在 Swagger 供关系行级排障，但前端不再调用——它们回答的是「这条关系存不存在」，与新页回答的「这个人是谁、挂在哪」不是同一个问题。
- **循环导入**：`user/crud` 统计归属数要读两张关系表的 model，而 `org_member/service` 又要用 `SbpSysUserCRUD`，模块级互相 import 会在 `sys` 包初始化时爆循环 —— 后者的 import 下沉到 `user_orgs()` 方法内。

### 2.20 知识发布关系并入知识文档详情抽屉

原「知识发布关系」页（`views/module_gsi/docPublication`，已删除）单独用 `page-with-team` 分页，回答的是「这条关系指向哪个团队 / 哪一版」——与「这篇知识现在有没有生效关系」其实是同一个问题，用户得跨两页用 `doc_id` 对齐。现在收进知识文档页的详情抽屉：

- **一屏三级**：文档档案 → 送审快照明细（`doc_record/list?doc_id=`，二级抽屉看 `snapshot_json`）→ 知识发布区块（仅 `status=Published` 时请求 `page-with-team?doc_id=`）；快照与发布关系都是个位数，`page_size=100` 一次拉完，抽屉里不再叠第二套分页。
- **送审脉络直接可读**：快照明细带 `created_by`（送审人）、`team`（受众团队编码，内容审为空）、`assignee`（审批人）、`created_at`（送审时间）与 `updated_at`，二级抽屉再给 `comment`（保存说明/审批意见）；默认 `created_at` 倒序，最新一次送审在最前面，不需要再点进详情拼时间线。
- **未发布不请求发布接口**：`Draft` 必然没有生效关系，省掉一次必然为空的请求；未发布时发布区显示空态而非空表。
- **未命中口径不丢**：发布区保留 `team_matched` / `team_valid` 并给未命中条数 alert —— 这是发现「team 存了历史名称」的唯一入口，不能因为收页面就略掉（`01` §八 L9 的处置动作因此改到本抽屉）。
- **生效快照可直接点开**：发布行的 `record_id` 是链接，直接开二级抽屉看该版 `snapshot_json`，不必回快照列表按 ID 找。
- **代价**：跨文档按团队反查（「某团队被授权了哪些知识」）页面上没有了，走 Swagger 的 `page-with-team?team=` —— 与 §2.19 同一取舍：接口不删，页面只留主路径。

## 四、生命周期

### 4.1 启动（`app/__init__.py` lifespan）

1. 建扩展：`vector`（pgvector）、`pg_trgm`。
2. 建表：`kb.bootstrap` 十一张（已存在的表跳过，不做迁移；存量库的 `sbp_ai_kb_parse_step` / `sbp_ai_kb_chat_turn_metric` 靠这一步建出来，也可手工跑 `sql/v2.0_parse_step_tracking.sql` / `sql/v2.1_kb_chat_turn_metric.sql`）。
3. `ensure_keyword_index()`：幂等补建 `gin_trgm_ops`（受 `SEARCH_INDEX_AUTO_CREATE` 控制）。
4. 审计表清理 → **`KbParseJobService.reset_unfinished()`**：把 `queued/running` 改判 `failed`（`error_code=PARSE_FAILED`），避免重启后任务永远转圈。
5. 对象存储：`S3_ENABLE` 且 `S3_AUTO_CREATE` 时幂等建桶（页图预览依赖，失败只告警）。
6. 契约台账清理：过期 nonce、过期幂等。
7. `configure_tracing()`：把 `AI_TRACE_*` 写进 `LANGSMITH_*`（必须在首次调 LangChain 之前，见 `§2.15`）。
8. 种子数据。

任一步失败**只记日志不阻断启动**（除建表失败，那会让整域不可用）。

### 4.2 运行期

- 解析任务跑在 FastAPI `BackgroundTasks` 里（进程内），**不是独立 worker**：进程重启 = 任务失败（由第 4 步兜底）。
- SSE 流由请求协程持有，客户端断连触发 `is_disconnected`，停止生成。

### 4.3 关停

- 无优雅停机钩子：正在生成的回答会被中断，会话里可能只写入 user 行（不会写入半截 assistant 行，因为两行是同事务写）。
- 页图存在对象存储（`parse-previews/<job_id>/page-<n>.png`，再加 `S3_KEY_PREFIX`），不随进程清理；失效靠预签名 URL 过期，桶内对象交生命周期策略回收。

### 5.1 解析任务一直 `queued` / `running`


1. `SELECT uuid, status, progress, error_code, updated_time FROM sbp_ai_kb_parse_job WHERE uuid = '<job_id>';`
2. 看 `sbp_ai_kb_parse_step` 里最新 `attempt` 的第一行 `failed`/`running`：那一步就是卡点，`error_code` 形如 `FAQ_Timeout` / `EXTRACT_CustomException`，`error_message` 是给人看的原因。
3. `updated_time` 是否在动？不动 → 后台任务没跑（多进程部署时 `BackgroundTasks` 只在受理进程内跑）。
4. 查日志关键字：`解析任务失败（job_id=` / `PDF 页图渲染失败（job_id=` / `页图预览保存失败（job_id=`；后者带 `上传流失败` + `XAmzContentSHA256Mismatch` 时见 §3.6 厂商兼容。
5. 若进程刚重启 → 该任务已被 `reset_unfinished` 改判 `failed`，让 GSI 重新提交（同 `job_id` 幂等会回放旧 202，需换 `job_id`）。
6. 回了 202、日志里却只有幂等台账 `INSERT/SELECT`、没有任务行 `INSERT` → 回放前校验未生效或被绕过：先看日志有无 `幂等回放目标已不存在`（有则已自动作废重跑）；线上旧版本无此校验时，确认 `SELECT biz_id, status, body_hash FROM sbp_ai_system_idempotency WHERE scope = 'job' AND biz_id = '<job_id>';` 后删掉该行重提（详见 §2.8）。

### 5.2 #02 返回 `succeeded` 但 `result.chunks` 为空

1. 请求里 `options.chunk` 是否为 `true`？为 `false` 时 `build_result_chunks` 直接返回 `[]`。
2. 文档是否只有标题、没有正文？分片器不产空切片。
3. `SELECT jsonb_array_length(chunks), jsonb_array_length(warnings) FROM sbp_ai_kb_parse_result WHERE job_id = '<job_id>';`
4. `warnings` 里有 FAQ 截断提示 → 正文超 30000 字符，只有前段参与提取。

### 5.3 03.1/03.3 报 409 `STALE_REVISION`

按这条链查，**从下往上**：

1. `content_hash` 不符：`SELECT publication_id, revision, content_hash FROM sbp_ai_kb_revision WHERE publication_id = '<pid>' ORDER BY revision DESC LIMIT 3;`，对比调用方提交的摘要（摘要算法见 `kb/knowledge/schema.py::canonical_content_hash`，字段为 `seq/heading/content/page_from/page_to`，**不含 `chunk_id`**）。
2. `base_record_id` 不是当前指针：`SELECT current_record_id, current_revision FROM sbp_ai_kb_publication WHERE publication_id = '<pid>';`
3. `revision` 不够大：必须严格大于 `current_revision`（相等也算冲突）。
4. 并发两人同时改 → 后提交者必然 409，这是设计行为，重读基线再提交。

### 5.4 03.2 返回 404（基线读不到）

1. `SELECT publication_id, record_id, revision, status, content_hash FROM sbp_ai_kb_revision WHERE publication_id = '<pid>';`
2. 目标 `record_id` 的 `content_hash IS NULL` → 该快照已被 03.4 删除（墓碑行），404 是正确行为。
3. 行完全不存在 → `record_id` 传错，或该发布单元从未写入。
4. `current_record_id` 有值但查不到对应 revision → 指针断链（R2），检查是否有手工删库。

### 5.5 检索一条都不返回（`no_evidence=true`）

按顺序排除：

1. **先看授权**：管理台调 `POST /api/v1/kb/retrieval/search`，看 `authorized_publication_count`。
   - `0` → 授权问题（用户没有可见发布单元），不是检索问题。
   - `>0` → 继续。
2. **看知识是否可检索**：`SELECT c.publication_id, c.status, c.revision, r.searchable FROM sbp_ai_kb_chunk c JOIN sbp_ai_kb_revision r ON r.record_id = c.record_id WHERE c.publication_id = '<pid>' LIMIT 5;`。`chunk.status=archived` 或 `revision.searchable=false` → 未生效或已停用。
3. **看向量**：`SELECT count(*) FILTER (WHERE embedding IS NULL), count(*) FROM sbp_ai_kb_chunk WHERE status='online';`。有 `NULL` → 写入时向量化被跳过（不应发生）或模型维度变更。
4. **看通道**：`mode=natural_language` 且 `EMBEDDING_BASE_URL` 为空 → 500 `INTERNAL_ERROR`（不是空结果）；`rerank_ready=false` 见 `GET /kb/retrieval/config`。
5. **关键词通道查全文**：`SELECT count(*) FROM sbp_ai_kb_chunk WHERE content ILIKE '%<关键词>%' AND status='online';`。有结果但接口无命中 → 授权过滤掉了。
6. 索引是否建出来：`SELECT indexname FROM pg_indexes WHERE tablename = 'sbp_ai_kb_chunk';`，缺 `ix_sbp_ai_kb_chunk_content_trgm` 时关键词检索会走全表扫（慢但**不会空**）。

### 5.6 问答返回 `no_evidence=true` 但检索明明有命中

1. 问答走的是**自然语言通道**且只取 `KB_RERANK_TOP_N`（8，实际受窗口 6 限制）条，命中不在前 6 名就会判无证据。
2. 精排闸门：`KB_RERANK_MIN_SCORE=0.3` 与 `top1×0.6`。用管理台同一个问题搜一次，看 `score` 是否低于 0.3。
3. `KB_GRADE_MIN_CHUNKS` 被调大过？`grep KB_GRADE_MIN_CHUNKS env/*`。

### 5.7 回答的引用整条消失

1. `SELECT message_id := uuid, role, status, jsonb_array_length(citations) FROM sbp_ai_kb_chat_message WHERE session_id = '<sid>' ORDER BY created_time;`
2. `citations` 为空但 `answer` 正常 → 模型没有给出可验证的引用（`quote` 不是切片正文逐字子串），按设计整条不返回，不是丢数据。
3. `citations` 有值但 #10 不返回 → 依赖失效：`SELECT knowledge_deps FROM ...` 里的 `publication_id` 是否仍在授权范围、`record_id` 是否仍是当前指针。

### 5.8 重复治理 409

| 码 | 含义 | 处置 |
| --- | --- | --- |
| `RESULT_EXPIRED` | 快照超过 30 分钟 | `SELECT uuid, created_time, expires_at FROM sbp_ai_kb_dup_result WHERE uuid='<result_id>';` 确认后让 GSI 重新发起首查 |
| `SOURCE_CHANGED` | 分组内成员内容变了 | 重新 D02 首查（新 `result_id`） |
| `IDEMPOTENCY_CONFLICT` | 同 `request_id` 不同正文 | 换 `request_id` |

`SELECT result_id, group_key, updated_time FROM sbp_ai_kb_dup_group WHERE group_key = '<group_id>';` 可确认治理行是否还在（过期快照不影响它）。

**管理端主动治理（`/kb/dup-groups/{detect,check,preview}`）**

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 400「范围内没有生效内容」 | `publication_ids` 全为非 `active` 或该租户无生效快照 | 先 `GET /publication/list?status=active` 确认；删除过的发布单元不再参与 |
| 400「…不存在」 | `publication_ids` 里有不存在的 ID | 删掉该项（不静默跳过） |
| 400 混租户 / `kinds` 非法 | 多个租户 ID 混在一个范围；`kinds` 不在五类枚举内 | 只传一个租户；`kinds` 用 5.5 的五类取值 |
| 413 `PAYLOAD_TOO_LARGE` | 范围 > `DUP_MAX_SCOPE_ITEMS`（1000） | 缩小 `publication_ids` 分批检测，不支持截断 |
| 409「请重新发起检测」 | 快照超过 30 分钟或服务重启（`dup_result` 为空） | 重新 `POST /detect`，再用新的 `group_id` 预览 |
| 预览 400 动作不合法 | 每个成员必须恰好一条动作；`keep` 只能给主项；`merge_answer` 只给 FAQ 组 | 按详情里的 `members[].hit_id` 逐条给动作 |

管理端上传（`POST /kb/parse-jobs/upload`）同步失败同样在**受理前**返回：空文件 400、后缀不在白名单 400、超限 413，且不产生任务行；对象存储未开启或写失败只影响原件留存（`file_meta.object_key=null`），不影响解析。

### 5.9 SSE 只有 `meta` 就断了

1. `KB_CHAT_STREAM_PING_INTERVAL` 与网关空闲超时的关系：网关 30 秒断连而心跳 15 秒，理论安全；若网关更短，需调小心跳。
2. 日志关键字：`AI 对话流式开始`、`MODEL_FAILED`、`TURN_DISCARDED`。
3. `error` 帧的 `code` 直接对应原因：`TIMEOUT`（首 token 或空闲超时）、`DEPENDENCY_UNAVAILABLE`（授权/向量化）、`MODEL_FAILED`（模型报错）。
4. 若会话在生成期间被删除 → `TURN_DISCARDED` 是正确行为，不是故障。

### 5.10 `/v1` 全部 401

1. 服务端 `CONTRACT_V1_SHARED_SECRET` 是否为空？为空时报 503 而非 401，先排掉这种情况。
2. 时钟偏差：`SELECT now();` 与调用方时间比对，超过 5 分钟直接 401。
3. 签名原文最后一行：body 是否被中间件重排/压缩？用 `curl --data-binary @file.json` 保证字节一致。
4. `DEBUG=true` 时日志会打 `body_sha256` 与 `body_len`，直接和调用方比对。

### 5.11 授权为空 / 有团队但检索不到（用 `/gsi` 逐跳核对）

检索 `no_evidence=true` 且 `authorized_publication_count=0` 时，按授权链**从左到右**核对，每一步都有只读入口（[`03-接口清单.md`](03-接口清单.md) §六）：

| 步 | 查什么 | 命令 | 结论怎么读 |
| --- | --- | --- | --- |
| 1 | 人是否在团队里 | `GET /api/v1/gsi/sys/audience-team-member/user-teams?user_id=<uid>` | `team_count=0` → 没有成员关系，授权必然为空；此时先查 `sbp_ai_kb_chat_session.user_id` 是否写错（非数字主键在入口就返回空集，不报错） |
| 2 | 团队是否有效 | 同上，看 `valid_team_count` | `>0` 但 `<team_count` → 部分团队被停用/删除；团队编码改动会让旧关系失效 |
| 3 | 团队编码对不对 | `GET /api/v1/gsi/sys/audience-team/list?group_code=<code>` | 只有 `group_name` / `audience_team` 命中 → 该团队的历史数据仍在用兼容标识，本侧只认 `group_code`（`01` §八 L9） |
| 4 | 发布关系指向哪个团队 | `GET /api/v1/gsi/km/doc-publication/page-with-team?team=<code>&doc_id=<doc_id>` | `total=0` → 这条知识没发给该团队；`team_matched=false` → `team` 存的是历史名称，授权落空 |
| 5 | 本侧是否有对应行 | `GET /api/v1/kb/publication/detail/<publication_id>` | 404 → 03.1/03.3 还没投递过；`status!=active` → 已停用/删除，检索硬过滤 |

**只看 `/gsi` 不够的一点**：`invisibleTeams` / `expireAt` 本侧未解析（`01` §八 L10），所以「GSI 页面上被排除的团队、本侧仍能召回」是已知缺口，不是数据错。FAQ 侧可先看 `GET /api/v1/gsi/faq/publication/list?faq_id=…` 的 `rules_valid` / `invisible_teams`，确认 GSI 侧到底配了什么。

### 5.12 LangSmith 看不到 trace / 指标表没行

| 现象 | 先查 | 典型原因 |
| --- | --- | --- |
| LangSmith 无数据、启动日志无「AI 追踪就绪」 | `AI_TRACE_ENABLE` | 开关未开，或 `AI_TRACE_API_KEY` 为空（**失败关闭**，启动日志会有一条 warning） |
| 启动日志有「就绪」但仍无数据 | 网络与 `AI_TRACE_ENDPOINT` | 出网被拦或端点写错；脱敏已开时看到 run 树但输入输出为空是**预期** |
| 改了环境变量不生效 | 重启时间 | 配置在进程启动时写成 `LANGSMITH_*` 并清过一次 `lru_cache`；启动之后再改 env 不会生效 |
| 指标表无行、但问答正常 | 应用日志有没有「单轮指标写入失败」 | 指标写入是**失败只告警**的设计（`02` §八 D9）：库连接池耗尽、表未建都会导致缺行，不影响回答 |
| 指标表 `tokens_in/out = 0` | 该轮是不是 `sync` | 非流式门面不返回 usage，记 0 是已知口径，不是漏采 |
| 会话记录页概览卡全 0、但指标表有行 | 筛选条件、`/kb/chat-metric/summary` 的函数日志 | 汇总按**会话维度**过滤（`session_id`/`title` 模糊、`user_id`/`status` 等值）：带了不存在的 `user_id` 或 `status=deleted` 就会真回 0；指标表的行不会被删，会话被软删后依然计入它自己那一行 |
| 抽屉里消息有、指标列全是 `-` | `/kb/chat-metric/list?session_id=...` 是否回空页 | 指标写失败只告警（上一行同理）；或该会话的轮次发生在指标表上线之前 |
| 抽屉对话流里多出「失败轮」行 | 行上的 `error_code` | 不是重复行：断连/超时/生成失败本来就只有指标、没有助手消息；跨页时只看顶部 alert 的 `failed_turns` 计数 |
| 二判从没触发过 | `KB_GRADE_JUDGE_ENABLE` 与 `top_score` | 默认关；开了但在灰区外（`top_score ≥ 0.55`）也不会调 |

```sql
-- 保留 90 天（该保留期目前只是注释，需要人工执行）
```

### 6.3 重跑某个解析任务

同一 `job_id` 会被幂等台账回放旧的 202，**不能直接重提**。做法：让 GSI 生成新 `job_id` 重新下发（旧任务行保留）。

### 6.4 重建关键词索引

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_sbp_ai_kb_chunk_content_trgm
  ON sbp_ai_kb_chunk USING gin (content gin_trgm_ops);
```

或用 `sql/v1.6_keyword_search_index.sql`。`CONCURRENTLY` 不会锁表，但耗时更长。

### 6.5 裁剪问答指标（当前无自动任务）

```sql
-- 先看量与占用
SELECT count(*) AS total, min(created_time) AS since, pg_size_pretty(pg_total_relation_size('sbp_ai_kb_chat_turn_metric')) AS size

-- 只保留 180 天（保留期按审计要求定，没有代码写死）
```

走 `ix_sbp_ai_kb_chat_turn_metric_created_time`；积量大时按天分批删，避免一次长事务。只删指标不删消息：指标缺历史不影响任何业务（`02` §八 D9/D10）。

### 6.6 临时关闭某条通道

| 目标 | 做法 | 副作用 |
| --- | --- | --- |
| 关闭语义检索 | 清空 `EMBEDDING_BASE_URL` 并重启 | 知识写入也会失败（向量化是写入前置），不是只关读 |
| 关闭精排 | 清空 `RERANK_BASE_URL` 并重启 | 检索仍可用，按 RRF 融合序 |
| 关闭契约 | `CONTRACT_V1_ENABLE=false` | `/v1` 全部 404，GSI 立即不可用 |
| 关闭页图 | `PARSE_PREVIEW_ENABLE=false`（或 `S3_ENABLE=false`） | 新任务 `pages=[]`，历史任务不受影响（历史页图仍在桶里） |
| 关闭 AI 追踪 | `AI_TRACE_ENABLE=false` 并重启 | 零上报、无 trace；指标表照写（`trace_id` 置空），质量底账不断 |
| 关闭灰区二判 | `KB_GRADE_JUDGE_ENABLE=false` 并重启 | 灰区低分证据照常作答（不再多花一次模型调用），行为回到接入前 |

### 6.7 回滚

无迁移框架：表结构变更靠 `sql/*.sql` 手工执行（如 `v1.4_merge_entry_meta_into_publication.sql`、`v1.7_dup_group_governance.sql`、`v1.9_parse_result_publish_link.sql`、`v2.0_parse_step_tracking.sql`、`v2.1_kb_chat_turn_metric.sql`）。启动期幂等补列的有 `parse_result` 的 `pages/suggested_doc_type/publication_id/published_time/artifacts` 五条（`ensure_parse_result_schema`）、`parse_job.attempt`（`ensure_parse_job_schema`）与 API 日志的 JSONB 转换；新建表由 `ensure_tables` 建（已登记在 `kb/bootstrap.py::TABLES`，表数 9 → 11，中间新增 `sbp_ai_kb_parse_step` 与 `sbp_ai_kb_chat_turn_metric`）。回滚代码不会回滚表结构，**先确认新代码对旧结构的兼容性**（列只增不改是当前约定；旧代码不读新表/新列，可安全回滚）。

代码回滚到接入追踪/指标之前时：旧代码不读 `sbp_ai_kb_chat_turn_metric`，新表留着不影响运行（只是停止增长）；`AI_TRACE_*` / `KB_GRADE_JUDGE_*` 配置项在旧代码里不存在，留着也不报错。反之从旧代码升上来不需要手工建表（`ensure_tables` 会补）。
