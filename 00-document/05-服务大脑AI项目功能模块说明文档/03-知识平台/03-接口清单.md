## 一、全局约定

### 1.1 两组前缀，两套约定

| 维度 | 契约侧 `/v1` | 管理端 `/api/v1/kb` |
| --- | --- | --- |
| 挂载点 | `app/modules_api/router.py`（`API_PREFIX="/v1"`） | `app/api/v1/routers.py`（`DOMAIN_CONTROLLERS`：`/kb` 7 个 Router、`/gsi` 11 个只读 Router） |
| 鉴权 | HMAC-SHA256 五头 + nonce 防重放 | 管理台 JWT |
| 响应体 | **裸 JSON**，不套 `code/msg/data` | `{code, msg, data}`（`ResponseSchema`） |
| 错误体 | `{"error": {"code", "message", "retryable"}}` | 同一 `ResponseSchema`，`code` 非 200 |
| 路由类 | `ContractApiRoute`（继承 `ApiLogRoute`） | `ApiLogRoute` |
| 写操作幂等 | `request_id` / `job_id` 幂等台账 | 无幂等（重复点击即重复执行） |
| 分页 | 不透明游标 `cursor` / `next_cursor` | 页码 `page_no/page_size` + `PageResultSchema` |

### 1.2 契约五头（每个 `/v1` 请求必带）

| 头 | 说明 |
| --- | --- |
| `X-AI-Signature-Version` | 固定 `v1` |
| `X-AI-Client-Id` | 调用方标识，本期 `gsi-service` |
| `X-AI-Timestamp` | 13 位 Unix 毫秒；与服务端偏差 ≤ ±5 分钟（`CONTRACT_CLOCK_SKEW_MS=300000`） |
| `X-AI-Nonce` | 16–128 位 `[A-Za-z0-9_-]`，600 秒窗口内不可重复 |
| `X-AI-Signature` | HMAC-SHA256 十六进制小写 |

签名原文（七行，`\n` 连接，最后一行是**原始请求体字节**的 SHA-256，任何重排/加空格都会变摘要）：

```
POST
/v1/knowledge/entries
<query 原文，无则空行>
<X-AI-Client-Id>
<X-AI-Timestamp>
<X-AI-Nonce>
<sha256(原始body)>
```

失败一律 401 `UNAUTHORIZED`（缺头、时钟越窗、签名不符、nonce 重放同一个出口）；服务端未配共享密钥时 503 `AUTHORIZATION_UNAVAILABLE`（绝不放行）。

### 1.3 幂等三域

| 域 | 业务键 | 用于 | 重放行为 |
| --- | --- | --- | --- |
| `job` | `job_id` | #01 | 回放首次 202，响应头 `X-Idempotent-Replay: true` |
| `request` | `request_id` | 03.1/03.3/03.4/#20/#07/#08/#11/#14 | 同上，状态码随结果一起存 |
| `event` | `request_id` | #12/#13 | 同上 |

同 ID 不同正文 → 409 `IDEMPOTENCY_CONFLICT`。删除类（03.4/#20/#12）留**墓碑**（`expires_at=NULL`），同 ID 永不回放。

### 1.4 时间与时区

契约响应里的 `created_at` / `updated_at` / `expires_at` 均为 **ISO 8601 带时区**字符串（UTC，如 `2026-11-03T08:12:33.412Z`）；`authorization.issued_at` / `expires_at` 是 **Unix 毫秒整数**（不是字符串，也不是秒）。

### 1.5 错误码总表（`ERROR_CODE_STATUS`）

| 码 | HTTP | retryable | 含义 |
| --- | --- | --- | --- |
| `INVALID_REQUEST` | 400 | 否 | 参数缺失/格式错/游标非法/路径与正文不一致 |
| `SCOPE_REQUIRED` | 400 | 否 | 缺少权限范围块 |
| `UNSUPPORTED_STREAM` | 400 | 否 | `stream=true`（本期只支持非流式） |
| `UNAUTHORIZED` | 401 | 否 | 验签失败/缺头/时钟越窗/nonce 重放 |
| `CONTEXT_OUT_OF_SCOPE` | 403 | 否 | 当前身份无权访问请求范围内的资源 |
| `GOVERNANCE_SCOPE_DENIED` | 403 | 否 | 治理范围失效或越权 |
| `NOT_FOUND` | 404 | 否 | 资源不存在或不可访问（含他人会话） |
| `IDEMPOTENCY_CONFLICT` | 409 | 否 | 同 ID 不同正文 |
| `STALE_REVISION` | 409 | 否 | 基线已变（`content_hash` 不符 / `base_record_id` 过期 / `revision` 不够大） |
| `SOURCE_CHANGED` | 409 | 否 | 治理对象内容已变化，需重新检测 |
| `RESULT_EXPIRED` | 409 | 否 | 治理快照超过 30 分钟 |
| `PAYLOAD_TOO_LARGE` | 413 | 否 | 文件 >10MB 或治理范围 >1000 项 |
| `RATE_LIMITED` | 429 | 是 | 限流 |
| `INTERNAL_ERROR` | 500 | 是 | 内部错误（含向量化/生成依赖故障） |
| `AUTHORIZATION_UNAVAILABLE` | 503 | 是 | 授权数据或 HMAC 密钥不可用 |
| `PARSE_FAILED` | 200 | — | **任务态**失败码，出现在 #02 的 `error_code`，不是错误体 |

### 1.7 管理端错误约定（§3.7–3.9 的 37 个端点共用）

管理端走基座全局异常处理，**不使用**契约错误体。响应形状 `{code, msg, data, status_code, success}`，`success=false`：

| 场景 | HTTP | `code` | `msg` / `data` |
| --- | --- | --- | --- |
| 参数校验失败（含路径参数类型不符） | 422 | `1`（`RET.ERROR`） | `msg` 为首条错误摘要；`data` 是 pydantic `errors()` 全量列表 |
| 业务拒绝（`CustomException` 默认） | 400 | `-1`（`RET.EXCEPTION`） | 服务层传入的中文说明，如「cursor 无效：请原样回传上一页的 next_cursor」 |
| 目标不存在（`get_or_404` 或显式 404） | 404 | `-1` | 「发布单元不存在」/「会话不存在」 |
| 状态冲突 | 409 | `-1` | 「分组已处于 X 状态，不能重复处理」 |
| 未登录 / 无权限 | 401 / 403 | `-1` | 中间件话术 |
| 未捕获异常 | 500 | `-1` | 生产环境固定「服务器内部错误」，`data` 不外泄 |

**`code` 不承载业务语义**（只有 `-1` / `1` 两种），前端一律用 `status_code` 或 `success` 判断，不要匹配 `msg` 文本，也不要套用 §1.5 的契约错误码表——那是两套体系。

### 3.1 解析（#01 / #02）

#### #01 `POST /v1/parse/jobs`（202）

| 字段 | 类型 | 必填 | 约束 | 说明 |

| `version_id` | string | 是 | 非空白 | 业务版本（字符串，不按数字比较） |
| `file_url` | string | 是 | `http/https` | 本侧同步拉取 |

| `options.language` | string | 是 | 非空白 | 解析语言 |

| `resource_type` | string | 是 | `document` / `faq` | FAQ 需额外字段 |

```json
{"job_id": "J-20261103-001", "status": "queued", "message": "任务已受理，请查询结果。"}
```

错误：`UNAUTHORIZED`(401)、`INVALID_REQUEST`(400，含 FAQ 缺 `prompt_text`/`model_key`)、`PAYLOAD_TOO_LARGE`(413，文件 >10MB 或后缀不在白名单)、`IDEMPOTENCY_CONFLICT`(409)。

#### #02 `GET /v1/parse/jobs/{job_id}`（200）

响应：`{job_id, status, progress, result?, error_code?, error_message?}`

| `result` 字段 | 说明 |
| --- | --- |
| `pages[]` | `{page_no, width, height, image_url}`，非 PDF 或未接入对象存储为 `[]`；`image_url` 是对象存储预签名 GET URL（每次查询重签，直连桶，不需契约签名头） |

| `suggested_doc_type` / `suggested` | 建议分类与建议元数据（`title`/`summary`/`tags`） |

```json
{
  "job_id": "J-20261103-001", "status": "succeeded", "progress": 100,
  "result": {"file_name": "报销制度.pdf", "pages": [], "warnings": [],
```

### 3.2 知识写入与读取（03.1–03.4、#20）

#### 03.1 `POST /v1/knowledge/entries`（201）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `request_id` | string | 是 | 幂等键 |
| `tenant_id` / `user_id` | string | 是 | 身份与归属 |
| `resource_type` / `resource_id` | string | 是 | `document` / `faq`；GSI 原始资源 |
| `publication_id` / `record_id` / `version_id` | string | 是 | 发布单元 / 快照 / 版本 |
| `revision` | int | 是 | `≥ 1` |
| `knowledge_no` | string | 是 | 对外知识编号 |
| `metadata` | object | 是 | 原样保存 |
| `content_hash` | string | 是 | 对 `chunks` 重算的摘要，必须一致 |
| `chunks[]` | array | 是 | 见下 |
| `chunks[].chunk_id` | string | **否** | v3：新增切片省略，由本侧分配 `record_id:seq` |
| `chunks[].seq` | int | 是 | 从 1 起连续 |

### 3.6 重复治理（#16–#19；D06 走管理端 `check`）

**正文写入三条端点与契约同引擎**（`KbEntryService`）：`POST /entry` = 03.1、`PUT /entry/{id}` = 03.3、`POST /deactivate/{id}` = #20。管理端只负责「整篇正文按 `PARSE_CHUNK_SIZE`/`PARSE_CHUNK_OVERLAP` 切片 + 摘要 + 展示字段同步 + 异常映射」，切片、向量、版本表由同一份领域服务落库，因此管理端写入的内容与 GSI 契约写入在库内不可区分（`record_id` 前缀 `admin-`、`user_id=admin` 是唯一区别）。

写入口径：

- `POST /entry`：`publication_id` 留空则生成 `kb-{12}`；已存在且已有生效快照时 **409**（提示改用 `PUT /entry`）；已存在但仍是空壳（`current_record_id` 为空）时补录首版（`revision=1`）；`title`/`resource_type` 等归属字段对空壳会一并回写，否则会因归属不一致被判 403。`tenant_id` 随 03.1 落库，检索候选在 SQL 侧按 `publication.tenant_id == 请求租户` 硬过滤，留空等于这份知识对任何租户都不可召回。
- `PUT /entry/{id}`：必须已有生效快照（否则 409「请先写入正文」）、发布单元未停用/删除（否则 409）；`base_record_id` 给了就必须等于当前 `current_record_id`，不等回 409「基线已变化」。旧快照与旧切片保留，不做覆盖。
- `POST /deactivate/{id}`：切片 `status=archived`、版本 `searchable=false`、发布单元转 `inactive`；`reason` 必填。与 `PATCH /status` 的 `inactive` 不同，停用**不可靠「上线」恢复**（切片已归档），要恢复需重新 `POST /entry`。

**删除是逻辑删**（与契约 03.4 同口径）：`DELETE /delete/{publication_id}` 只把 `status` 置 `deleted`，行、版本、切片全部保留；检索、治理范围生成、`effective_pointers` 都硬过滤 `status=active`，所以即不可召回。重复调用幂等；`GET /detail` 仍能读到该行（`status=deleted`），便于追溯。物理级联删（`KbPublicationCRUD.delete_cascade`）只留给内部脚本，页面不提供不可恢复操作。

**坑位**：`/chunks/detail/{chunk_id}` 的路径参数在主键 `id` 上（`ge=1` 整数），传契约 `chunk_id`（形如 `REC-3:2`）会 422。管理端切片**列表**返回的 `id` 才是这个路径参数。

**来源与关联（只读溯源）**：`GET /source/{id}` 回答「这个发布单元是谁写进来的、能不能找到对应的解析任务」，但它**不是关联表查询**——`publication` 与 `parse_job` 之间没有列级外键（见 [`02-数据模型与表关系.md`](02-数据模型与表关系.md) §1.2「内容与作业分离」）。两句口径：

- `write_channel`：按 `current_record_id` 前缀判定。`admin-*` = 管理台写入（`POST/PUT /entry`、管理台删快照）；其余 = GSI 契约写入；无快照 = `pending`（空壳）。
- `parse_jobs`：用 `publication.resource_id` 比对 `parse_job.file_meta->>'doc_id'`（契约 #01 把 `doc_id` 存在 JSONB 里，没有独立列），最多 20 条、按创建时间倒序，`matched_by` 固定回 `file_meta.doc_id`。管理台上传的任务没有 `doc_id`，**永远匹配不到**；匹配是在查询层做的推测，入库内容经过人工编辑，不保证与解析产物一致。
- 反向入口：解析任务详情页用 `GET /list?resource_id=<doc_id>` 反查发布单元，这是 `resource_id` 过滤参数的用途。

**主动治理三端点的范围来源**：管理端不签 GSI 的 `scope`，`publication_ids` 留空表示「全部生效发布单元」，后端按当前生效快照反查 `record_id` / `content_hash` 生成正式 `scope`（`dup_result.scope.build_scope_from_store`）。异常口径：范围为空 400「没有生效内容」、`publication_id` 不存在 400、混合租户 400、超过 `DUP_MAX_SCOPE_ITEMS`（1000）413。

**快照绑定**：`detect` 落的 `dup_result` 快照绑定 `tenant_id + user_id + scope_digest`，管理端固定操作者 `ADMIN_USER_ID="admin"`，所以「检测 → 详情 → 预览」能读到同一份快照；超过 30 分钟或服务重启后快照失效，`preview` 回 409「请重新发起检测」。`preview` 是草稿态，结果同时写回 `dup_group.merged_preview`，不进入正式知识库。

**动作约束（与 #19 同口径）**：每个成员恰好一条 `actions`，`keep` 只能给 `keep_hit_id` 那一条，`merge_answer` 仅可用于 `faq_ai` / `faq_manual` 分组，否则 400。

检索示例（`POST /api/v1/kb/retrieval/search`）：

```json
{"code":0,"msg":"成功","success":true,"status_code":200,"data":{"request_id":"debug-1","no_evidence":false,"elapsed_ms":120.4,"authorized_publication_count":37,"hits":[{"publication_id":"P-9","chunk_id":"REC-3:2","title":"报销制度","snippet":"……差旅费报销标准……","score":0.83}]}}
```

错误（其余见 §1.7）：`503` 授权数据或向量化不可用（与 #07 同口径，不降级为空结果）、`400` `user_id` 非数字、`422` `query` 超 500 字或 `limit` 越界。

管理端检索**必须显式传 `user_id`**：没有登录上下文，只能「以谁的身份查」；非数字 `user_id` 会算出空授权集，返回 `no_evidence=true` 而不是报错。

## 五、调用顺序建议

**解析 → 写入（GSI 正常链路）**

1. `POST /v1/parse/jobs` → 拿 `job_id`
2. 轮询 `GET /v1/parse/jobs/{job_id}` 直到 `succeeded`（失败看 `error_code`）
3. 编辑人员确认后：`POST /v1/knowledge/entries`（首发）或 `PUT /v1/knowledge/entries/{id}`（修订，先 `POST .../query` 读基线拿 `record_id`）
4. 校验写入结果：`POST /v1/knowledge/entries/{id}/query` 回读，确认 `searchable=true`

**查重链路**

1. `POST /v1/knowledge/duplicates/check`（保存前快速判断）→ 若 `is_duplicate=true` 转治理
2. `POST /v1/knowledge/duplicates/groups/query`（首查，拿 `result_id` + `expires_at`）
3. 逐组 `POST /v1/knowledge/duplicates/groups/{group_id}/query`（带 `result_id`）
4. `POST /v1/knowledge/duplicates/merge-preview` → 人工确认后回 GSI 走 03.3

**问答链路**

1. `POST /v1/chat/sessions`（或复用已有 `session_id`）
2. `POST /v1/chat/completions`
3. 超时未返回 → 用**新的** `request_id` 调 `POST /v1/chat/requests/{原 request_id}/query`
4. 需要清理：`DELETE /v1/chat/sessions/{id}/messages`（保留会话）或 `DELETE /v1/chat/sessions/{id}`

**排障优先顺序**：先 `GET /api/v1/kb/parse-jobs/detail/{job_id}`（解析）→ 再看 `GET /api/v1/kb/publication/baseline/{id}`（写入是否可读）→ 再看 `POST /api/v1/kb/retrieval/search`（能否召回）→ 最后 `GET /api/v1/kb/chat-message/list?session_id=...`（回答与引用）。

**管理端主动治理链路（无 GSI 参与）**

1. `POST /api/v1/kb/parse-jobs/upload`（自备文件）或 `GET /parse-jobs/list` 找已有任务
2. `POST /api/v1/kb/dup-groups/detect`（选定 `publication_ids` 或留空=全量）→ 拿 `result_id` 与 `items`
3. `GET /api/v1/kb/dup-groups/list` 看物化后的治理行；`GET /detail/{group_id}` 看成员与当前 `merged_preview`
4. 需要判断「这份新内容能不能存」→ `POST /api/v1/kb/dup-groups/check`（只报不拦）
5. 人工决策后 `POST /api/v1/kb/dup-groups/preview/{group_id}`（30 分钟内）→ 预览写回 `merged_preview`
6. 结论落定后 `PATCH /api/v1/kb/dup-groups/status/{group_id}`（`merged` / `dismissed`）

> 管理端**没有**「执行合并」的端点：合并后的知识必须回到 GSI 走 03.3 修订，或在管理台手工维护。预览只是草稿，不落正式表。

### 6.3 三个必用的核对动作

1. **授权为空** → `GET /api/v1/gsi/sys/audience-team-member/user-teams?user_id=…`：`team_count=0` 说明人没进任何团队（授权必然为空）；有团队但 `valid_team_count=0` 说明团队被停用/删除。再到 `GET /api/v1/gsi/sys/audience-team/list?group_code=…` 确认编码。
2. **有团队但检索不到** → `GET /api/v1/gsi/km/doc-publication/page-with-team?team=<group_code>&doc_id=…`：`team_matched=false` 表示该行 `team` 存的不是现行 `group_code`（历史名称/兼容标识），本侧授权直接落空。
3. **FAQ 生效规则可疑** → `GET /api/v1/gsi/faq/publication/list?faq_id=…`：`rules_valid=false` + `rules_error` 给出原因（缺 `invisibleTeams`、JSON 非法、来源为空）；`rules_source=record` 表示 publication 上的规则为空、用的是快照。

### 6.4 三处口径提醒

- **时间不是 UTC**：本组返回的是 GSI 库里的墙上时间（`timestamp(6)`），不要按 `/v1` 的 ISO 8601 UTC 解读。
- **`/gsi` 只读，不修数据**：看到 `team_matched=false`、`rules_valid=false` 都要回 GSI 侧修，本侧没有任何写入口。
- **不计入「56 个」**：§二 的 56 个不含这 23 个，也不含 `/api/v1/system` 的日志/存储接口。
