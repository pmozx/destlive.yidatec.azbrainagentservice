# 05 · 服务大脑AI项目功能模块说明文档

> **本目录回答一句话**：这个已经做完的模块，**具体实现了什么、数据长什么样、怎么调、坏了怎么查**。
> 面向接手开发、联调对接、验收与运维；写的是**代码里真实跑的东西**，不是设计蓝图。
> 当前版本 v1.0（2026-11-02 建目录）· 维护人 孟星旭

---

## 一、这个目录和别的目录有什么不同

同一件事在四个目录里都有描述，但视角不同。写作前先确认自己该写哪一层，避免重复：

| 目录 | 视角 | 时态 | 典型问题 | 本目录不重复写 |
| --- | --- | --- | --- | --- |
| `01-…需求与架构文档` | 设计蓝图 | 将来/应该 | 为什么这样设计？整体分几层？表结构规划是什么？ | 架构分层原理、ADR 决策理由（只引用） |
| `03-…开发规范文档` | 编码约定 | 一直 | 代码该怎么写？错误怎么处理？表怎么命名？ | 通用规范条文（只引用条目号） |
| `04-…开发过程文档` | 过程证据 | 过去 | 哪次验收过了？评审发现了什么？ | 缺陷清单与整改批次（只引用编号） |
| **`05-…功能模块说明文档`** | **实现说明（as-built）** | **现在** | 这个模块现在能干什么？四张表怎么关联？11 个接口怎么调？收到 409 先查哪张表？ | — |

三条硬规矩：

1. **以代码为准**：文档与代码不一致时，改文档；代码已改而文档没改，视为文档缺陷。
2. **不写"计划做什么"**：未实现的能力放 `04-实现与运维说明.md` 的「已知限制」，不混进功能清单，避免把空表当成已上线能力。
3. **每个结论可核对**：涉及实现的地方给 `路径:行号`，涉及数据的地方给表名+列名，涉及接口的地方给方法与完整路径。

## 二、目录结构

```
05-服务大脑AI项目功能模块说明文档/
├── README.md                          ← 本文件：目录地图、模块清单、新增模块流程
├── 01-模块说明编写规范.md              ← 五份文档各写什么、模板、命名、评审清单（新增模块先读它）
├── 02-日志审计与接入追踪/              ← 示例模块（system 域）★ 已完成
│   ├── README.md                      ← 模块总览：定位、边界、能力地图、表/接口速查、术语
│   ├── 01-业务功能说明.md              ← 谁在什么场景用它、功能点清单、流程、状态判定、保留策略
│   ├── 02-数据模型与表关系.md          ← 逐表字段字典、主键/唯一键/索引、表间引用与依赖、写入读取矩阵
│   ├── 03-接口清单.md                  ← 端点台账、入参出参、错误码、调用示例、前端映射
│   └── 04-实现与运维说明.md            ← 代码地图、关键决策、配置项、排障手册、测试覆盖、已知限制
└── 03-知识平台/                        ← 知识平台（kb 域）★ 已完成
    ├── README.md
    ├── 01-业务功能说明.md
    ├── 02-数据模型与表关系.md
    ├── 03-接口清单.md
    └── 04-实现与运维说明.md
```

编号规则：`01` 固定留给编写规范；**模块目录从 `02` 起连续编号**，与规范共用同一序列（沿用 `00-document/README.md` §2.1「子目录与同级文档共用序号」）。模块内部的四份正文编号**含义固定**，任何模块都不许调换顺序或改名（见 `01-模块说明编写规范.md` §三）。

## 四、五份文档的职责边界（摘要）

细节与模板见 [`01-模块说明编写规范.md`](01-模块说明编写规范.md)，这里只给"一句话职责"，用来判断某段内容该放哪份文件：

| 文档 | 只回答 | 判断口诀 |
| --- | --- | --- |
| `README.md` | 这个模块是干什么的、由哪几块组成、从哪读起 | **导航**，不展开细节 |
| `01-业务功能说明.md` | 谁为了什么用它、点了什么发生了什么、什么算成功/失败 | 写**行为**，不写字段类型 |
| `02-数据模型与表关系.md` | 有哪些表、每个字段什么意思、表和表怎么对上、谁写谁读 | 写**数据**，不写页面交互 |
| `03-接口清单.md` | 怎么调：路径、参数、返回、错误、示例 | 写**契约**，不写内部实现 |
| `04-实现与运维说明.md` | 代码在哪、为什么这么写、配置怎么调、出问题怎么查 | 写**实现与运维**，不写业务规则 |

同一事实只在一处定义，其余位置引用。例如"`status=1` 表示失败"定义在 `01` §状态判定，`02` 的字段字典写"取值见 `01` §5.1"，`03` 的出参说明写"同 `01` §5.1"，`04` 不再重复。

## 五、命名规范（本目录增量部分）

完整规范见 `00-document/README.md` §二与 [`01-模块说明编写规范.md`](01-模块说明编写规范.md) §二，此处只列本目录特有的三条：

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 模块目录 | `NN-<业务模块名>`；`NN` 从 `02` 起；用**业务名**而非代码包名，多子模块用 `-` 连接 | `02-日志审计与接入追踪`（不是 `02-system-api_log`） |
| 模块内正文 | 固定四份、固定名：`01-业务功能说明` / `02-数据模型与表关系` / `03-接口清单` / `04-实现与运维说明` | 所有模块完全一致，便于横向对照 |
| 模块内索引 | 固定 `README.md` | 不参与编号 |

跨目录引用沿用 `目录号-文档号`；**模块内引用**写 `模块号/文档号`，如 `05-02/02` 表示本模块的数据模型文档；同模块内直接写 `02-数据模型与表关系.md`。

禁止：文件名带空格/下划线/括号、双段编号、`v2`/`final`/`新版` 等版本词（版本写文首变更记录）、把代码包名当模块名（`integration_*` 这类已废弃域名更不允许出现）。

## 六、新增一个模块的流程

1. **盘代码**：按 `01-模块说明编写规范.md` §六 的「盘点清单」把路由、模型、写入方、读取方、配置项、测试列全（用 grep，不靠记忆）。
2. **建目录**：`NN-<模块名>/`，从本 README §三 取下一个编号。
3. **按序写四份**：先 `02-数据模型与表关系`（数据是地基，写完功能与接口才有依据）→ 再 `01-业务功能说明` → `03-接口清单` → 最后 `04-实现与运维说明` 与 `README`。
4. **自检**：走一遍 `01-模块说明编写规范.md` §七 的评审清单（12 条），重点核对"每条字段都有含义、每个端点都有错误码、每个写入方都有事务边界"。
5. **登记**：更新本 README §三 清单行与状态；若模块间有表引用，在双方 `02-数据模型与表关系.md` 的「跨模块引用」小节互指。
