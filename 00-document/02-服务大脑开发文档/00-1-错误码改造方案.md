# 00-1 · 错误码改造方案（含 13 个接口的对应关系）

> 版本 v1.0 · 2026-10-28
> **前提**：`业务系统对接接口文档/gsi-ai-openapi.json` 是由 `知识平台与AI接口参数手册.html` 页面上的「下载 OpenAPI JSON」导出的，两者同源。因此本文以 **HTML 手册为唯一源头**，JSON 视为导出产物（导出质量单独列在 §5.5）。
> 配套：`00-接口评审报告.md`（整体评审：业务流程与业务字段）、`02-1-知识平台开发计划与说明.md`（一期任务）。
> 更正说明：早期判断"手册没有错误码章节"有误——用命令行工具检索超长单行 HTML 时被跳过，实际手册有 `错误码与处理方式`（19 行）与 `当前实现与交付边界` 两节，且 JSON 里 403/413 分支也存在。

---

## 一、先看三句结论

1. **错误码本身写得不错，问题不在码，在"码和接口对不上"**：总表列了 20 个码，但 13 个接口的错误面板里只写了 6 个 HTTP 状态码 + 一个通用示例 `INVALID_REQUEST`，没有说"这个接口会返回哪些码"。更硬的证据：总表定义了 `RESULT_UNAVAILABLE → 409`，但**13 个接口里没有任何一个声明了 409 能承载它**（13 号查询接口恰好没有 409 分支）。
2. **不建议改成"统一 200"**：现在 `401 管签名、403 管业务授权、429 管限流` 的划分是对的，是这套接口里最有价值的部分。统一 200 会让限流退避、监控告警、网关熔断全部失效。
3. **需要改 8 处**：补"码 × 接口"矩阵、统一 413 的含义、取消 `RESULT_UNAVAILABLE`、错误体加 4 个字段、码做枚举、三套码分开命名、补 4 个缺失码、修导出产物。

## 三、问题分析

### 3.1 错误码体系（10 个问题）

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| E1 | **码与接口没有对应关系** | 总表 20 个码；13 个接口的错误面板只列 6 个状态码，示例统一是 `INVALID_REQUEST` | 业务系统看到 400 不知道该按"改字段"还是"换模型"处理；联调用例无法按码覆盖 |
| E2 | **`RESULT_UNAVAILABLE` 无处落地** | 13 号接口（唯一涉及"旧结果"的接口）没有 409 分支 | 码定义了却永远不会出现；或实现时只能塞进 200 结果里，与 `result_visible=false` 重复 |
| E3 | **413 一个状态码两种含义** | 表中 `SCOPE_TOO_LARGE` 是"白名单太大"，`PAYLOAD_TOO_LARGE` 是"请求体超 10 MB"；而 03/04/06/07/10/12/13 的 413 示例统一是 `PAYLOAD_TOO_LARGE` | 调用方无法判断该"缩批次"还是该"改权限方案" |
| E4 | **同一件事两个状态码** | `SCOPE_REQUIRED/SCOPE_TOO_LARGE` 写 `400 / 413`，并注明"search 返 400、Chat 返 413" | 同一类错误在知识接口和会话接口表现不同，无法写统一处理 |
| E5 | **`CONTEXT_OUT_OF_SCOPE` 被复制到 5 个接口** | 06/07/10/12/13 的 403 示例都是它 | 06 列表、07 详情不消费证据，不可能"证据越权"；这三个接口真正该报的是租户/授权类错误 |
| E6 | **01、05 的 404 语义不明** | 提交任务、创建会话这两个"新建"接口声明了 404 | 新建操作没有"找不到"的对象；实际想表达的应是"租户/用户不存在"（403） |
| E7 | **三套码共用 error 命名** | 接口体 `error.code`、任务结果 `error_code`/`error_message`、操作结果 `result.error.code` | 手册最后一段自己也提醒"不要混淆"——说明命名本身就容易混，应改字段名而不是加提醒 |
| E8 | **`LEGACY_CONFIG_ID` 描述的是不存在的字段** | 当前 01/12 请求体里没有"GSI 配置 ID"字段 | 属于旧版本调用方的兼容残留，新接入方看不懂，应删除或标注为历史 |
| E9 | **码没有枚举，导出后示例是错的** | JSON 里 6 个状态码的 `code` 示例**全部**是 `INVALID_REQUEST`（401 的 schema 写 INVALID_REQUEST，examples 却是 UNAUTHORIZED）；`enum` 数量为 0 | 用工具生成的客户端里 `code` 是无约束字符串、描述错误，拿不到可枚举的码表 |
| E10 | **缺 4 个码** | 见 §5.4 | 这些错误现在只能落到 `INVALID_REQUEST`，无法区分 |

### 3.2 业务流程（7 处不顺）

| # | 问题 | 说明 |
| --- | --- | --- |
| F1 | 一轮问答要两次跨系统调用、两次授权 | 04 检索 → 12 生成；`authorization` 与 `allowed_snapshots` 传两遍，GSI 要算两次权限，两次之间权限变化还会对不上 |
| F2 | 创建会话就传知识授权，但授权最长 120 秒 | 会话是长期对象，创建时传入的白名单对后续任何一次请求都不生效；每次请求都要重新传 → 授权对"会话"没有实际意义 |
| F3 | 08 改名 / 09 删除 / 11 清空也带 `authorization`（可选） | 这三件事不读知识，字段纯冗余；却可能触发 GSI 计算上万条白名单 |
| F4 | 07 与 06 返回字段完全同构 | 07 无信息增量，前端取摘要只能逐个调 10 |
| F5 | 03 只支持整篇替换，`INVALID_CHUNKS` 无定位信息 | 2000 条切片里错 1 条，只返回一个总码，业务系统无法知道是哪条错 |
| F6 | 解析产物与正式切片结构不一致 | 02 的 chunk 无 `chunk_id`、有 `source_type`；03 的 chunk 有 `chunk_id`、无 `source_type` → 中间靠人工转换，字段必丢 |
| F7 | 三套失败语义并存，且没有补偿接口 | 接口失败 4xx / 任务失败 200+`error_code` / 操作失败 200+`result.error`；`delivery` 明确没有 cancel、sync-jobs、reconcile → 任务卡住或发布异常时没有补偿路径，码表里也没有对应表达 |

### 3.3 业务字段（5 处不够用）

| # | 问题 | 影响 |
| --- | --- | --- |
| G1 | 错误体只有 `code` / `message` / `retryable` | 没有"哪个字段错了"（`field`）、没有"哪几条切片错了"（`violations[]`）、没有回执号（`request_id`）→ 400 难排查，批量提交几乎不可用 |
| G2 | 429 没写 `Retry-After`，409 `SESSION_BUSY` 没写等多久 | 调用方只能猜一个固定间隔重试，容易把服务打得更满 |
| G3 | 任务失败只有 `error_code` + `error_message` | 没有失败阶段（下载 / 解析 / 落库）、没有"是否可重试"、没有"是否已计费"，业务侧没法自动决策 |
| G4 | `content_hash` 是整包一个 | 切片级变更时无法判断"哪几条变了"，只能全量重算；也没有"摘要不匹配"这个错误码 |
| G5 | 会话/任务/操作三类结果里都叫 `error` | 见 E7 |

## 五、改造建议

### 5.1 三套码分开，不要都叫 error

| 场景 | 现在 | 建议 | HTTP |
| --- | --- | --- | --- |
| 请求被拒绝 | `error.code` | 保留 `error.code` | 4xx/5xx |
| 解析任务跑完但失败 | `error_code` / `error_message` | 改为 `failure: { code, message, stage, retryable }` | 200（任务结果） |
| 超时操作的结果失败 | `result.error.code` | 改为 `result.failure`（同上结构） | 200（操作结果） |

理由：现在三种都叫 error / error_code，手册末尾不得不写一段"不要混淆"的提醒。**改字段名比写提醒可靠**。`stage` 取值建议：`download` / `parse` / `chunk` / `index` / `generate`。

### 5.2 错误体加 4 个字段（都可选，向后兼容）

| 新增字段 | 用在哪 | 解决什么 |
| --- | --- | --- |
| `request_id` | 全部错误 | 回执号，排障和对账时业务系统能直接引用 |
| `field` | 400 类 | 指出是哪个字段错（如 `options.language`） |
| `violations[]` | 03 的 `INVALID_CHUNKS` | 每条给 `{ index, chunk_id, field, code, message }`，2000 条里错哪条一眼看到 |
| `retry_after_ms` | 429 / 409 `SESSION_BUSY` | 告诉调用方等多久再重试，替代"猜一个固定间隔" |

### 5.3 状态码归位规则（避免同类错误两套码）

| 情况 | 用哪个状态码 | 备注 |
| --- | --- | --- |
| 字段/枚举/条数/切片结构错 | **400** | 带 `field` / `violations` |
| 签名、时间戳、nonce 失败 | **401** | 只用于签名鉴权，不用于业务授权 |
| 租户不允许、知识授权过期、证据越权 | **403** | 三者的 `retryable` 不同：租户→否，授权过期→是，证据越权→否且要告警 |
| 对象不存在（含"不属于你"的掩蔽） | **404** | 新建类接口不要用 404（见 E6） |
| 幂等冲突/修订号过期/版本竞争/会话忙 | **409** | 带 `retry_after_ms`（会话忙） |
| 请求体或白名单超过容量 | **413** | **`SCOPE_TOO_LARGE` 一律 413**，不再"search 400 / chat 413" |
| 限流 | **429** | 带 `Retry-After` |
| 内部错误 / 依赖不可用 | **500 / 503** | 503 用于模型或数据库暂时不可用 |
| 任务或操作本身失败 | **200** + 结果里的状态字段 | 不是 HTTP 失败 |

### 5.4 补 4 个码、删 2 个码

| 动作 | 码 | 用在哪 | 理由 |
| --- | --- | --- | --- |
| 新增 | `CONTENT_HASH_MISMATCH` | 03 | `content_hash` 校验失败现在只能报 `INVALID_REQUEST`，业务侧分不清是"内容变了"还是"字段写错了" |
| 新增 | `CONTEXT_TOO_MANY` | 12 | `contexts` 上限 20 条，超了现在是 `INVALID_REQUEST`，与"字段格式错"混在一起 |
| 新增 | `SERVICE_UNAVAILABLE`（503） | 全部 | 模型/库暂时不可用，与"代码 bug 导致的 500"区分，前者可重试后者要报警 |
| 新增 | 任务失败码入表 | 02 / 13 | `PARSE_FAILED`、`GENERATION_FAILED` 现在只活在示例里，没有清单也没有 `stage` |
| 删除 | `RESULT_UNAVAILABLE` | — | 与 13 的 `result_visible=false` 重复，且无 409 分支承载 |
| 删除 | `LEGACY_CONFIG_ID` | 01 / 12 | 请求体里没有"配置 ID"字段，是旧版本兼容残留 |

### 5.5 导出产物与文档结构（同源导出带来的问题）

| 问题 | 现状 | 修法 |
| --- | --- | --- |
| 示例码错位 | 每个状态的 schema `code` 示例都写 `INVALID_REQUEST`，与 examples 里的真实码（如 `UNAUTHORIZED`）不一致 | 导出时按状态填对应示例码 |
| 没有枚举 | `enum` 数量为 0 | 每个接口的 `code` 用 `enum` 列出 §4.1 的码清单 |
| 结构重复 | 13 份错误体、13 份 `allowed_snapshots` 全部内联（JSON 37 万字符 / 1 万行） | 导出时抽成 `components.schemas.Error` / `AllowedSnapshot`，13 处 `$ref` |
| 码表位置 | 只有一张按 HTTP 分组的总表 | ① 总表保留作索引；② 每个接口的错误页签加"本接口会返回的码"；③ 总表加"适用接口"列 |

## 六、改造优先级

| 优先级 | 改什么 | 不改会怎样 |
| --- | --- | --- |
| **P0** | 码 × 接口矩阵（§4）+ 逐接口清单（§4.1） | 业务系统没法写异常分支，联调用例只能覆盖 6 个状态码 |
| **P0** | 统一 413 语义；`SCOPE_TOO_LARGE` 一律 413 | 同一错误两种表现，调用方处理逻辑分裂 |
| **P0** | 错误体加 `request_id` / `field` / `violations[]` | 03 提交 2000 条切片出错时无法定位，实际不可用 |
| **P0** | `code` 做枚举 | 生成的客户端里是自由字符串，拼错也不报错 |
| **P1** | 取消 `RESULT_UNAVAILABLE`，统一用 `result_visible` | 两套机制表达同一件事，实现方会各写一套 |
| **P1** | 三套码分开命名（`failure` / `result.failure`） | 业务系统长期混淆任务失败与接口失败 |
| **P1** | 403 码归位（06/07/10 换掉 `CONTEXT_OUT_OF_SCOPE`）+ 01/05 的 404 改 403 | 列表页收到"证据越权"这种看不懂的错 |
| **P1** | 补 `CONTENT_HASH_MISMATCH` / `CONTEXT_TOO_MANY` / `SERVICE_UNAVAILABLE` | 这些错误全落到 `INVALID_REQUEST`，无法区分 |
| **P2** | `400 / 404` 的细节约束（02 补 400、01 补 413） | 边界输入行为靠猜 |
| **P2** | 导出修复（枚举、示例、`$ref`、逐接口码页签） | 改一处描述要改 13 处，早晚不一致 |

> 关于"要不要统一 200"：**不建议**。现结构里 `401`（签名）与 `429`（限流）必须靠状态码触发"重新签名"和"退避重试"，`5xx` 是监控告警的唯一抓手。若公司规范强制统一 200，最低限度保留 `401/429/5xx` 的 HTTP 语义，其余业务错误走 200 + `code`，并在响应头保留 `Retry-After`。
