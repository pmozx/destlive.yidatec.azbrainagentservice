## 二、交付范围

### 2.1 接口清单（13 个，与 OpenAPI 逐一对应）

| # | 方法 | 路径 | 说明 | 关键契约约束 |
| --- | --- | --- | --- | --- |
| 1 | POST | `/v1/parse/jobs` | 提交文档 / FAQ 解析任务 | 202 受理；`job_id` 幂等；10MB 请求体上限 |
| 2 | GET | `/v1/parse/jobs/{job_id}` | 查询进度与完整结果 | 四态；`failed` 走 HTTP 200 + `error_code`；`chunks` 不得含向量 |
| 3 | POST | `/v1/knowledge/index` | 提交 / 停用 / 删除正式切片 | `event_id` 幂等 + `revision` 单调 + 原子版本切换；同步返回 200 |
| 4 | POST | `/v1/knowledge/search` | 关键词 / 自然语言检索 | 必须在 `allowed_snapshots` 内检索，禁止先全库后隐藏；空白名单返回空命中 |
| 5 | POST | `/v1/chat/sessions` | 创建新会话 | 会话归属于 `tenant_id + user_id` |
| 6 | POST | `/v1/chat/sessions/query` | 分页查询我的会话 | 游标分页；POST 承载签名身份 |
| 7 | POST | `/v1/chat/sessions/{id}/query` | 查询会话详情与版本 | 写操作前取 `session_version` |
| 8 | PATCH | `/v1/chat/sessions/{id}` | 修改会话标题 | 版本不一致 409 |
| 9 | DELETE | `/v1/chat/sessions/{id}` | 删除会话 | **DELETE 携带 JSON 正文，网关须透传** |
| 10 | POST | `/v1/chat/sessions/{id}/messages/query` | 查询历史消息 | 知识依赖失效则整条回答与引用隐藏 |
| 11 | DELETE | `/v1/chat/sessions/{id}/messages` | 清空会话历史 | 保留会话壳；迟到生成结果不得写回 |
| 12 | POST | `/v1/chat/completions` | 发送问题并生成回答 | **非流式**（`stream=true` 返回 `UNSUPPORTED_STREAM`）；60s 超时 |
| 13 | POST | `/v1/chat/requests/{target_request_id}/query` | 查询超时操作的结果 | 正文 `request_id` 为新 ID，路径为原操作 ID；支持执行中/失败态 |

### 2.2 跨切面能力（不体现为独立接口，但必须自建）

| 编号 | 能力 | 要点 |
| --- | --- | --- |
| C1 | HMAC 签名鉴权 | 7 行原文（v1 / client_id / 时间戳 / nonce / 方法 / 原始路径+查询 / body 的 SHA-256）；±5 分钟；不排序不重序列化 |
| C2 | 防重放 | `client_id + nonce` 原子登记，保留至 timestamp+5 分钟；多实例须共享持久存储 |
| C3 | 幂等台账 | `job_id` / `event_id` / `request_id` 三类；同 ID 不同正文 → 409 |
| C4 | 统一错误体 | `{error:{code,message,retryable}}`，14 类业务码（含 403/409/413/429 分支） |
| C5 | 权限白名单下推 | `allowed_snapshots` 转 SQL 条件或临时表 JOIN，含 `SCOPE_TOO_LARGE` 上限 |
| C6 | 数据隔离 | 共用 `service_brain` 库，AI 独立 schema（建议 `ai_knowledge`）+ 独立账号按 schema 授权；GSI 不查 AI 表 |

### 2.3 明确不在本次范围

- 点赞 / 点踩、答案反馈（GSI 侧实现，AI 只需保持 `session_id`/`message_id` 稳定）；
- 权限计算（visibility / 部门 / 指定人 → 由 GSI 生成白名单）；
- 知识业务状态与审批发布（GSI 维护，AI 只收「正式切片」）；
- 座席前端页面、知识中心管理页面；
- 种子文档收集与入库运营、培训与录屏、UAT 组织（属运营/验收工作，不计入开发工时）。

## 六、单人产能与工期测算

```
容量 = 12 周 × 5 工作日 − 元旦 1 天 = 59 人日
负载 = 52 人日（任务级汇总）
占用 = 88%，缓冲 = 7 人日（另含周会/答疑的日常占用）
```

- 按 4.3 人日/周有效产出（预留约 15% 管理事务）→ 52 / 4.3 ≈ **12 周**，与排期一致；
- 若按 5 人日/周满负荷 → 约 **10.5 周**，但无缓冲，不建议；
- 若必须压缩到 6 周（30 人日）：只能交付 #1/#2/#3/#4 + 签名与错误码，**会话与问答 9 个接口全部后延**，且需放弃示例级契约测试。

## 十二、质检 Agent 扩展（二期增量，不在本文评估内）

本文的 13 个接口交付的是「知识与问答」的地基：解析、索引、检索、会话、生成。**通话录音解析与质检（Agent 编排）**是系统的核心业务线，包含转写解析、四类判定（硬规则 / 语义 / 知识一致性 / 工单一致性）、质检编排图、计分与标签、四层报告与 Findings，原计划未覆盖，工时记 0。

| 项 | 结论 |
| --- | --- |
| 增量范围 | 25 个任务（Q0.1–Q6.3），P8 质检内核 22.0 + P9 编排与计分 8.0 + P10 报告与验收 14.5 |
| 增量人日 | **44.5 人日**（对照 `../01-服务大脑项目文档/系统需求文档.md` 的 26 条质检相关需求，平均 1.7 人日/条） |

| 复用边界 | 检索、生成、幂等台账、编排框架、schema 隔离复用一期，**不重复计工时**（若重建需额外 17.0 人日） |

| 累计口径 | 52 + 44.5 = **96.5 人日**；59 + 50 = **109 个工作日**；单人日历 **22 周（约 5 个月）** |
| 不能并入一期 12 周的原因 | 一期 12 周仅余 7 人日缓冲，质检域需 44.5 人日，缺口 37.5 人日 |
