## 三、使用方式

| 你要做的事 | 怎么用 |
| --- | --- |
| 排整改计划 | 读 §二 的 A / B / C / D 四组：**A 组无依赖可直接开工**，B 组等一句决策，C 组等对应链路立项，D 组已判定不做（不必重提）；§五 给了执行顺序 |
| 提 PR 前自查 | 对照 [`../../03-…/01-团队开发规范.md`](../../03-服务大脑AI项目开发规范文档/01-团队开发规范.md) §5 的提交前自查清单，命中的存量条目在本报告查编号 |
| 确认某条问题是否还存在 | 先看 §三（已失效/作废），再在 §二 找对应编号；标注「已关闭」的条目改代码前先跑对应回归测试 |
| 想复盘历史上怎么修的 | §一 只有一行结论；逐条过程（DDL 清单、失败排查、验证表）在 `git log`（v1.0–v1.7 版本）与代码注释里，`§四 踩坑备忘` 收了有长期价值的 7 条 |
| 复核结论是否可信 | 每条结论都附代码位置或库内实测；复跑方式见报告内各条测试文件路径（如 `tests/core/test_db_getter.py`） |

## 四、维护约定

1. **只追加版本，不重写结论**：新一轮评审在文首加版本行与章节，旧结论保留并用【vX 复核】标注状态，便于追溯「当时为什么这么判断」。
   **例外（v2.0 起）**：**允许"压缩"但不允许"改判"**——把已关闭条目的过程细节（DDL 清单、逐次验证表、失败排查）压成一行结论与版本号，判定结果本身不得改动；被压缩的原文在 `git log` 里可查，有长期价值的教训必须留进 `§四 踩坑备忘`。压缩后必须同步修正跨文档引用（规范文档、本目录 README 中的章节号）。
2. **修复必须附测试**：标记「已修复」的 P0 / P1 条目需给出回归测试文件与用例数；无测试的修复只能标「已改待验」。
3. **问题编号稳定**：`P0-1`、`P1-5` 等编号不复用；新增问题顺延编号，作废标注原因。
4. **与规范双向可查**：规范条目引用本报告编号，本报告的执行批次引用规范条目（R / F / D / L / T）。
