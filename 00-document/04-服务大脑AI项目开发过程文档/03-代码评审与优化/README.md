## 三、使用方式

| 你要做的事 | 怎么用 |
| --- | --- |
| 排整改计划 | 读 §五 建议执行批次（第 0 批已完成 → 第 1 批 P0-3/4/5/6 → 第 2、3 批）；每条问题带文件:行号，可直接建 issue |
| 提 PR 前自查 | 对照 [`../../03-…/01-团队开发规范.md`](../../03-服务大脑AI项目开发规范文档/01-团队开发规范.md) §5 的提交前自查清单，命中的存量条目在本报告查编号 |

| 复核结论是否可信 | 每条结论都附代码位置；复跑方式见报告内各条测试文件路径（如 `tests/test_db_getter_transaction.py`） |

## 四、维护约定

1. **只追加版本，不重写结论**：新一轮评审在文首加版本行与章节，旧结论保留并用【vX 复核】标注状态，便于追溯「当时为什么这么判断」。
2. **修复必须附测试**：标记「已修复」的 P0 / P1 条目需给出回归测试文件与用例数；无测试的修复只能标「已改待验」。
3. **问题编号稳定**：`P0-1`、`P1-5` 等编号不复用；新增问题顺延编号，作废标注原因。
4. **与规范双向可查**：规范条目引用本报告编号，本报告的执行批次引用规范条目（R / F / D / L / T）。
