# 中文质检要求 - 样例 — 详尽说明

> 来源：`04-中文质检要求样例-原件.docx`（原文件名「中文质检要求 - 样例.docx」）
> 内容：完整的质检规则库样例，共 60 条规则，分四大类

---

## 概述

该文件提供了一套完整的、可直接参考的质检规则样例集，是所有质检规则库建设的技术范本。每条规则均采用统一的字段结构：

| 字段 | 说明 |
|------|------|
| 规则编号 | 唯一标识（如 TEL-001） |
| 规则名称 | 规则的简明标题 |
| 适用范围 | 所适用的质检对象类型 |
| 判定条件 | 描述判定该规则时所核查的具体事项 |
| 合格标准 | 明确描述何为合格 |
| 不合格判定 | 明确描述何为不合格 |
| 备注 | 补充说明、判定方式建议、注意事项 |

规则共分为四大类：

| 规则库 | 编号前缀 | 数量 | 适用对象 |
|--------|----------|------|----------|
| 电话质检规则库 | TEL- | 16 条 | 通话录音及转写文本 |
| Interaction 工单质检规则库 | INT- | 11 条 | Interaction 工单 |
| Incident 工单质检规则库 | INC- | 16 条 | Incident 工单 |
| Request 工单质检规则库 | REQ- | 13 条 | Request 工单 |

---

## 一、电话质检规则库（TEL-001 ~ TEL-016）

电话质检规则覆盖了从通话开始到结束的完整服务流程，包括基础规范、身份验证、服务态度、交互技巧和服务闭环五个维度。

---

### TEL-001

**规则名称**：接听前耳机与通话音质要求

**适用范围**：电话质检

**判定条件**：核查工程师接听电话前是否已正确佩戴耳机，通话过程中是否存在明显杂音、回声、电流声或其他影响沟通质量的异常声音。

**合格标准**：工程师接听前已佩戴耳机，且通话过程中无明显杂音或线路异常。

**不合格判定**：未佩戴耳机即接听电话，或通话过程中存在明显杂音、回声、电流声等影响沟通的异常情况。

**备注**：建议结合录音内容进行判定。

---

### TEL-002

**规则名称**：标准开场语使用要求

**适用范围**：电话质检

**判定条件**：核查工程师接听电话时是否使用标准开场语。

**合格标准**：工程师使用标准开场语：
> "欢迎致电阿斯利康IT服务台，我是XXX，请问您K账号多少"

**不合格判定**：未使用标准开场语，或开场语缺少以下任一核心信息：
1. 欢迎致电阿斯利康IT服务台
2. 自我身份说明
3. 索取用户K账号

**备注**：允许姓名部分按实际情况替换。

---

### TEL-003

**规则名称**：身份验证前置要求

**适用范围**：电话质检

**判定条件**：核查工程师是否在提供技术支持前完成身份验证。

**合格标准**：工程师在提供任何技术支持、信息查询、故障处理或账户相关服务前，已完成身份验证。

**不合格判定**：在未完成身份验证前即提供技术支持或处理用户问题。

**备注**：属于强制合规项。

---

### TEL-004

**规则名称**：身份验证方式范围要求

**适用范围**：电话质检

**判定条件**：核查工程师使用的身份验证方式是否属于允许范围。

**合格标准**：身份验证方式仅使用以下之一：
1. Teams
2. 邮件
3. iPad序列号
4. 直线经理

**不合格判定**：使用上述范围之外的方式进行身份验证，或身份验证方式无法识别。

**备注**：与 TEL-003 配套使用。

---

### TEL-005

**规则名称**：身份验证未通过不得提供支持

**适用范围**：电话质检

**判定条件**：核查身份验证未通过时，工程师是否继续提供支持。

**合格标准**：身份验证未通过时，工程师未提供技术支持。

**不合格判定**：身份验证未通过，但工程师继续提供技术支持、查询信息或处理问题。

**备注**：属于强制合规项。

---

### TEL-006

**规则名称**：同日重复来电确认要求

**适用范围**：电话质检

**判定条件**：核查用户描述问题后，工程师是否主动确认用户当天是否已就同一问题咨询过IT服务台。

**合格标准**：工程师明确询问：
> "就此问题今天是否有咨询过IT服务台"

**不合格判定**：未进行同日重复来电确认。

**备注**：建议按标准话术进行识别。

---

### TEL-007

**规则名称**：结束前确认其他需求

**适用范围**：电话质检

**判定条件**：核查工程师在结束通话前是否确认用户还有无其他需要帮助的内容。

**合格标准**：工程师在结束前明确询问用户是否还有其他问题或其他需要帮助的事项。

**不合格判定**：结束通话前未确认用户是否还有其他需求。

**备注**：允许话术同义表达，但语义必须明确。

---

### TEL-008

**规则名称**：服务评价引导要求

**适用范围**：电话质检

**判定条件**：核查工程师在结束通话前是否引导用户进行服务评价。

**合格标准**：工程师明确引导用户评价，标准话术为：
> "麻烦您稍后点击邮件中的笑脸提交评价"

**不合格判定**：未进行服务评价引导。

**备注**：建议优先识别标准话术。

---

### TEL-009

**规则名称**：标准结束语使用要求

**适用范围**：电话质检

**判定条件**：核查工程师在结束通话时是否使用标准结束语。

**合格标准**：工程师使用标准结束语：
> "如果没有其他问题，工单就帮您关闭了"

**不合格判定**：未使用标准结束语，或结束语未体现以下两个核心含义：
1. "确认无其他问题"
2. "工单关闭"

**备注**：允许轻微口语差异，但核心含义不得缺失。

---

### TEL-010

**规则名称**：服务态度合规要求

**适用范围**：电话质检

**判定条件**：核查工程师在通话过程中是否保持礼貌、积极、友好、专业的服务态度。

**合格标准**：工程师全程语气礼貌、态度积极、表达友好、服务专业。

**不合格判定**：语气冷漠、生硬、敷衍，或服务态度明显不专业。

**备注**：建议作为语义辅助判定项，并结合人工复核。

---

### TEL-011

**规则名称**：不良情绪禁止要求

**适用范围**：电话质检

**判定条件**：核查工程师是否在通话中出现不良情绪或失当表达。

**合格标准**：工程师未出现以下任一行为：
- 呵斥
- 嘲笑
- 辱骂
- 明显提高声调表达不满
- 明显不耐烦

**不合格判定**：出现上述任一不良情绪或失当表达。

**备注**：属于负向强判项，建议结合录音人工复核。

---

### TEL-012

**规则名称**：有效解释要求

**适用范围**：电话质检

**判定条件**：核查用户未理解时，工程师是否进行了补充解释或换一种方式说明。

**合格标准**：用户未理解时，工程师进行了进一步解释、重新组织表达或补充说明。

**不合格判定**：用户未理解时，工程师仅机械重复原句，未进行任何补充解释。

**备注**：建议结合上下文语义判定。

---

### TEL-013

**规则名称**：打断用户前礼貌提示要求

**适用范围**：电话质检

**判定条件**：核查工程师打断用户前是否进行礼貌提示。

**合格标准**：如需打断用户，工程师先使用礼貌提示，例如：
> "非常抱歉，打断您一下"

**不合格判定**：在未作礼貌提示的情况下直接打断用户。

**备注**：建议以是否存在明确礼貌提示为判定依据。

---

### TEL-014

**规则名称**：普通话使用要求

**适用范围**：电话质检

**判定条件**：核查工程师在通话过程中是否使用标准普通话。

**合格标准**：工程师全程使用标准普通话，表达清晰可辨。

**不合格判定**：未使用标准普通话，且已影响沟通清晰度或专业性。

**备注**：建议作为人工复核项。

---

### TEL-015

**规则名称**：转接正确性要求

**适用范围**：电话质检

**判定条件**：核查工程师需要转接时，是否将用户正确转接至对应号码、队列或支持路径。

**合格标准**：转接目标正确，且用户被清晰引导至正确支持路径。

**不合格判定**：转接错误，或未正确引导用户进入对应号码、队列或支持路径。

**备注**：建议结合业务记录判定。

---

### TEL-016

**规则名称**：静音前告知要求

**适用范围**：电话质检

**判定条件**：核查工程师在将电话置于静音前是否提前告知用户。

**合格标准**：静音前已明确告知用户，标准话术为：
> "抱歉同事，我需要帮您确认一下，电话会处于静音状态，请您保持电话不要挂断，稍等。"

**不合格判定**：未提前告知即直接静音。

**备注**：建议优先识别标准话术。

---

## 二、Interaction 工单质检规则库（INT-001 ~ INT-011）

Interaction 工单记录每次客户交互的基础信息，质检重点在于工单的唯一性、字段规范性和身份验证记录。

---

### INT-001

**规则名称**：Interaction 唯一创建要求

**适用范围**：Interaction 工单

**判定条件**：核查每一通实际通话是否对应且仅对应一个 Interaction 工单。

**合格标准**：每一通通话创建一个且仅一个 Interaction 工单。

**不合格判定**：漏建 Interaction 工单，或同一通话重复创建多个 Interaction 工单。

**备注**：属于强制一致性规则。

---

### INT-002

**规则名称**：Interaction Short Description 包含 CTI 要求

**适用范围**：Interaction 工单

**判定条件**：核查 Short Description 是否包含 CTI 信息。

**合格标准**：Short Description 包含来源于服务大脑开单信息的 CTI 信息。

**不合格判定**：Short Description 未包含 CTI 信息。

**备注**：建议单独提取 CTI 字段进行匹配。

---

### INT-003

**规则名称**：Interaction Short Description 问题概括要求

**适用范围**：Interaction 工单

**判定条件**：核查 Short Description 是否包含对用户问题的简短描述。

**合格标准**：Short Description 包含由工程师总结的用户问题简短描述，且能体现核心问题。

**不合格判定**：缺少问题描述，或描述无法体现用户反馈的核心问题。

**备注**：与 INT-002 分开判定以降低误识别。

---

### INT-004

**规则名称**：Interaction Short Description 字数要求

**适用范围**：Interaction 工单

**判定条件**：核查 Short Description 中的问题简短描述字数是否符合限制。

**合格标准**：问题简短描述字数不超过 6 个字。

**不合格判定**：问题简短描述超过 6 个字。

**备注**：建议明确字数统计口径。

---

### INT-005

**规则名称**：Interaction Type 一致性要求

**适用范围**：Interaction 工单

**判定条件**：核查 Type 字段是否与实际沟通渠道一致。

**合格标准**：Type 与实际沟通渠道一致，且取值仅为以下之一：
1. Phone
2. Chat
3. Email

**不合格判定**：Type 与实际沟通渠道不一致，或 Type 不在允许范围内。

**备注**：允许值仅限枚举值。

---

### INT-006

**规则名称**：Interaction Caller 一致性要求

**适用范围**：Interaction 工单

**判定条件**：核查 Caller 字段是否与实际报修用户一致。

**合格标准**：Caller 对应的用户 K 账号与实际报修人一致。

**不合格判定**：Caller 与实际报修用户不一致，存在错挂、代挂或挂至无关用户的情况。

**备注**：属于关键归属字段。

---

### INT-007

**规则名称**：Interaction closed abandon 状态原因范围要求

**适用范围**：Interaction 工单

**判定条件**：当 State 为 closed abandon 时，核查 State Reason 是否在允许范围内。

**合格标准**：State Reason 仅为以下之一：
1. Wrong Number
2. Hung up
3. User Abandoned
4. Junk Email
5. Insufficient Information to Progress

**不合格判定**：State 为 closed abandon，但 State Reason 不在允许范围内。

**备注**：属于严格枚举规则。

---

### INT-008

**规则名称**：Interaction closed complete 状态原因限制要求

**适用范围**：Interaction 工单

**判定条件**：当 State 为 closed complete 时，核查是否选择了其他 State Reason。

**合格标准**：State 为 closed complete 时，不选择任何其他 State Reason。

**不合格判定**：State 为 closed complete 时，存在其他 State Reason。

**备注**：属于严格互斥规则。

---

### INT-009

**规则名称**：Interaction Work Notes 身份验证记录要求

**适用范围**：Interaction 工单

**判定条件**：核查 Work Notes 中是否记录身份验证方式。

**合格标准**：Work Notes 包含身份验证方式记录。

**不合格判定**：Work Notes 未记录身份验证方式。

**备注**：与 INT-011 配合使用。

---

### INT-010

**规则名称**：Interaction Work Notes 录音 ID 记录要求

**适用范围**：Interaction 工单

**判定条件**：核查 Work Notes 中是否记录录音 ID。

**合格标准**：Work Notes 包含录音 ID，且录音 ID 格式与实际录音编号一致。

**不合格判定**：Work Notes 未记录录音 ID，或录音 ID 格式明显错误。

**备注**：示例格式：
> a06edd99-1e80-4e91-96ae-a8f271b42318

---

### INT-011

**规则名称**：Interaction 身份验证记录标准格式要求

**适用范围**：Interaction 工单

**判定条件**：核查 Work Notes 中的身份验证记录是否使用规定格式。

**合格标准**：身份验证记录使用以下标准格式之一：

| 英文格式 | 中文格式 | 验证方式 |
|----------|----------|----------|
| Caller's Identity has been verified via Teams | 已经通过Teams验证身份 | Teams |
| Caller's Identity has been verified via Email | 已经通过邮件验证身份 | 邮件 |
| Caller's Identity has been verified via iPad SN | 已经通过iPad序列号验证身份 | iPad序列号 |
| Caller's Identity has been verified via LM | 已经通过直线经理验证身份 | 直线经理 |

**不合格判定**：身份验证记录缺失，或未使用规定格式，或验证方式不在允许范围内。

**备注**：建议进行字符串精确匹配或近似匹配。

---

### Interaction 工单规则分类汇总

|------|----------|--------|-------------|

## 三、Incident 工单质检规则库（INC-001 ~ INC-016）

Incident（事件）工单记录故障和异常事件的处理过程，质检重点在于工单分类准确性、模板规范性和关闭合规性。

---

### INC-001

**规则名称**：Incident Caller 一致性要求

**适用范围**：Incident 工单

**判定条件**：核查 Caller 字段是否与实际用户一致。

**合格标准**：Caller 与实际报修用户一致。

**不合格判定**：Caller 与实际用户不一致。

**备注**：关键归属字段。

---

### INC-002

**规则名称**：Incident Category 一致性要求

**适用范围**：Incident 工单

**判定条件**：核查 Category 字段是否与实际问题一致。

**合格标准**：Category 与用户实际问题匹配。

**不合格判定**：Category 与实际问题不一致。

**备注**：建议与 Subcategory 分开判定。

---

### INC-003

**规则名称**：Incident Subcategory 一致性要求

**适用范围**：Incident 工单

**判定条件**：核查 Subcategory 字段是否与实际问题一致。

**合格标准**：Subcategory 与用户实际问题匹配。

**不合格判定**：Subcategory 与实际问题不一致。

**备注**：建议与 Category 联动校验。

---

### INC-004

**规则名称**：Incident Priority 上限要求

**适用范围**：Incident 工单

**判定条件**：核查非母单场景下 Priority 是否高于 3 级。

**合格标准**：非母单场景下，Priority 不高于 3 级。

**不合格判定**：非母单场景下，Priority 高于 3 级。

**备注**：如属于母单场景，应排除本规则。

---

### INC-005

**规则名称**：Incident Short Description 包含 CTI 要求

- "如何使用"
- 及其他等同含义字样

**不合格判定**：Short Description 中出现上述禁用词。

## 五、规则体系设计特征总结

### 5.1 规则命名规范

| 前缀 | 适用对象 | 规则总数 |
|------|----------|----------|
| TEL- | 电话质检 | 16 |
| INT- | Interaction 工单 | 11 |
| INC- | Incident 工单 | 16 |
| REQ- | Request 工单 | 13 |
| **合计** | | **56**（文件共 60 条，部分可能在不同版本中有调整） |

### 5.2 规则结构统一性

每条规则均严格遵循六字段结构：编号 → 名称 → 适用范围 → 判定条件 → 合格标准 → 不合格判定 → 备注。这种结构化表达为实现配置化规则系统提供了良好的数据模型基础。

### 5.3 规则分层特征

| 规则层级 | 特征 | 典型示例 | 建议判定方式 |
|----------|------|----------|-------------|
| 硬性规则 | 标准明确、边界清晰 | TEL-002 开场语、INT-005 Type 枚举、INC-015 Resolution Code 枚举 | 规则引擎（关键词匹配、正则、字段校验） |
| 半结构化规则 | 需要语义判断但标准明确 | TEL-010 服务态度、TEL-012 有效解释、INT-003 问题概括 | 规则模板 + LLM 辅助 |
| 强制合规项 | 不容许任何例外 | TEL-003 身份验证前置、TEL-005 验证未通过不得支持、TEL-011 不良情绪 | 硬性规则 + 人工复核 |
| 分析类规则 | 跨工单/跨维度的趋势发现 | INC/REQ 禁用词检测（工单类型错误信号）、INT-001 唯一创建（漏建/重复创建） | 统计分析 + 根因推荐 |

### 5.4 判定方式多样性

根据备注字段的指示，规则采用了以下多种判定方式：

| 判定方式 | 适用规则数量 | 示例 |
|----------|-------------|------|
| 精确匹配/关键词识别 | ~20 条 | INT-011 身份验证格式、INC-007 禁用词、REQ-007 禁用词 |
| 字段校验/枚举校验 | ~15 条 | INT-005 Type 枚举、INT-007 State Reason 枚举、INC-015 Resolution Code |
| 语义判定/LLM 辅助 | ~10 条 | TEL-010 服务态度、TEL-012 有效解释 |
| 人工复核 | ~8 条 | TEL-011 不良情绪、TEL-014 普通话 |
| 交叉校验 | ~5 条 | INC-002+003 Category+Subcategory 联动、INC-014 Service 一致性 |
| 时间校验 | ~4 条 | INC-011/012 邮件模板时间、REQ-011/012 邮件模板时间 |

### 5.5 跨工单类型的共性规则模式

三种工单类型（Interaction、Incident、Request）之间存在以下共性规则模式：

| 共性模式 | INT | INC | REQ |
|----------|-----|-----|-----|
| Caller 一致性 | INT-006 | INC-001 | REQ-001 |
| Short Description 含 CTI | INT-002 | INC-005 | REQ-005 |
| Short Description 概括要求 | INT-003 | INC-006 | REQ-006 |
| Description 模板要求 | — | INC-008 | REQ-008 |
| Description Caller PRID | — | INC-009 | REQ-009 |
| 派单模板联系电话 | — | INC-010 | REQ-010 |
| 邮件模板时间间隔 | — | INC-011 | REQ-011 |
| 邮件模板时间真实性 | — | INC-012 | REQ-012 |
| Priority 上限 | — | INC-004 | REQ-004 |

### 5.6 工单类型差异化规则

Incident 和 Request 各自有差异化的禁用词规则，体现了不同工单类型的功能定位：

| 工单类型 | 禁用词规则 | 禁用的关键词 | 设计意图 |
|----------|-----------|-------------|----------|
| Incident | INC-007 | "How to"、"如何使用" | 防止故障工单被误用为操作指导 |
| Request | REQ-007 | "无法"、"不能"、"报错" | 防止需求工单被误用于故障申报 |

此外，Interaction（INT）和 Incident/Request 之间还有一个关键差异：INT 有状态管理规则（INT-007 状态原因枚举、INT-008 状态互斥）和 Work Notes 记录规则（INT-009/010/011），而 INC/REQ 关注的是模板规范性、关闭时效和 Resolution 规范。

### 5.7 对质检系统实现的指导意义

1. **规则引擎可配置化**：所有硬性/枚举类规则（约占 60%）可直接配置化为规则引擎的判定条件
2. **LLM Prompt 模板设计**：所有语义类规则（约占 15%）需要配套 LLM Prompt 模板，并定义评估标准
3. **人工复核工作流**：强制合规类和语义辅助类规则（约占 25%）需配套人工复核工作流
4. **字段级校验**：工单类规则中的字段必填、枚举校验、互斥校验可直接通过 ITSM 系统 API 完成
5. **证据输出标准化**：备注中多次提到"建议识别标准话术""建议提取字段""建议交叉校验"，为证据输出提供了明确方向
