## 一、项目愿景与核心诉求

希望规划一套面向呼叫中心的智能质检体系，整合知识库、质检规则、工单、录音文件以及大语言模型（LLM）能力，形成从单通质检到团队分析再到改进闭环的一体化方案。

### 1.1 三个核心诉求

**诉求一：知识库重组**

希望评估是否从当前以应用为单位的组织方式，调整为以业务单元为单位进行建设。比如"会议活动"作为一级业务主题，其下再按报名、签到、证书、变更等业务子主题分类，应用系统作为次级或附属维度存在。这样更符合客户问题表达方式，也更利于 AI 进行知识检索、语义判断和质检分析。

**诉求二：规则可配置化**

希望规则可以灵活配置和控制，并且支持非 AI 人员维护使用。规则体系需要同时支持硬性规则、语义规则、知识一致性判断和工单一致性校验。

**诉求三：多层级输出**

希望不仅有单通质检结果和评分，还能生成员工分析报告、团队/项目 Findings、缺陷汇总，以及团队和个人维度的缺陷趋势、成长路径和培训建议，从而形成质量管理闭环。

## 二、项目目标定义

这套体系的核心，不只是"用大语言模型去听录音并打分"，而是建设一套可持续运营的智能质检平台。目标定义为以下几个层次：

### 2.1 业务目标

- **提升质检覆盖率**：从传统人工抽检的低覆盖，逐步提升到高比例甚至全量质检。
- **提升质检一致性**：减少不同质检员之间标准不一致的问题。
- **缩短质检周期**：从通话结束到质检结果输出尽量自动化、缩短反馈时间。
- **沉淀共性问题**：不仅看单通电话是否合规，还能发现团队、项目、流程、知识、培训层面的系统性问题。
- **支持员工成长**：从"找问题"升级为"发现问题 + 分析原因 + 给出改进路径"。

### 2.2 管理目标

- **规则可配置**：业务团队、质检团队可以在不依赖算法工程师的前提下，维护和调整质检规则。
- **知识可复用**：知识库能够按业务视角组织，而不是仅按系统或应用拆散。
- **结果可追溯**：每一个质检结论都能回溯到录音、转写文本、规则、知识依据。
- **输出可管理**：结果不只是一个分数，而是一整套可用于运营管理的报告和看板。

### 2.3 AI 目标

- 利用大语言模型提升复杂场景判断能力，如话术适配、情绪识别、是否真正解决问题、是否体现同理心、是否给出错误指引等。
- 将大模型与传统规则结合，避免完全黑盒，保证可解释性和可控性。
- 把知识库、工单、录音、质检标准打通，形成统一分析能力。

## 三、总体方案框架

### 3.1 建议的总体能力架构

整个体系可以分成 6 个层次：

#### 第一层：数据输入层

包括：

| 数据类型 | 说明 |
|----------|------|
| 录音文件 | 通话音频原始文件 |
| ASR 转写文本 | 自动语音识别后的结构化文本 |
| 工单数据 | Interaction / Incident / Request 工单 |
| 客户信息 / 业务标签 | K 账号、所属 BU、业务线标签 |
| 知识库内容 | 标准化的业务知识条目 |
| 质检规则库 | 配置化的质检规则集合 |
| 坐席与组织信息 | 坐席个人信息、团队归属、技能组 |
| 历史质检结果 | 过往的质检评分和标签数据 |
| 投诉、升级、复联等结果数据 | 服务结果反馈数据 |

#### 第二层：基础处理层

包括：

- 录音转文字（ASR）
- 说话人分离（客户/坐席）
- 静音、打断、语速、情绪等音频特征提取
- 工单与通话匹配
- 知识召回（Knowledge Retrieval）
- 数据清洗与标准化

#### 第三层：规则与 AI 评估层

采用**规则引擎 + 大语言模型结合**的方式：

**强规则类判断**

适合传统规则引擎直接判定，包括：

- 是否说了开场白
- 是否核验身份
- 是否出现禁用话术
- 是否超时静默
- 是否超出规定时长
- 是否按规定创建工单
- 是否选择正确工单分类

**弱规则 / 语义类判断**

需要语义理解，包括：

- 是否准确理解客户问题
- 是否有效安抚情绪
- 是否给出完整解决方案
- 是否存在推诿
- 是否符合服务规范

**知识一致性判断**

- 坐席回答是否与知识库一致
- 是否存在错误解释
- 是否存在过期信息
- 是否漏答关键信息

**工单一致性判断**

- 通话内容与工单记录是否一致
- 是否少记、错记、误分类

**风险识别**

- 投诉风险
- 合规风险
- 客户流失风险
- 升级风险

#### 第四层：结果生成层

输出：

- 单通质检结果
- 单员工分析报告
- 团队 / 项目汇总报告
- Findings 与缺陷聚类
- 改进建议与培训建议
- 趋势看板与成长路径

#### 第五层：运营管理层

包括：

- 规则配置后台
- 知识维护后台
- 质检复核机制
- 申诉与修正流程
- 标注与反馈闭环
- 模型持续优化机制

#### 第六层：决策与改进层

用于支持：

- 培训计划
- 流程优化
- 知识库修订
- 项目运营改进
- 绩效与辅导

## 四、知识库设计：按"业务单元"还是"应用"建设

### 4.1 按业务单元建设的核心理由

把知识库从"按应用创建"改为"按业务单元创建"。

因为呼叫中心场景中，客户的问题通常不是从"应用系统视角"出发，而是从**业务问题视角**出发。

比如客户问的是：

- 我怎么报名会议活动？
- 为什么我的活动签到失败？
- 活动后证书在哪里下载？
- 报名信息填错了怎么办？

**客户不会天然区分这是应用 A、应用 B 还是应用 C 的功能模块。**

如果知识库按应用拆得很碎，容易导致：

- 坐席找知识困难
- AI 检索不到完整上下文
- 同一个业务主题的信息分散在多个应用下
- 质检时难以判断"坐席是否回答完整"

### 4.2 推荐的知识库组织方式

建议采用以下层级结构：

**业务单元 / 业务域 → 主题 → 子主题 → 应用 / 流程节点 → 知识条目**

示例：以"会议活动"为例

```
会议活动（业务单元）
├── 活动报名（主题）
│   ├── 报名流程（子主题）
│   │   ├── 应用 A - 报名模块（应用/流程节点）
│   │   │   ├── 知识条目：报名操作步骤
│   │   │   └── 知识条目：常见报名失败原因
│   │   └── 应用 B - 报名验证（应用/流程节点）
│   │       └── 知识条目：验证码收不到的处理方法
│   └── 报名信息修改（子主题）
│       └── ...
├── 活动签到（主题）
│   ├── 签到失败（子主题）
│   │   ├── 应用 C - 签到系统（应用/流程节点）
│   │   │   ├── 知识条目：签到失败常见原因
│   │   │   └── 知识条目：二维码失效处理方法
│   │   └── ...
│   └── ...
├── 活动证书（主题）
│   └── ...
└── 活动变更（主题）
    └── ...
```

### 4.3 这种结构的优势

- 更符合用户问题表达方式
- 更适合 AI 做语义检索
- 更方便做质检判断
- 更有利于跨应用问题归类
- 方便后续做缺陷聚类和趋势分析

### 4.4 需要注意的问题与解决思路

如果完全按业务单元建，也要避免两个风险：

**风险一：知识重复**

同一条规则或处理方式可能被多个主题重复维护。

解决思路是采用三层知识模型：

- **公共知识层**：跨业务通用的处理规则和流程（如"如何验证用户身份"、"标准投诉处理流程"）
- **业务知识层**：某业务主题特有的知识和解决方案（如"会议活动报名失败的处理方法"）
- **应用细节层**：具体系统的操作步骤和技术细节（如"应用 A 的报名模块操作指南"）

**风险二：责任边界不清**

按业务建库后，谁来维护内容必须明确。

建议每个主题必须有：

- 业务 Owner
- 知识 Owner
- 审核人
- 生效机制

## 五、质检规则体系设计

**"规则可以灵活输入和控制，但非 AI 人员也可以使用"**，这是设计重点要求。

所以不要把质检能力完全做成 Prompt 工程，而要做成**配置化规则体系**。

### 5.1 规则体系建议分层

建议将质检规则分成四类：

#### 第一类：硬性规则

适合传统规则引擎直接判断，标准明确。

例如：

- 是否使用标准开场白
- 是否进行身份核验
- 是否说了结束语
- 是否触发敏感词
- 是否出现长时间静音
- 是否超出规定时长
- 是否按规定创建工单
- 是否选择正确工单分类

这类规则的特点是：

- 判断清晰
- 可解释性强
- 适合配置化
- 不一定需要大模型

#### 第二类：半结构化规则

需要一些语义判断，但边界相对明确。

例如：

- 是否完整告知处理路径
- 是否回答了客户核心问题
- 是否给出了下一步动作
- 是否体现服务礼貌
- 是否存在明显推诿

这类适合：

- 规则模板 + LLM 判定
- 需要可配置的评分标准与判定依据

#### 第三类：复杂语义规则

需要大模型综合上下文、知识库、工单信息做判断。

例如：

- 坐席解答是否准确且符合知识库
- 是否真正解决客户问题
- 是否识别客户情绪并做了有效安抚
- 是否遗漏了关键风险提示
- 是否存在"表面回答了，但实际上未解决"的情况

#### 第四类：分析类规则

不只针对单通，而是针对趋势和模式。

例如：

- 某团队在哪类业务问题上缺陷高发
- 某员工重复出现哪类缺陷
- 某项目上线后问题集中在哪个主题
- 某知识条目是否频繁引发错误回答

### 5.2 规则配置的产品形态建议

为了让非 AI 人员也能用，建议规则配置页面支持以下元素（举例说明，并非最终要求）：

| 配置元素 | 说明 | 示例 |
|----------|------|------|
| 规则名称 | 规则的唯一标识 | "是否完成身份核验" |
| 规则分类 | 硬性/半结构化/复杂语义/分析类 | 硬性规则 |
| 适用范围 | 项目、业务线、团队、渠道 | 涉及账户、订单、个人信息查询的来电 |
| 触发条件 | 什么情况下触发该规则判定 | 通话涉及账户/订单/个人信息 |
| 评分方式 | 扣分/加分/通过/不通过 | 未执行扣 10 分 |
| 扣分/加分分值 | 具体分值 | -10 |
| 判定方式 | 关键词、正则、字段校验、模型判断 | 关键词规则 + 大模型辅助 |
| 知识依据 | 关联的知识条目 | 知识库-身份验证流程 |
| 示例 | 合格/不合格的参考示例 | 展示标准话术和违规话术 |
| 优先级 | 多条规则冲突时的优先级 | 高 |
| 生效时间 | 规则何时开始生效 | 2026-07-01 |
| 版本号 | 规则的版本管理 | v1.0 |

### 5.3 推荐的规则表达方式

**不要让业务人员直接写复杂 Prompt。**

应该设计成"表单式 + 模板式"。

**示例一：硬性规则**

> **规则名称**：是否完成身份核验
>
> **适用场景**：涉及账户、订单、个人信息查询的来电
>
> **判定标准**：坐席需在处理前核验至少 2 项身份信息
>
> **判定方式**：关键词规则 + 大模型辅助
>
> **评分**：未执行扣 10 分
>
> **证据输出**：显示命中的对话片段

**示例二：复杂语义规则**

> **规则名称**：是否准确解答活动报名失败问题
>
> **知识依据**：知识库-会议活动-活动报名-报名失败
>
> **判定标准**：坐席需识别失败原因，并提供与知识库一致的解决方案
>
> **判定方式**：知识召回 + 大模型语义比对
>
> **评分**：错误解释扣 15 分，部分遗漏扣 8 分
>
> **证据输出**：标准答案、坐席回答、差异点说明

## 六、数据与处理流程设计

（注意：以下为建议链路，还需 AI 团队评估确认）

### 6.1 端到端流程

#### 第一步：采集原始数据

输入包括：

- 通话录音
- 通话元数据（时间、坐席、客户、队列、项目）
- ASR 文本
- 工单信息
- 业务标签
- 知识库内容
- 质检规则

#### 第二步：预处理

包括：

- 录音转写
- 说话人区分
- 去噪与文本清洗
- 通话与工单关联
- 主题识别
- 客户意图识别

#### 第三步：知识召回

基于通话主题、客户问题、工单类型，从知识库中召回相关知识条目。

这一步非常关键，因为后续要做：

- 是否答对
- 是否答全
- 是否按最新规则回答
- 是否应升级处理

#### 第四步：规则判定

包括：

- 传统规则引擎判定
- 大模型语义判定
- 音频特征判定
- 工单一致性判定

#### 第五步：结果整合与打分

形成：

- 维度分
- 总分
- 缺陷标签
- 风险标签
- 改进建议
- 证据片段

#### 第六步：报告输出与管理闭环

包括：

- 单通报告
- 员工报告
- 团队报告
- 项目报告
- Findings 汇总
- 培训建议
- 规则优化建议
- 知识库优化建议

## 七、质检报告设计

希望输出分数、员工分析报告、项目团队 Findings、缺陷汇总，并看到团队和个人缺陷及成长路径。报告不能只是一份打分表，而要形成**多层级输出**。

### 7.1 单通质检报告

**面向**：质检员、主管、坐席本人

**应包含**：

| 内容项 | 说明 |
|--------|------|
| 基础信息 | 通话时间、时长、员工、项目、业务类型 |
| 总分与维度分 | 综合得分和各子维度得分 |
| 规则命中情况 | 哪些规则合格、哪些不合格 |
| 关键缺陷 | 重要的不合格项详情 |
| 亮点表现 | 表现优秀的方面 |
| 知识一致性判断 | 坐席回答是否与标准知识一致 |
| 工单一致性判断 | 通话内容与工单记录是否一致 |
| 风险提示 | 合规风险、投诉风险、升级风险 |
| 关键证据片段 | 命中缺陷的对话原文 |
| 改进建议 | 针对性的改善方向 |

**建议维度可以包括**：

- 服务规范
- 业务准确性
- 问题解决能力
- 沟通体验
- 合规风险
- 工单规范性

### 7.2 员工分析报告

**面向**：员工本人、班组长、培训团队

**应包含**：

| 内容项 | 说明 |
|--------|------|
| 周期总分趋势 | 以周/月为单位的得分变化趋势 |
| 各维度得分变化 | 每个质检维度的得分变化 |
| 高频缺陷类型 | 反复出现最多的缺陷种类 |
| 高频优秀表现 | 反复表现优秀的方面 |
| 与团队平均水平对比 | 个人在团队中的相对位置 |
| 典型案例 | 优秀和需要改善的代表性通话 |
| 成长建议 | 针对缺陷的改进方向 |
| 培训建议 | 建议参加哪些培训课程 |
| 成长路径记录 | 从入职至今的能力变化轨迹 |

#### 成长路径设计

"成长路径"，建议做成类似下面的逻辑：

- **第一阶段**：基础服务规范达标 — 开场、核验、结束语等基础流程合规
- **第二阶段**：业务知识准确率提升 — 能正确回答常见业务问题
- **第三阶段**：复杂问题解决能力提升 — 能独立处理非标场景
- **第四阶段**：高情绪客户处理能力提升 — 能有效安抚和处理投诉客户

这样**管理层能看到员工不是只有"差/好"，而是在哪个能力阶段、下一步该补什么**。

### 7.3 团队/项目报告

**面向**：项目经理、运营经理、质量负责人

**应包含**：

| 内容项 | 说明 |
|--------|------|
| 整体质检得分 | 团队的总体质检评分 |
| 覆盖率 | 质检覆盖的通话比例 |
| 缺陷分布 | 各类型缺陷的数量和占比 |
| 风险分布 | 各类型风险的分布情况 |
| 主题问题排名 | 哪些业务主题下问题最多 |
| 业务类型问题排名 | 哪些业务类型问题最集中 |
| 团队间对比 | 不同团队之间的质检得分对比 |
| 规则命中趋势 | 各规则的命中率变化趋势 |
| 知识库不匹配问题 | 哪些知识条目频繁与坐席回答不匹配 |
| Findings 汇总 | 本周期内的管理发现汇总 |

### 7.4 Findings 报告建议

**Findings 不要只写"发现了什么"，而要写成运营可用的格式**：

| Findings 字段 | 说明 |
|---------------|------|
| Finding 标题 | 简洁概括发现的问题 |
| 问题描述 | 详细描述问题的具体表现 |
| 影响范围 | 影响的业务、团队、客户范围 |
| 涉及团队/项目 | 受影响的组织单元 |
| 根因判断 | 分析问题的根本原因 |
| 证据样本 | 引用具体的案例和数据 |
| 风险等级 | 高/中/低 |
| 建议动作 | 针对性的改进措施 |
| 责任人 | 负责落实改进的人 |
| 跟踪状态 | 进行中/已完成/待启动 |

**示例**：

> **Finding**：活动签到失败场景下，坐席对"超时未签到"和"系统异常"的区分不清
>
> **影响**：导致错误承诺和重复来电
>
> **范围**：会议活动项目 A/B 组
>
> **根因**：知识条目描述不清 + 培训未覆盖异常分流
>
> **建议**：修订知识条目、增加专项培训、增加规则提醒

## 八、缺陷体系与成长路径设计

这部分是很多质检体系容易缺失的地方。

如果没有统一缺陷分类，最后只能看到很多零散问题，**无法形成管理动作**。

### 8.1 缺陷分类建议

建议建立统一的**缺陷树**，至少包括：

#### 一级缺陷分类

| 一级缺陷类型 | 说明 |
|-------------|------|
| 服务规范类 | 与标准服务流程相关的问题 |
| 业务知识类 | 与业务知识掌握相关的问题 |
| 沟通技巧类 | 与沟通表达能力相关的问题 |
| 解决能力类 | 与问题分析和解决能力相关的问题 |
| 合规风险类 | 涉及合规和安全的问题 |
| 工单处理类 | 与工单创建和填写相关的问题 |
| 情绪处理类 | 与客户情绪管理相关的问题 |

#### 二级缺陷示例

以"业务知识类"为例，二级缺陷可以包括：

- 回答错误
- 回答不完整
- 使用过期知识
- 未识别特殊场景
- 未告知限制条件
- 升级条件判断错误

以"沟通技巧类"为例，二级缺陷可以包括：

- 打断客户
- 缺乏同理心
- 表达模糊
- 逻辑不清
- 重复机械表述

### 8.2 成长路径建议

成长路径不是简单分高低，而是按**能力成熟度**定义。

| 等级 | 名称 | 描述 |
|------|------|------|
| L1 | 基础合规型 | 能完成基础服务流程；开场、核验、结束语达标；无明显合规问题 |
| L2 | 标准执行型 | 能依据知识库正确回答常见问题；工单填写规范；基础客户安抚到位 |
| L3 | 问题解决型 | 能独立处理复杂问题；能识别异常场景；能减少客户重复来电 |
| L4 | 体验优化型 | 能处理高情绪客户；能提供更完整、更主动的解决方案；有稳定高质量表现 |
| L5 | 示范辅导型 | 能输出优秀案例；能帮助团队复盘；可作为培训标杆 |

这样就可以把**个人报告从"缺陷清单"升级为"能力地图"**。

## 九、大语言模型在体系中的定位

LLM 不是替代所有模块，而是**嵌入到关键节点中**。

### 9.1 LLM 适合做的事情

- 对话摘要
- 客户意图识别
- 服务过程理解
- 复杂语义规则判断
- 知识一致性校验
- 根因归纳
- 缺陷聚类
- 报告自动生成
- 员工反馈建议生成
- 项目 Findings 提炼

### 9.2 LLM 不应单独承担的事情

- 明确格式校验（如工单字段非空、长度限制）
- 固定流程校验（如开场白、结束语的固定文本匹配）
- 严格合规项判定（如身份验证方式范围校验）
- 可量化的静音/抢话/时长判断
- 强依赖精确条件的打分

这些更适合**规则或传统算法**。

## 十一、关键设计原则总结

1. **LLM 嵌入关键节点而非替代所有模块** — 规则引擎与 LLM 各司其职，保证可解释性
2. **规则做成配置化体系而非纯 Prompt 工程** — 表单式 + 模板式，非 AI 人员可维护
3. **知识库按业务视角组织** — 公共层 + 业务层 + 应用层三层结构，符合客户问题表达方式
4. **输出四层级报告** — 单通 → 员工 → 团队 → Findings，形成管理信息流
5. **缺陷体系与成长路径配套** — 从"缺陷清单"升级为"能力地图"，形成改进闭环
6. **规则四类分层** — 硬性 / 半结构化 / 复杂语义 / 分析类，不同判定方式各取所长
7. **结果可追溯** — 每个结论都能回溯到录音、转写、规则、知识依据
