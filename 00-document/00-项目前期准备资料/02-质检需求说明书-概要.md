# 服务大脑质检需求说明书 v1.0 — 概要

> 来源：`02-质检需求说明书-原件.pdf`（董如鑫，2026/07/07，12 页；原文件名「服务大脑质检需求说明书v1.0.pdf」）

## 一、项目愿景与目标

希望规划一套面向呼叫中心的智能质检体系，整合**知识库、质检规则、工单、录音文件以及大语言模型（LLM）能力**，形成从单通质检到团队分析再到改进闭环的一体化方案。

三个核心诉求：知识库按业务单元重组（而非按应用拆分）；质检规则可灵活配置且非 AI 人员可维护；输出不仅有分数还有管理可用的多层级报告。

### 1.1 业务目标

- 提升质检覆盖率：从人工抽检的低覆盖，提升到高比例甚至全量质检
- 提升质检一致性：减少不同质检员之间标准不一致的问题
- 缩短质检周期：从通话结束到结果输出尽量自动化
- 沉淀共性问题：不仅看单通合规，还能发现团队、项目、流程、知识、培训层面的系统性问题
- 支持员工成长：从"找问题"升级为"发现问题→分析原因→给出改进路径"

### 1.2 管理目标

- 规则可配置：业务/质检团队可以不依赖算法工程师维护规则
- 知识可复用：知识库按业务视角组织，不按系统或应用拆散
- 结果可追溯：每个结论都能回溯到录音、转写、规则、知识依据
- 输出可管理：结果不只是一个分数，而是全套运营管理报告和看板

### 1.3 AI 目标

- 利用 LLM 提升复杂场景判断（话术适配、情绪识别、是否真正解决问题、同理心、错误指引等）
- 将大模型与传统规则结合，避免完全黑盒，保证可解释性和可控性
- 打通知识库、工单、录音、质检标准，形成统一分析能力

## 二、总体方案框架（六层架构）

### 第一层：数据输入层
录音文件、ASR 转写文本、工单数据、客户信息/业务标签、知识库内容、质检规则库、坐席与组织信息、历史质检结果、投诉/升级/复联等结果数据

### 第二层：基础处理层
录音转文字、说话人分离（客户/坐席）、静音/打断/语速/情绪等音频特征提取、工单与通话匹配、知识召回、数据清洗与标准化

### 第三层：规则与 AI 评估层（四类判定）
- **强规则类**：开场白、身份核验、禁用话术、超时静默等
- **弱规则/语义类**：理解准确度、情绪安抚、解决方案完整性、推诿判断、服务规范
- **知识一致性**：坐席回答 vs 知识库比对（错误解释、过期信息、漏答关键信息）
- **工单一致性**：通话内容 vs 工单记录（少记、错记、误分类）

### 第四层：结果生成层
单通质检结果、单员工分析报告、团队/项目汇总报告、Findings 与缺陷聚类、改进建议与培训建议、趋势看板与成长路径

### 第五层：运营管理层
规则配置后台、知识维护后台、质检复核机制、申诉与修正流程、标注与反馈闭环、模型持续优化

### 第六层：决策与改进层
培训计划、流程优化、知识库修订、项目运营改进、绩效与辅导

## 三、知识库设计

### 3.1 核心主张：按业务单元建设

把知识库从"按应用创建"改为"按业务单元创建"。客户问题从业务视角出发（如报名、签到、证书），而非从系统视角。

当前"按应用拆碎"的问题：坐席找知识困难、AI 检索不到完整上下文、同一业务主题信息分散在多个应用下、质检时难以判断回答完整性。

### 3.2 推荐层级结构

**业务单元/业务域 → 主题 → 子主题 → 应用/流程节点 → 知识条目**

### 3.3 三层知识模型

- **公共知识层**：跨业务通用的处理规则
- **业务知识层**：某业务主题特有的知识
- **应用细节层**：具体系统的操作细节

### 3.4 管理机制

每个主题需要指定：业务 Owner、知识 Owner、审核人、生效机制。避免两个风险：知识重复和责任边界不清。

## 四、质检规则体系设计

### 4.1 四类规则分层

**第一类：硬性规则** — 传统规则引擎直接判断（开场白、身份核验、敏感词、静音、工单创建等）。特点：判断清晰、可解释性强、适合配置化、不一定需要大模型。

**第二类：半结构化规则** — 需要语义判断但边界明确（是否完整告知处理路径、是否体现服务礼貌、是否明显推诿）。适合规则模板 + LLM 判定，需要可配置的评分标准。

**第三类：复杂语义规则** — 需要 LLM 综合上下文/知识库/工单判断（解答准确性、问题是否真正解决、情绪识别与安抚、关键风险提示遗漏、表面回了但实际未解决）。

**第四类：分析类规则** — 针对趋势和模式（某团队哪类问题高发、某员工重复缺陷、某项目上线后问题集中领域、某知识条目频繁引发错误回答）。

### 4.2 规则配置的产品形态

支持非 AI 人员维护，规则配置页面应包含：规则名称、分类、适用范围（项目/业务线/团队/渠道）、触发条件、评分方式、扣分/加分分值、判定方式（关键词/正则/字段校验/模型判断）、知识依据、示例、优先级、生效时间、版本号。

### 4.3 表达方式：表单式 + 模板式

不让业务人员写复杂 Prompt。以"是否完成身份核验"为例：

> 适用范围：涉及账户、订单、个人信息查询的来电
> 判定标准：坐席需核验至少 2 项身份信息
> 判定方式：关键词规则 + 大模型辅助
> 评分：未执行扣 10 分
> 证据输出：显示命中的对话片段

## 五、数据与处理流程

六步端到端流程：
1. **采集原始数据**：通话录音、元数据、ASR 文本、工单、业务标签、知识库、质检规则
2. **预处理**：录音转写、说话人区分、去噪清洗、通话与工单关联、主题/意图识别
3. **知识召回**：基于通话主题、客户问题、工单类型，从知识库中召回相关条目（关键步骤，后续所有准确性判定依赖此步骤）
4. **规则判定**：传统规则引擎 + LLM 语义判定 + 音频特征判定 + 工单一致性判定
5. **结果整合与打分**：维度分、总分、缺陷标签、风险标签、改进建议、证据片段
6. **报告输出与管理闭环**：单通报告、员工报告、团队报告、项目报告、Findings 汇总、培训建议、规则/知识库优化建议

## 六、质检报告设计（四层级）

### 6.1 单通质检报告（面向质检员、主管、坐席）
包含：基础信息、总分与维度分、规则命中情况、关键缺陷、亮点表现、知识/工单一致性判断、风险提示、证据片段、改进建议。建议维度：服务规范、业务准确性、问题解决能力、沟通体验、合规风险、工单规范性。

### 6.2 员工分析报告（面向本人、班组长、培训团队）
包含：周期总分趋势、各维度得分变化、高频缺陷/优秀表现、与团队平均水平对比、典型案例、成长建议、培训建议、成长路径记录。

**成长路径五阶段：** L1 基础合规型 → L2 标准执行型 → L3 问题解决型 → L4 体验优化型 → L5 示范辅导型。让管理层看到员工不是在"差/好"之间，而是在哪个能力阶段、下一步该补什么。

### 6.3 团队/项目报告（面向项目经理、运营经理、质量负责人）
包含：整体得分、覆盖率、缺陷/风险分布、主题/业务类型问题排名、团队间对比、规则命中趋势、知识库不匹配问题、Findings 汇总。

### 6.4 Findings 报告（运营可用的管理格式）
每一项 Finding 应包含：标题、问题描述、影响范围、涉及团队/项目、根因判断、证据样本、风险等级、建议动作、责任人、跟踪状态。

## 七、缺陷体系与成长路径

### 7.1 缺陷分类树

**一级缺陷：** 服务规范类、业务知识类、沟通技巧类、解决能力类、合规风险类、工单处理类、情绪处理类

**二级缺陷示例（业务知识类下）：** 回答错误、回答不完整、使用过期知识、未识别特殊场景、未告知限制条件、升级条件判断错误

### 7.2 成长路径（能力成熟度模型）

L1→L5 五级进阶，将个人报告从"缺陷清单"升级为"能力地图"。

## 八、LLM 在体系中的定位

### LLM 适合做的事
对话摘要、客户意图识别、服务过程理解、复杂语义规则判断、知识一致性校验、根因归纳、缺陷聚类、报告自动生成、员工反馈建议生成、项目 Findings 提炼

### LLM 不应单独承担的事
明确格式校验、固定流程校验、严格合规项判定、可量化的静音/抢话/时长判断、强依赖精确条件的打分——这些更适合规则或传统算法

## 九、建议系统模块拆分

| 模块 | 核心功能 |
|------|----------|
| 知识管理模块 | 业务单元视角建库、主题/子主题分类、版本管理、Owner 机制、知识质量评估 |
| 规则管理模块 | 规则配置、模板、适用范围管理、评分模型、版本管理、测试与灰度发布 |
| 质检执行模块 | 录音接入、ASR 解析、自动质检、结果复核、异议申诉、证据展示 |
| 报表分析模块 | 单通/员工/团队/项目报告、Findings 管理、趋势看板 |
| 模型运营模块 | Prompt 模板管理、评估集管理、模型效果监控、人工反馈闭环、错误案例回灌 |

## 十、关键设计原则总结

1. LLM 嵌入关键节点而非替代所有模块
2. 规则做成配置化体系而非纯 Prompt 工程
3. 知识库按业务视角组织，含公共层+业务层+应用层三层结构
4. 输出四层级报告：单通 → 员工 → 团队 → Findings
5. 缺陷体系与成长路径配套，形成改进闭环
6. 强规则/弱规则/语义规则/分析类规则分层设计
7. 规则配置支持非 AI 人员维护（表单式 + 模板式）
