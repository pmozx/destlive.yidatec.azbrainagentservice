## 1. Python 基础编码规范

### 1.1 代码风格与工具

- 统一使用 `ruff`（lint + format）+ `mypy`（至少对 `app/core/` 与 `app/modules/*/service.py` 开启检查）；行宽 120。
- 命名：模块/包 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE_CASE`，私有函数/变量加 `_` 前缀。
- 类型注解：所有公开函数必须完整注解参数与返回值；禁止裸 `dict`/`list`，使用 `dict[str, Any]` 等泛型写法。

```python
# ✅
async def load_name_maps(db: AsyncSession, space_ids: list[int]) -> dict[int, str]: ...

# ❌
async def loadNameMaps(db, ids): ...
```

### 1.2 异常处理

**规则 R1：禁止用 `except Exception` 包装后把原始异常"翻译"成字符串再抛出。** 存量整改：`base_crud.py` 有 18 处 `raise CustomException(msg=f"...: {e!s}")`，把 `IntegrityError`（应映射 409）压成 500，且 `msg` 会把 SQL 细节回显给客户端（对应报告 P0-5/P2-3）。

```python
# ❌ 吞掉异常类型，全局 handler 永远接不到 IntegrityError
try:
    await db.execute(stmt)
except Exception as e:
    raise CustomException(msg=f"创建失败: {e!s}")

# ✅ 不捕或只记日志，让全局异常处理器按类型映射（IntegrityError -> 409 等）
async with db.begin():
    await db.execute(stmt)
```

**规则 R2：清理类操作（删 S3、删向量）允许 `except Exception` 只告警不阻断主流程，但必须 `logger.exception` 记录完整堆栈，且注释说明"失败只告警"是有意为之。**

**规则 R3：禁止裸 `except:`；`except Exception` 范围尽量小，不要包住整个业务块。**

**规则 R4：业务异常必须显式携带 HTTP 状态码**——`CustomException` 默认状态码按整改后约定（4xx），"资源不存在"一律用 `get_or_404` 或显式 `status_code=404`：

```python
# ❌ 默认 500，"名称已占用"监控上变成服务器故障
raise CustomException(msg="空间编码已存在")

# ✅
raise CustomException(msg="空间编码已存在", status_code=409)
```

### 1.3 模块与导入

**规则 R5：禁止为"转发"而创建只含 re-export 的兼容模块。** 教训（存量已消化）：`integration_kb/pipeline/chunker.py` 等 6 个纯转发文件曾零引用存在，2026-11-02 随 integration 模块整体删除；确需过渡期保留兼容层时必须加 `warnings.warn(DeprecationWarning, ...)` 并登记清理期限。另注意：删除模块时必须同步清理全部引用方（本次删除遗留 7 处断裂 import，见优化报告 〇-A.3）。

**规则 R6：依赖方向必须单向**：`modules/* → core → common`，禁止 core 反向 import 业务模块（存量整改：`core/router_class.py:148`）、禁止并列业务域互相 import。跨域复用代码一律上移到 `core/`（教训：`kb/publication/service.py` 曾引 `integration_kb` 的 `validate_embedding`，模块删除后变成断裂 import——`core/rag/vector_store.py:117` 本就有同名函数，当初应直接引 core）。

```python
# ❌ core 反向依赖业务模型，形成循环依赖（靠延迟导入掩盖）
from app.modules.system.api_log.model import SystemApiLogModel  # inside app/core/

# ✅ 横切能力通过依赖注入接收写入函数，core 不认识任何业务模型
def register_audit_writer(write: Callable[[ApiLogRecord], Awaitable[None]]) -> None: ...
```

**规则 R7：禁止在模块导入时执行副作用**（如 `core/logger.py:92` 在 import 时执行 `setup_logger()`）。初始化动作放到 `lifespan`。

### 1.4 死代码与文档一致性

**规则 R8：删除死代码胜过注释它。** 无调用点的函数、模板项目残留（`common/constant.py` 的代码生成器常量、`require_superadmin` 等）直接删除，git 可找回。

**规则 R9：docstring 是契约。** `get_or_404` 写"HTTP 404"就必须返回 404；"自动填充审计字段"就必须真的填充。review 时 docstring 与行为不一致按 bug 处理。

**规则 R10：超长函数（>80 行）与超长文件（>500 行）需在 review 中说明理由或拆分**。编排函数（lifespan、pipeline 节点）优先拆分为"步骤函数列表 + 统一执行器"模式。

### 1.5 同步阻塞

**规则 R11：async 函数内禁止出现同步阻塞调用**（`requests`、`time.sleep`、同步文件 IO、同步 SDK）。阻塞调用必须显式指定线程池：

```python
# ❌ 默认执行器不可控，解析占满后会拖慢同用默认执行器的审计落库
document = await asyncio.to_thread(parse_document, path)

# ✅ 解析与 IO 分池（解析/IO 专用线程池收口在 core，如 app/core/executor.py；
#    教训：runtime/executor.py 原放在 integration_kb，随模块删除丢失，大文档解析分池需重建时放 core）
document = await run_in_parse_pool(parse_document, path)
await storage.put_file(...)  # 内部走 run_in_io_pool
```

### 1.6 日志

**规则 R12：统一使用 `from app.core.logger import logger`（loguru）**，禁止模块内自建标准库 logger（存量整改：`core/chat/streaming.py:18`）。清理失败必须 `logger.exception`，禁止静默 `pass`。

## 2. FastAPI 开发规范

### 2.1 路由与分层

**规则 F1：严格分层 controller → service → crud → model，禁止越层。**

- controller：参数解析 + 调 service + 包响应，**禁止**出现 `select/execute/db` 操作；
- service：业务编排，**禁止**手写 ORM 语句绕过 CRUD（存量整改：space/category/session/stats service 共 10+ 处裸 SQL）；需要批量/条件更新时给 `CRUDBase` 补方法（`update_by_condition` 返回 rowcount）；
- crud：数据访问，**禁止**包含业务判定（存量整改：`task/crud.get_latest_by_doc` 里"取最新一条"属于业务语义，且实现是全量取出取第一条）。

```python
# ❌ service 裸写 update，不查 rowcount，记录被删时接口静默成功
await self.db.execute(update(MessageModel).where(id == mid).values(feedback=fb))

# ✅ 下沉到 CRUD，带 rowcount 校验
updated = await self.message_crud.update_by_condition(
    where=[MessageModel.id == mid], values={"feedback": fb}
)
if updated == 0:
    raise CustomException(msg="消息不存在", status_code=404)
```

**规则 F2：新路由统一登记到 `app/api/v1/routers.py` 的 `DOMAIN_CONTROLLERS` 总表**，禁止在业务模块里散落 `include_router`。

**规则 F3：SSE/长连接路由不注入请求级 db 依赖**（事务横跨流生命周期会长期占用连接）；流内的 DB 访问用短会话，且**读会话在最后一次查询后立即关闭**（教训：已删除的 `integration_chat/service.py:46` 曾让会话贯穿 90s 流——#14 问答链路重建时强制遵守）。

### 2.2 依赖注入

**规则 F4：请求级资源（db session）只通过 `Depends(db_getter)` 注入；后台/流程内资源显式创建并注释原因。**

**规则 F5：LangChain 客户端等进程级资源用单例 + lifespan 管理，禁止每请求实例化**（存量整改：`EmbeddingClient()` 在 5 处每请求新建，底层 `httpx.AsyncClient` 从不关闭）：

```python
# ❌ 每请求新建外壳与连接池，缓存随对象丢弃，句柄泄漏
vector = await EmbeddingClient().embed_query(text)
stream = LlmClient(timeout=settings.KB_LLM_TIMEOUT).stream_chat_events(...)

# ✅ 进程级单例，生命周期跟随应用，关停统一 aclose()
from app.core.clients import get_embedding_client, get_llm_client
vector = await get_embedding_client().embed_query(text)
```

**规则 F6：同一请求体只解析一次。** 需要多个依赖读取 body 时，第一个解析后存 `request.state`，后续依赖复用（存量整改：契约链路同一 body 被 `json.loads` 4 次）。

### 2.3 错误处理

**规则 F7：统一响应出口。** JSON 接口一律返回 `SuccessResponse`/`ErrorResponse`；异常统一交给 `app/core/exceptions.py` 的全局 handler，业务代码只负责抛带状态码的 `CustomException` 或领域异常。

**规则 F8：契约层（`ContractApiRoute`）把异常转成错误响应时，必须保证请求级事务回滚**（存量整改：报告 P0-1）。新增横切标记（如 `contract_failed`）必须在写它的同一 PR 里确保有读取方，禁止"只写不读"的隐式契约。

**规则 F9：错误码收敛一套**：成功 `0`，客户端错误 4xx 段，服务端错误 5xx 段；禁止混用 `RET` 中的 1/-1/200/201（存量整改）。

### 2.4 数据校验（Pydantic）

**规则 F10：入参出参一律用 Schema 校验，禁止 controller 手工拆字段。**

**规则 F11：同一张表禁止两份语义不一致的 Schema**（教训：已删除模块中 `MessageCreateSchema` role 是 int、`MessageOutSchema` role 是 str，靠手工字段搬运转换）。入参用领域语言（`Literal["user","assistant"]`），出参转换用 `model_validate` + validator，不写逐字段搬运：

```python
# ❌ 12 个字段手工搬运，新增列必漏
payload = {name: getattr(obj, name) for name in MessageOutSchema.model_fields if hasattr(obj, name)}
payload["role"] = ROLE_LABEL.get(obj.role, "assistant")

# ✅ 出参统一验证转换
class MessageOutSchema(BaseModel):
    role: str
    @field_validator("role", mode="before")
    @classmethod
    def _role(cls, v): return {1: "user", 2: "assistant"}.get(v, v)

msg = MessageOutSchema.model_validate(obj)
```

**规则 F12：继承要克制。** 禁止"为了省字段"让流式请求继承会话创建请求（教训：已删除的 `ChatStreamInSchema` 继承 `SessionCreateSchema` 导致 title/scope 语义稀释）；公共字段抽显式基类。

**规则 F13：枚举状态文案由枚举自身提供 `label` 属性**，禁止在 service/stats 里另维护一份 `{0: "待解析", ...}` 字典（存量整改：4 处映射）。

## 3. 数据库表结构设计规范

> 本项目数据库为 **PostgreSQL 16 + pgvector**，明确不支持 MySQL（删除 MySQL 兼容分支）。当前阶段不使用数据库迁移，表结构由各域启动期 bootstrap 幂等建表（`checkfirst`，只补缺表）。

### 3.1 命名

**规则 D1：统一命名约定，在 `MappedBase.metadata` 设置 `naming_convention`**（存量整改：当前未设置，`uq_` 前缀误用于 `Index(unique=True)`，会造成 `ON CONFLICT` 语义陷阱）：

| 对象 | 前缀/格式 | 示例 |
|---|---|---|
| 表名 | `sbp_ai_<域>_<实体>`，实体**单数** | `sbp_ai_kb_publication` |
| 主键 | `pk_<表名>` | `pk_sbp_ai_kb_publication` |
| 唯一约束 | 用 `UniqueConstraint`，名 `uq_<表名>_<列>` | `uq_sbp_ai_kb_chunk_rec_seq` |
| 普通索引 | `ix_<表名>_<列>` | `ix_sbp_ai_kb_chunk_pub_rev` |
| 外键 | `fk_<表名>_<列>` | — |
| CHECK | `ck_<表名>_<规则>` | `ck_sbp_ai_kb_pub_rev_positive` |

**规则 D2：时间列统一后缀 `_at`**（`created_at/updated_at/deleted_at/expires_at`），存量 `_time` 表保留但新表禁用；`BaseQueryParam` 同时支持两种后缀。

**规则 D3：状态列统一 `String(20)` + 应用层 `StrEnum`**，禁止 int 状态与 str 状态混用（存量整改：`status` 一半 int 一半 varchar）；关键状态机列补 CHECK 约束：

```python
status: Mapped[str] = mapped_column(
    String(20), server_default="queued", nullable=False,
    comment="状态 queued/running/succeeded/failed",
)
__table_args__ = (
    CheckConstraint("status IN ('queued','running','succeeded','failed')", name="ck_parse_job_status"),
)
```

### 3.2 字段类型与默认值

**规则 D4：默认值必须落在数据库侧**（`server_default`），时间列用 `server_default=func.now()` + `onupdate=func.now()`（存量整改：全库默认值只在 Python 侧，裸 SQL/ETL 插入即报 NOT NULL，批量 update 还得手写时间戳）。

**规则 D5：结构化数据用 JSONB，不用 TEXT 存 JSON 字符串**（存量整改：`task_step.detail` 用 Text 存 JSON，出参靠 validator 兜底解析）。**JSONB 列若参与过滤/聚合，必须建 GIN 索引**（`jsonb_path_ops`）：

```python
# ✅ 会被按成员/键过滤的 JSONB 列
__table_args__ = (Index("ix_kb_chat_msg_deps_gin", "knowledge_deps", postgresql_using="gin",
                        postgresql_ops={"knowledge_deps": "jsonb_path_ops"}),)
```

**规则 D6：数值存数值类型，禁止 `String` 存数字**（存量整改：`api_log.process_time String(20)` 存毫秒，无法聚合排序）。

**规则 D7：向量列维度与配置联动，模型注释必须写明"换维度需手写 SQL 重建表 + 重建 HNSW"**，并增加启动期维度自检（存量整改：模型用 `settings.VECTOR_DIM`、迁移硬编码 1024，换模型后静默写失败）。

### 3.3 主键、外键与关联

**规则 D8：每表一个对外身份标识。** 自增 `id` 做主键 + `uuid` 做外部标识是允许的上限，禁止三重身份（存量整改：`publication` 同时有 `id` PK + `uuid` UNIQUE + `publication_id` UNIQUE）。

**规则 D9：关联关系三种口径中选一种并全项目统一（推荐：逻辑外键 + 应用层事务内保证）**，且必须在列 comment 写明指向：

```python
# ✅ 逻辑外键必须注明指向
publication_id: Mapped[str] = mapped_column(
    String(64), nullable=False, comment="关联 sbp_ai_kb_publication.uuid（逻辑外键）",
)

# ❌ 裸列无注释无指向，删除父记录后孤儿数据无人清理
record_id: Mapped[str] = mapped_column(String(64), nullable=False)
```

若选物理外键（如同库强关联的 message→session），用 `ondelete="CASCADE"` 即可，`onupdate="CASCADE"` 在 PG 中无实际语义不要写；且**禁止物理外键与应用层补偿删除双保险并存**（存量整改）。

**规则 D10：冗余计数字段要么有事务内一致性保障，要么删掉改 JOIN 聚合**（存量整改：`space.doc_count` 从未被写入，列表页恒为 0）。

**规则 D11：一个业务状态机只有一个事实源。** 同一次解析的状态禁止在 document/task/task_step 三表各自存一份再靠映射表对齐（存量整改）；派生状态用函数计算（如 `to_pipeline_status(task_status)`），不落列。

### 3.4 索引

**规则 D12：索引按查询建，不按模板建。** `ModelMixin` 目前给每张表强加 4 个索引，其中单列 `id`（主键自带）、单列 `is_deleted`（布尔低选择性）、与复合索引前缀重复的 `created_time` 均属浪费（存量整改，如 `sbp_ai_kb_chat_message` 8 个索引中 4 个无价值）。新表索引清单必须能回答"哪个查询用它"。

**规则 D13：以下字段默认建索引**：高频过滤外键（`request_id/biz_id/publication_id/doc_id`）、状态+时间组合（轮询用）、过期时间（`expires_at`，供清理扫描）。`LIKE '%x%'` 前缀通配查询不走索引，需要时用 pg_trgm 或改前缀查询。

**规则 D14：唯一约束与查询维度对齐**。查重字段（如 `content_hash`）如果参与业务查询必须建索引。

### 3.5 迁移管理

**规则 D15：当前阶段不使用数据库迁移。** 模型是唯一事实源：空库由各域启动期 `bootstrap` 幂等建全表；`create_missing_tables` 只补缺失表，禁止依赖它补列/改类型/加索引。

**规则 D16：表结构变更必须空库可建通。** 新增表或改列时，确保全新空库能由启动期建表得到与模型一致的完整结构；禁止出现"必须先跑某段 SQL 才能建表"的隐式前置。

**规则 D17：存量库的结构变更走手工 SQL。** 补列、改类型、改索引必须写成显式 SQL 脚本并随发布评审，禁止只改模型就上线（存量库不会自动补列）。

## 4. LangChain 与 LangGraph 使用规范

### 4.1 组件封装

**规则 L1：LLM/Embedding/Rerank 客户端统一走 `app/core/clients/`，进程级单例，禁止业务模块自行实例化**（对应规则 F5）。新增 provider 时继承 `BaseHttpClient`，获得统一的超时、退避重试（仅 429/5xx）、内网直连、错误归一。

**规则 L2：重试口径按组件声明**：Rerank 快速失败（`max_retries=1`，精排宁可失败不拖流）；LLM 走 LangChain `max_retries`；**Embedding 必须显式配置重试**，批量向量化失败要能与流水线续跑快照衔接（存量整改：当前无显式重试，灌库中途失败即中断）。

**规则 L3：一个能力只允许一个实现。** 禁止"core 一份、业务模块一份"的同名函数并存（教训：`parse_and_chunk/process_document` 曾两套完整流水线并存且已分叉——2026-11-02 integration 侧删除后，`core/rag/pipeline.py` 成为唯一实现，规则以它为准）。迁移期过渡必须留 `DeprecationWarning` 与清理期限。

```python
# ❌（历史教训）同名函数两个包都能 import，语义不同且已分叉
from app.core.rag import process_document                      # 线性版（曾为零调用死代码）
from app.modules.integration_kb.pipeline import process_document  # LangGraph 版（已删除）

# ✅ core/rag/__init__ 只导出真正被复用的通用函数，业务层从唯一实现导入
from app.core.rag import parse_and_chunk, supported_suffixes
```

**规则 L4：MinerU 等重客户端直接支持 bytes/路径入参**，禁止"内存 bytes → 临时文件 → SDK"的多余拷贝（存量整改）。

### 4.2 Prompt 管理

**规则 L5：运行时 prompt 集中在 `prompt.py` 单一模块，带 `PROMPT_VERSION` 常量。** `prompt_template` 表与代码 prompt 二选一：要么接入表读取（进程内缓存 + 版本兜底），要么删表并在 ADR 记录"prompt 随代码版本管理"（现状：原硬编码 prompt 随 integration 模块删除，`system/prompt_template` 表空置——#14 重建时必须先做这个二选一）。

### 4.3 状态（State）管理

**规则 L6：Graph State 用 `TypedDict(total=False)`，只放可序列化的业务数据；`Request/AsyncSession/db` 等请求级依赖放 `config["configurable"]` 或闭包，禁止进 state**（历史教训：已删除的 `ChatState` 曾混入 `Request/AsyncSession`，一旦挂 checkpointer 立即崩溃——#14 重建时强制遵守）：

```python
# ❌ 不可序列化对象混入 state
class ChatState(TypedDict, total=False):
    request: Request
    db: AsyncSession
    question: str

# ✅ state 只含业务数据；依赖经 configurable 注入
class ChatState(TypedDict, total=False):
    question: str
    hits: list[KnowledgeHit]
    answer: str

graph.invoke(state, config={"configurable": {"db": db, "client_ip": ip}})
```

**规则 L7：会被多个节点写入的键必须声明 Reducer（`Annotated[list[X], operator.add]`）；单写键不加。** 路由分支禁止"约定式"——节点间用隐式 `route` 字符串中转（历史教训：曾 4 个节点隐式写 `route`，忘写时静默 fallback 到 abort），改用条件边函数直接判定并 `Literal` 标注。

**规则 L8：`Literal` 常量、阶段枚举与库表枚举对齐**：图内阶段枚举与节点一一对应，禁止一个节点覆盖两个阶段（历史教训：`index_node` 曾覆盖 EMBED+WRITE，导致续跑粒度与注释承诺不符）。

### 4.4 图编排模式

**规则 L9：图定义编译一次、模块级缓存；禁止每次执行重编译**（历史教训：原文档流水线每次 `process_document` 都重编译）：

```python
# ✅ 模块级缓存编译结果（每次调用返回同一张图）
@lru_cache(maxsize=1)
def _build_graph() -> CompiledStateGraph:
    builder = StateGraph(ChatState)
    ...
    return builder.compile()
```

**规则 L10：节点只做编排；产物落盘、快照、通知等副作用抽独立函数**（如 `persist_artifacts`、`pipeline/snapshot.py`），节点函数体超过 ~40 行即拆分。

**规则 L11：checkpoint 与业务快照二选一作为续跑状态源**（历史教训：曾 PostgresSaver 全量 state 落库 + S3 快照双状态源，MB 级冗余且可能不同步；`core/rag/checkpointer.py` 现为零消费者空转，#14 重建前建议下线）。推荐：checkpoint 只存 `{bundle_key, 各节点摘要}`；或不挂 checkpointer，纯用 `resume_from` + 对象存储快照。

**规则 L12：节点失败必须能定位阶段**：异常携带节点信息（自定义 `PipelineNodeError(stage, cause)`），禁止靠回调副作用更新 `state["stage"]` 推断失败位置。瞬时错误（429/5xx/网络）在 worker 层做 2–3 次指数退避，pipeline 保持纯函数。

**规则 L13：问答图（无 checkpointer）与文档流水线图（挂 checkpointer）的差异必须写在图定义 docstring 中**，包括不挂的理由。

### 4.5 流式输出（SSE）

**规则 L14：流式统一走 `core/chat/streaming.iter_stream` + `utils/sse.format_sse`**：首字超时与空闲超时分离、每 20 帧探测断连、异常折算收尾帧（error + done），保证前端永远收到收尾帧。

**规则 L15：终止分支也要落库成对消息**：拒答/异常路径给 assistant 落占位消息（或标记 user 消息 aborted），禁止留下"有问无答"的悬空历史污染下一轮上下文（历史教训：原 `_abort` 不落库）。

**规则 L16：整条流式链路有总 deadline**：检索 + 重排纳入同一 `asyncio.timeout` 或基于起始时间的剩余预算控制（历史教训：超时曾只覆盖 retrieve）。

### 4.6 RAG 链路

> 现状说明（2026-11-02）：integration 检索/问答链路已删除，`core/rag/vector_store.py` 的 search/upsert 当前零调用方；`kb` 域的 `sbp_ai_kb_chunk`（自带 vector 列）是唯一分片存储。本章规则为 #07/#14 在 kb 域重建时的强制要求。

**规则 L17：检索策略（上架/完成状态过滤、top_k、min_score）以 `metadata` 字段进向量库过滤层实现，禁止召回后应用层循环过滤再静默丢弃**（历史教训：曾 top_k=20 召回后过滤无回补，有效召回率被降低）。

**规则 L18：`top_k/min_score` 基础设施层默认 `None`，强制调用方显式传**（历史教训：三处默认值不一致，忘传只回 10 条）。

**规则 L19：向量库 metadata 键名必须来自白名单常量**，禁止 f-string 直接拼键名进 SQL（存量整改：`core/rag/vector_store._where_sql` 靠注释约束）；`min_score` 的量纲（`1 - cosine_distance`，[0,2]）写入 settings 描述。

**规则 L20：向量化行组装只允许一个实现**（`core/rag/pipeline.build_embedding_rows` + `field_map`），禁止业务模块手写 `zip(chunks, vectors)` 自算 hash（历史教训：kb 域曾出现第三份实现）。

## 5. 测试与评审基线

**规则 T1：`app/core/` 与各 service 的公开方法必须有最小回归测试**；修复 P0 级 bug 时必须先补暴露该 bug 的测试用例。

**规则 T2：涉及 DB 的测试在 CI 必须真实跑**——数据库不可达时跳过会制造"永远绿"的假象；用 docker service 或 testcontainers 保证。

**规则 T3：CR 提交前自查清单**：
1. 是否有零引用新文件 / 复制粘贴的重复逻辑（≥2 份即要求收编）？
2. 是否有 `except Exception` 包装翻译、默认 500、裸 SQL 越层？
3. 新表/新列是否过 §3 规范（命名、索引、server_default、JSONB+GIN）？
4. 图节点是否可序列化 state、是否有 Reducer 声明、阶段与枚举是否对齐？
5. async 路径是否引入了新的同步阻塞或每请求新建的客户端？
6. **删除模块/文件时：是否全仓 grep 清理了所有 import 方与引用方（含测试、前端、脚本、lifespan、配置注释）？** 并在合并前**实跑一次**启动与构建（后端 `TestClient(create_app())` 走完 lifespan、前端 `npm run build`）——只做静态 grep 会漏掉 lifespan 里的延迟 import 与 `.env` 里的孤儿配置。（历史教训：integration 模块删除遗留 7 处断裂 import + lifespan 五段失效初始化 + 前端断裂 re-export，直到复评才被发现，见优化报告 〇-A.3/A.5）
7. 本轮修复/删除留下的**能力空缺是否已登记**（ADR 或文档中的"能力回退清单"）？避免下一个人以为功能还在。
