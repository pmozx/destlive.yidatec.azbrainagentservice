## 一、文档目的与总则

### 1.1 目的

1. 给出 **`sbp_ai_[模块名]_[业务名]` 表命名强规范**（本文 §二）；
2. 说明 **AI 服务与 GSI 共用 `service_brain` 库（public schema）** 下的数据治理规则（§三）；
3. 定义 AI 服务四个模块域的职责边界与全部数据表设计（§四–§八）；
4. 给出开发必须遵守的设计约束清单（§十二）。

### 1.2 适用范围

适用于 AI 服务后端全部数据对象的创建与变更。GSI 侧 93 张表不在本文设计范围，仅作为引用方（§九）。

### 1.3 三方一致原则

**目录名 = 表前缀 = 类名前缀**。例如目录 `app/modules/kb/` 下管理 `sbp_ai_kb_*` 表，模型类 `KbChunk` ↔ 表 `sbp_ai_kb_chunk`。新增模块必须先在 `app/modules/__init__.py` 登记映射。

**例外：GSI 外部只读表**。`sbp_*`（无 `ai` 段）表由 GSI 侧维护，不属于 AI 模块码体系：统一放在 `app/modules_gsi/<模块名>/<业务名>/`，模型 / CRUD / Service / Controller 类名以 `Sbp` 开头（如 `SbpSysOrgModel` ↔ `sbp_sys_org`），只读且不建表，不登记 `app/modules/__init__.py`。

## 二、命名与设计规范（强规范）

### 2.1 表命名

```
sbp_ai_[模块名]_[业务名]
 │    │    │       └─ 业务名：小写英文，多词用下划线，≤3 个词（如 chat_session）
 │    │    └─ 模块名：见 2.2 模块码表
 │    └─ AI 服务固定段（区别于 GSI 的 sbp_ 前缀）
 └─ 服务大脑项目统一前缀（与 GSI 同库同 schema，前缀即边界）
```

规则：

| # | 规则 | 正例 | 反例 |
| --- | --- | --- | --- |
| 1 | 全小写 + 下划线，禁用驼峰/连字符 | `sbp_ai_kb_chunk` | ~~`sbp_ai_KBChunk`~~ |
| 2 | 模块名必须取自 §2.2 模块码表，禁止私设 | `sbp_ai_voice_rule` | ~~`sbp_ai_qc_rule`~~ |
| 3 | 表名总长 ≤ 63 字节（PostgreSQL 限制） | — | — |
| 4 | 关联表用两个业务名拼接，语义主在前 | `sbp_ai_kb_chat_message`（从属会话） | — |
| 5 | 禁止使用保留字（`order`、`user`、`desc` 等）作表名/列名 | `sbp_ai_voice_review` | ~~`ai_user`~~ |

### 2.2 模块码表

| 模块码 | 中文名 | 职责 | 表数量 |
| --- | --- | --- | --- |
| `system` | 系统与接入 | 统一日志审计（含安全头校验扩展）、nonce 防重放、幂等台账、请求台账、提示词模板、授权缓存 | 6 |
| `kb` | 知识平台 | 文档/FAQ 解析、发布单元与版本、切片与向量、会话与消息、重复治理 | 8 |
| `voice` | 语音质检 | 质检规则与版本、质检任务与结果、报告快照、Findings、复核申诉、评估集 | 8 |

>
> **`kb` 域的向量层 2 张（v1.2，2026-11-02）**：`sbp_ai_kb_vector_collection` / `sbp_ai_kb_vector_embedding` 挂在 `kb` 模块码下，
> 但**不是 ORM 模型**——没有 `__tablename__` 声明，不进 `bootstrap.py` 建表清单，由 `app/core/rag/vector_store.py`
> 用原生 SQL 懒建，因此上表 `kb` 计数仍为 8。全量 AI 表数 = 21 张 ORM 表 + 2 张向量层 = **23 张**（见 §4.1；v1.4 合并 `entry_meta` 后由 24 降为 23）。
>
> **`gsi` 不是 AI 模块码（v1.3，2026-11-02）**：`app/modules_gsi/` 只承载 GSI 外部只读表（`sbp_sys_*` / `sbp_km_doc*`），
> 不占用上表模块码，也不参与 `bootstrap.py` 建表。目录按「模块名 / 业务名」两级组织，类名统一 `Sbp` 前缀，
> 只读接口登记在 `/api/v1/gsi`。

### 2.3 字段规范

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 主键 | `id` int8 自增（ModelMixin 内置），对外一律不暴露 | — |
| 对外标识 | `uuid` varchar(64)（ModelMixin 内置，唯一）；契约中的 `job_id`/`session_id`/`message_id`/`request_id`/`group_id` 等一律使用该列值 | `session_id = uuid` |
| GSI 引用 | 引用 GSI 数据时按其类型对齐：`user_id` int8（`sbp_sys_user.id`）；`publication_id`/`record_id` varchar(64)（`sbp_km_doc_publication.id` / `sbp_km_doc_record.id`） | 见 §九 |
| 布尔 | `is_` 前缀 | `is_enabled` |
| 时间 | `*_time` 后缀，timestamptz，**库内统一 UTC，契约输出按手册口径**（见 §2.6） | `created_time` |
| JSON | jsonb，`*_meta`（元数据）/`*_results`（结果集）/复数语义后缀 | `rule_results` |
| 向量 | `embedding vector(1024)`，仅 `chunk` 表允许 | — |
| 枚举 | varchar + 取值域注释，禁止魔法数字 | `status: queued/running/...` |

### 2.4 公共字段组（ModelMixin，业务表强制继承）

`backend/app/core/base_model.py`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int8 PK 自增 | 内部主键 |
| `uuid` | varchar(64) 唯一 | 对外标识 |
| `created_time` | timestamptz | 创建时间（默认 now()） |
| `updated_time` | timestamptz | 更新时间（自动更新） |

**不做软删除（v1.7 决策）**：Mixin 不提供 `is_deleted` / `deleted_time` / `deleted_id`，`CRUDBase.delete()` 一律物理删、`restore()` 已移除。原因是基座猜不出"该不该留痕迹"——`kb_chunk` 必须物理删（软删的向量仍会被检索召回，违反 #06），`kb_revision` 要留墓碑（删除事件本身必须可查）。留痕迹是领域知识，由业务自己用 `status` 表达（如 `archived`），而不是让基座提供一个语义模糊的开关。

Mixin 也不再统一注入了 `(status, is_deleted)` / `(created_time, is_deleted)` 两个复合索引（软删列消失后它们会退化成单列索引）。`created_time` 自带单列索引已覆盖时间排序；需要「按状态筛 + 按时间排」的表自行声明 `(status, created_time)`。**继承该 Mixin 的表必须自带 `status` 列**；纯技术台账（如 nonce）可不继承 Mixin，但仍须遵循命名规范并至少有 `created_time`。

### 2.5 索引与约束命名

| 对象 | 命名 | 示例 |
| --- | --- | --- |
| 普通索引 | `ix_{表名}_{列1}_{列2}` | `ix_sbp_ai_kb_chunk_record_revision` |
| 唯一索引 | `uq_{表名}_{列1}_{列2}` | `uq_sbp_ai_system_nonce_client_nonce` |
| 外键约束 | `fk_{表名}_{引用表}`（外键仅限 AI 自有表之间，**禁止外键指向 GSI 表**） | `fk_sbp_ai_kb_chunk_publication` |
| 检查约束 | `ck_{表名}_{语义}` | `ck_sbp_ai_kb_chunk_seq_positive` |

### 2.6 时间与状态口径

- 库内时间统一 `timestamptz` 存 UTC；契约字段按手册（授权用毫秒时间戳、会话用 ISO 8601，差异已列入需求 §十二-8 待确认）；
- 状态机取值域在表注释中完整枚举，禁止代码硬编码字符串散落（统一走常量模块）；
- 删除一律物理删（基座不做软删，见 §2.4）；删除行为的可追溯性由 `api_log` 审计行与契约幂等台账承担，而不是靠"行还在库里"来证明。契约要求的幂等墓碑（§六-2.3）是**保留行**的硬数据（`status='archived'`），不参与清理。

### 2.7 建表与变更规范

- AI 侧不使用迁移工具：各业务域在 `backend/app/modules/<域>/bootstrap.py` 声明表，应用启动期由 `core/table_bootstrap.py` 的 `create_missing_tables` 做 checkfirst 幂等建表（**只补缺表，已存在的表一律跳过**——不补列 / 不改类型 / 不加索引 / 不补默认值）；
- 因此存量库的结构变更**必须由提交者写出 `ALTER` 语句**并随 PR 交付（放 `backend/sql/` 或 PR 描述），在目标环境显式执行。表级索引（含 `text()` 表达式索引）写在模型 `__table_args__` 里，新建库随建表自动建出，存量库需自己 `CREATE INDEX`；
- 删列 / 改类型 / 删索引等破坏性变更必须人工确认、提供数据备份与回滚说明后手动执行，没有任何脚本会自动做；
- 向量维度（1024）相关变更视为**重大变更**，需评审（ADR-4）。

## 三、数据库归属与治理

### 3.1 归属

| 项 | 值 |
| --- | --- |
| 数据库 | `service_brain`（与 GSI 共用实例与库） |
| Schema | `public`（与 GSI 同 schema，**前缀隔离**） |
| AI 表前缀 | `sbp_ai_`（GSI 表为 `sbp_` 无 `ai` 段，二者命名空间不相交） |
| AI 建表方式 | 应用启动期各域 bootstrap 幂等建表（checkfirst，只补缺表）；无迁移版本表 |
| GSI 迁移工具 | Flyway（版本表 `flyway_schema_history`） |

### 3.2 账号与授权（DBA 执行，上线前核验）

| 账号 | 权限 |
| --- | --- |
| AI 应用账号 | `sbp_ai_*` 表 DDL（迁移期）/ DML；8 张共享表**只读**且仅限指定字段 |
| GSI 应用账号 | 维持现状，**不得**拥有 `sbp_ai_*` 的写权限（如需读 AI 回执数据走接口，不走库） |

### 3.3 GSI 共享表（只读，AI 权限计算与知识对齐的唯一数据源）

| 表 | 允许读取的字段 | AI 用途 |
| --- | --- | --- |
| `sbp_sys_org` | id, parent_id, name, code, type, category, source_org_id, status, deleted | 组织层级与分类（`category` 区分 admin / business）；上下级不自动继承知识权限 |
| `sbp_sys_org_member` | org_id, user_id | 用户 ↔ 组织归属（不代替受众团队成员关系） |
| `sbp_sys_audience_team` | id, group_code, group_name, audience_team, status, deleted | 受众团队（仅 `status=1` 且 `deleted=0` 有效；新写入用 `group_code`） |
| `sbp_sys_audience_team_member` | team_id, user_id | 用户 ↔ 受众团队归属（按签名 `user_id` 查询，不用姓名） |
| `sbp_sys_user` | id, status, deleted, allow_login | 签名身份 → 用户有效性与登录状态；**不授予** `password_hash`、邮箱、手机号等无关列 |
| `sbp_km_doc_publication` | id, doc_id, team, record_id, index_status, updated_at | 知识按团队生效关系；`record_id` 指向当前生效快照，`index_status` 不能单独作为授权依据 |
| `sbp_km_doc_record` | id, doc_id, stage, status, snapshot_json | 当前生效快照（回答正文来源）；`snapshot_json` 的 `invisibleTeams` / `expireAt` 决定拒绝范围与有效期 |
| `sbp_km_doc` | id, title, status, doc_type, domain, team, expire_at, knowledge_no, deleted | 知识元数据（手册原始字段行损坏，只映射权限判断与展示所需列；正文以 `doc_record.snapshot_json` 为准） |

**只读纪律**：AI 侧代码中引用这些表的 ORM 模型必须标注只读；任何写操作在代码评审与数据库层双重拒绝（DR-04）。

**代码落点**：统一放在 `backend/app/modules_gsi/<模块名>/<业务名>/`，按 `model / crud / schema / service / controller` 五层组织，类名以 `Sbp` 开头（如 `SbpSysOrgModel` / `SbpSysOrgCRUD` / `SbpSysOrgService` / `SbpSysOrgRouter`）。基类 `SbpBase` / `SbpReadCRUD` 使用独立 metadata，**不登记 `app/modules/__init__.py`、不进入 `app/bootstrap.py` 建表清单**；只读接口挂在 `/api/v1/gsi`（`DOMAIN_CONTROLLERS["/gsi"]`），共 8 张表 / 13 条 GET。

### 3.4 Flyway / 启动期建表分治

1. 双方互检：GSI 的 Flyway 脚本不得出现 `sbp_ai_` 对象；AI 的 bootstrap 建表与手工 SQL 不得出现非 `sbp_ai_` 对象的 DDL；
2. `public` schema 下 DDL 权限按账号收敛（AI 账号无权创建非 `sbp_ai_` 前缀表——通过默认权限 + 流程评审保证）；
3. 索引膨胀与统计信息：共库实例下 AI 侧大表（chunk/审计）的 VACUUM/ANALYZE 纳入 DBA 例行任务清单（§十一）；
4. GSI 共享表的结构由 GSI 侧 Flyway 维护，AI 侧 `modules_gsi` 只做只读映射，不生成任何 DDL；其独立 `SbpBase.metadata` 不参与 `app/bootstrap.py` 建表。

## 五、system 模块（系统与接入）

### 5.1 模块说明

承接 `02-项目需求.md` 的 FR-INT / FR-AUD 横切需求：签名鉴权后的**审计留痕、防重放、幂等、超时结果查询、提示词版本化、授权缓存**。对应代码目录 `app/modules/system/`。

### 5.2 sbp_ai_system_api_log（统一接口日志审计）★ 扩展

**用途**：全部 `/v1/*` 与 `/api/v1/*` 调用的统一审计流水；本期扩展 HTTP 安全头校验留痕（FR-AUD-01~04）。
**现状**：表已存在于代码（`app/modules/system/api_log/model.py`），本设计在其上扩展 4 列。

业务字段（既有，略列）：

| 字段 | 类型 | 说明 |

**新增列（本期扩展）**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| auth_mode | varchar(8) | `jwt` / `hmac`；区分管理端与契约调用 |
| client_id | varchar(64) | HMAC 调用方标识（`X-AI-Client`） |
| request_id | varchar(64) | 契约追踪 ID，与应用日志双源关联（NFR-O-01） |
| security_check | jsonb | 安全头校验明细，结构见下 |

`security_check` JSONB 结构：

```json
{
  "headers_present": ["X-AI-Client","X-AI-Timestamp","X-AI-Nonce","X-AI-Signature"],
  "timestamp_deviation_ms": 1234,
  "nonce_state": "first_use | reused",
  "signature_result": "passed | failed | skipped(jwt)",
  "signature_digest": "ab12cd34...wxyz",   // 前8+后4位，禁存全量
  "failure_code": "SIGNATURE_EXPIRED"       // 通过时为 null
}
```

**索引**：`ix_sbp_ai_system_api_log_path_created(request_path, created_time)`、`ix_sbp_ai_system_api_log_username(username)`、`ix_sbp_ai_system_api_log_client_created(client_id, created_time)`、`ix_sbp_ai_system_api_log_request_id(request_id)`、`ix_sbp_ai_system_api_log_created_time(created_time)`（Mixin 单列索引），以及 `security_check` 的两条表达式索引（`(security_check->>'signature_result')` / `(security_check->>'nonce_state')`，服务等值过滤）。

**设计要点**：
1. 被拒请求（401/409）同样落审计，`response_code` 记实际码，`security_check.failure_code` 记原因——安全取证不依赖业务日志（ADR-13）；
2. 审计写入独立会话、异步执行，失败转应用日志，不阻断主请求（FR-AUD-05，NFR-P-06）；
3. `X-AI-Signature` 仅存摘要、nonce 全量留存（重放取证）；请求/响应体沿用脱敏与截断（FR-AUD-04/06）。

承接 FR-QC / FR-RPT / FR-OPS（质检部分）：规则配置、四类判定并行执行、计分、四层报告、复核申诉、评估集。对应代码目录 `app/modules/voice/`。**输入是 GSI 提供的转写文本**（ASR 不在本侧），录音原文件不得入库（DR-07）。

### 7.2 sbp_ai_voice_rule（质检规则）

**用途**：FR-QC-02/06：规则配置主表。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id / uuid / 时间组 / status | — | ModelMixin；`status` = `draft / active / retired` |
| rule_code | varchar(64) 唯一 | 规则编码 |
| name | varchar(200) | 规则名称（六段式之首） |
| category | varchar(50) | 一级缺陷分类（映射分类树，FR-QC-08） |

| params | jsonb | 判定参数（关键词表、正则、阈值、枚举与字段映射） |
| score | int4 | 分值（正扣分/负加分） |
| priority | int4 | 优先级（前置不成立短路，§7.5 说明） |
| knowledge_ref | jsonb | 知识依据（知识一致性类规则的知识锚点） |

### 7.4 sbp_ai_voice_qc_job（质检任务）

**用途**：一通通话的判定任务状态机。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id / uuid / 时间组 / status | — | ModelMixin；`status` = `queued / running / succeeded / failed / partial`（`partial` = 部分类别降级，FR-QC-11） |

### 7.5 sbp_ai_voice_qc_result（单通判定结果）★ 核心表

**用途**：FR-QC-03~12 的结果载体：结论、证据、计分、复核状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id / uuid / 时间组 / status | — | ModelMixin；`status` 保留（复核态见 `review_status`） |
| job_id | varchar(64) | 任务标识（1:1） |
| call_id | varchar(64) | 通话标识（冗余，便于直查） |
| rule_results | jsonb | 逐规则结果：`rule_code / verdict(pass/fail/na/undetermined) / score / evidence[]`；证据 = 说话人+时间区间+原文片段（FR-QC-03） |
| dimension_scores | jsonb | 维度分：服务规范/业务准确性/问题解决/沟通体验/合规风险/工单规范性（FR-QC-09） |
| total_score | numeric(6,2) | 总分 |
| defects | jsonb | 缺陷清单（标签 + 一级分类 + 证据引用） |
| risks | jsonb | 风险标签（合规风险类） |
| undetermined | jsonb | 未判定清单及原因（降级留痕，FR-QC-11） |
| model_versions | jsonb | 判定所用模型与提示词版本（可复现性） |
| review_status | varchar(20) | `pending / passed / corrected`（FR-QC-10） |

**索引**：`uq_sbp_ai_voice_qc_result_job(job_id)`、`ix_sbp_ai_voice_qc_result_call(call_id)`、`ix_sbp_ai_voice_qc_result_review(review_status)`。

**设计要点**：
1. 证据与判定强绑定存 JSONB，不拆子表（无独立检索诉求，避免过度设计）；
2. 硬规则短路：`priority` 高的硬规则命中"前置不成立"类结论时，其后的从属语义规则标 `na`，不计分（ADR-6）；
3. 修正走 `review` 表留原值，本表只存当前生效结论（FR-QC-10）。

## 八、integration 模块（已撤销，历史归档）

> **本章为历史归档，不代表当前状态。** 2026-11-02（v1.1）integration 过渡域连同代码整体删除，`sbp_ai_integration_*` 三张表（chunk / space / document）在 dev 环境已不存在。

原本的设计意图与最终处置：

| 原表 | 原用途 | 实际处置 |
| --- | --- | --- |
| `sbp_ai_integration_chunk` | 联调期切片临时表，带向量列与 HNSW 索引 | **未做数据迁移**：由 `sbp_ai_kb_chunk` 直接承接（`publication_id + record_id + revision + seq` 定位切片，`embedding vector(1024)`） |
| `sbp_ai_integration_space` | 集成期知识空间 | 随模块删除，无替代表（知识空间概念不再需要：契约以 `publication_id` 为单元） |
| `sbp_ai_integration_document` | 集成期空间文档 | 随模块删除，解析任务改由 `sbp_ai_kb_parse_job` / `parse_result` 承载 |

**当前纪律**：模块码只允许 `system` / `kb` / `voice`；未定稿能力**直接落在正式域**，不再设过渡域。这条纪律是对"迁移期双实现并存"教训的固化——过渡域一旦引入就会与正式实现长期并存，且删除时配套代码容易漏收尾。

## 十、数据生命周期与留存

| 数据 | 保留策略 | 执行 |
| --- | --- | --- |
| nonce | 7 天 | 定时清理（过期即删） |
| 幂等台账（非墓碑） | 90 天 | 定时清理 |
| **幂等墓碑** | **不清理** | 硬数据（FR-KB-08） |
| 请求台账 | 24 小时可查，90 天留档 | `expires_at` 控制 |
| 解析产物 | 90 天 | 定时清理 |
| 会话与消息 | 默认 6 个月（可配置） | 定时归档 |
| 旧 revision 切片 | 在线保留最近 2 个版本，更早归档后删除 | 版本切换任务联动 |
| 转写文本 | 按客户合规要求（默认 1 年，可配置） | 定时清理 |
| 判定结果/报告/Findings | 永久（业务数据） | — |
| 审计日志 | ≥ 1 年（含安全头校验明细） | 归档策略可配置 |

所有清理任务复用基座任务调度，任务本身进操作审计（FR-OPS-07）。

## 十一、设计约束清单（开发必读）

| # | 约束 | 依据 |
| --- | --- | --- |
| 1 | 表名必须为 `sbp_ai_<模块码>_<业务名>`，模块码只能取自 §2.2 模块码表（`system` / `kb` / `voice`）；**禁止新增 `integration` 表或过渡域**（v1.1 已撤销该模块码） | §2.1/2.2 |
| 2 | 业务表必须继承 ModelMixin 并自带 `status`；契约对外 ID 一律用 `uuid` 列 | §2.3/2.4 |
| 3 | AI 侧不使用迁移工具，启动期 bootstrap 幂等建表（缺表才建，已存在则跳过）；存量表变更必须交付 `ALTER`/`CREATE INDEX` 语句并备份，破坏性变更人工确认 | §2.7/§3.4 |
| 4 | 禁止外键指向 GSI 表；禁止在 AI 表复制 GSI 业务字段 | §2.5/§9.1 |
| 5 | 向量只允许出现在 `sbp_ai_kb_chunk.embedding`，维度 1024 不可变 | §6.6/ADR-4 |
| 6 | 权限过滤必须下推 SQL，禁止应用层后过滤 | ADR-8 |
| 7 | 审计异步独立会话落库；签名只存摘要；nonce 全量留存 | §5.2/5.3 |
| 8 | 墓碑数据不可清理；删除一律物理删，留痕由 `status` 表达或审计台账承担 | §5.4/§2.6 |
| 9 | 报告数字只来自 SQL 聚合（`payload`），模型文字只进 `interpretation` | §7.6 |
| 10 | 录音原文件禁止入库；转写文本最小必要保存 | DR-07/§7.1 |
| 11 | 枚举取值域写进表注释并在常量模块统一维护 | §2.6 |
| 12 | 目录名 = 表前缀 = 类名前缀，新模块先登记 `app/modules/__init__.py` | §1.3 |
| 13 | GSI 共享表只读：AI 侧统一放 `app/modules_gsi/<模块名>/<业务名>/`，类名 `Sbp` 前缀，独立 metadata、不进 `bootstrap.py`、不提供写操作；接口挂 `/api/v1/gsi` | §1.3/§3.3 |
