## 二、架构总览

### 2.1 分层

```
┌─────────────────────────────────────────────────────────────────┐
│  ① 接入层（契约）                                                │
│  /v1/*  20 接口 · HMAC 四头签名 · nonce 防重放 · 幂等 · 审计联动   │
│  /api/v1/*  管理端（JWT + RBAC，自研基座）                        │
├─────────────────────────────────────────────────────────────────┤
│  ② 编排层（Agent）                                               │
│  LangGraph StateGraph：知识链 · 会话问答链 · 质检链 · 报告链       │
├─────────────────────────────────────────────────────────────────┤
│  ③ 能力层                                                       │
│  检索（混合召回→RRF→rerank） · 生成（引用） · 重复治理             │

├─────────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────────┤
│  ⑤ 数据层                                                       │
│  PostgreSQL service_brain（与 GSI 共库）                         │
│  · public schema：sbp_ai_*（本项目，启动期 bootstrap 建表）      │

```

```
                          │  · 审计中间件（横切）         │
                          │  · LangGraph 编排            │
                          └──┬─────────┬─────────┬────┘
                             │         │         │
              ┌──────────────▼──┐ ┌────▼─────┐ ┌─▼────────────────┐
              │ service_brain   │ │ bge-m3   │ │ bge-reranker-v2-m3│

              │ GSI 表 +        │ │ (内网)    │ │ (内网)             │
              │ sbp_ai_* 表     │ └──────────┘ └──────────────────┘
              │ pgvector        │        │
              └─────────────────┘        │
                                   ┌─────▼──────────────┐

                                   │ OpenAI 兼容端点     │

```

要点：应用单容器单进程，模型服务独立部署可独立扩缩；PostgreSQL 为 GSI 与 AI 共用实例（`service_brain` 库），跨库 JOIN 不成立、也不允许——AI 与 GSI 的数据边界靠前缀与账号授权约束（ADR-10）。

### 2.3 三条主数据流

```
A. 知识流入（写）   GSI ─► #01 解析 ─► #02 产物 ─► GSI 审批 ─► #03/#05 写入
                   ─► 向量化 ─► 发布单元 revision+1 ─► GSI 切指针 ─► 检索生效

B. 问答流出（读）   GSI ─► #07/#14 ─► 授权计算（查 8 张共享表）
                   ─► 混合召回（权限下推 SQL） ─► RRF ─► rerank ─► 生成 ─► 引用回执

C. 质检流入         GSI ─► 通话转写 ─► 质检链（四类判定并行） ─► 计分
                   ─► 结果入库 ─► 报告聚合（SQL 数字 + 模型文字） ─► Findings
```

每条流的"断点"都有状态：解析任务状态机、请求台账、会话——任何一次调用中断后都可查询、可恢复、可审计。

## 三、架构原则

| # | 原则 | 落点示例 |
| --- | --- | --- |
| P1 | 判定逻辑与业务代码解耦 | 规则配置化 + 版本化（FR-QC-06） |
| P2 | 结果可解释、可追溯 | 证据六元组、判定留痕、`request_id` 贯穿 |
| P3 | 无证据不判定 | 召回为空 → `no_evidence`，禁止臆断 |
| P4 | 可解释性优先于智能程度 | 硬规则不调模型；报告数字来自 SQL |
| P5 | 可回滚 | 知识 revision、规则版本、提示词版本 |
| P6 | 失败降级不雪崩 | 单类判定失败 → 该类未判定；重排不可用 → 关键词通道 |
| P7 | 语料不出内网 | 向量化/重排私有化；送模型前脱敏最小化 |
| P8 | 共库不越界 | `sbp_ai_` 前缀 + AI 侧建表只管自有对象 + 账号最小授权 |

## 四、关键架构决策（ADR）

> 编号沿用旧架构文档并更新；**结论变化**的决策标注（变更）。

### ADR-1 项目定位：被调用的 AI 服务
AI 不持有业务事实，业务与权限事实留在 GSI，AI 提供带证据的判定与检索问答。代价：AI 强依赖共享表与契约稳定性；收益：无业务数据双写、无双主风险。

### ADR-2 编排：LangChain 组件 + LangGraph 状态图（不变）
质检/问答的判定路径天然是"分支 + 并行 + 降级"，状态图是自然表达。节点单测、超时预算、失败降级（FR-AGT）均依赖图结构。代价：增加学习成本；收益：每个判定步骤可独立测试、可中断恢复。

### ADR-3 对话模型：ChatGPT 5.6（变更）
统一使用 **ChatGPT 5.6** 作为解析辅助、问答生成、语义判定与报告解读的对话模型，经 **OpenAI 兼容端点**接入（`LLM_BASE_URL` / `LLM_MODEL` / 密钥全配置化，见 `backend/app/config/setting.py`）。模型调用不直接绑 LangChain ChatModel，而是经自研适配器（`core/clients/llm.py`：`chat` / `stream_chat`）暴露统一入口，便于超时、重试、成本记账与替换。代价：依赖端点配额；收益：不自建推理、模型可替换。**合规口径**：交付文档如对模型商标有顾虑，可表述为「OpenAI 系列对话模型（经兼容端点接入）」。

### ADR-4 向量化与重排：私有化部署（不变）
embedding 用 bge-m3（1024 维、8K 上下文、多语言），rerank 用 bge-reranker-v2-m3，均私有化部署，经 openai / ollama 协议访问。语料不出内网是合规底线。**维度一经上线不可变更**（与库表、HNSW 索引绑定），升级需全量重建。

### ADR-5 向量存储：pgvector 单库合流（变更）
向量与业务元数据同库（`service_brain` + pgvector 扩展），向量列挂业务列（`publication_id`/`record_id`/`revision`），一次 SQL 完成"权限过滤 + 向量检索 + 关键词过滤"，不存在跨库不一致窗口。代价：写放大与索引膨胀由生命周期策略控制（§十一）。

### ADR-6 判定分工：规则引擎处理可枚举项，模型处理语义项（不变）
固定话术、字段校验、时长阈值等交规则引擎；理解准确性、情绪安抚等交模型，但输出必须带证据。硬规则不调模型：可解释、可单测、零 token 成本。

### ADR-7 生成：非流式 + 请求台账（不变）
契约只做非流式（60 秒超时）。超时请求转 `sbp_ai_system_request_log`，GSI 经 #15 查询最终结果，不丢请求。

### ADR-8 权限：签名身份 → 实时查共享表 → SQL 下推（变更）
v2.1 契约删除了"白名单快照"思路：AI 按调用身份（`X-AI-Client` + `authorization{scope_id, issued_at, expires_at≤120s}`）**实时只读查询 8 张共享表**（组织及成员、受众团队及成员、用户、文档 / 发布 / 记录）计算授权，并将权限条件**下推到检索 SQL**（先过滤后检索），禁止先全库召回再应用层过滤。共享表不可用时返回 503 `AUTHORIZATION_UNAVAILABLE`，**禁止降级为全库检索**。为保护共享表，AI 侧以短 TTL + 权限数据水位（GSI 提供 `updated_at` 上界）做进程内缓存，水位未变不重查（P1，表 `sbp_ai_system_auth_cache`）。代价：联调依赖 DBA 授权与共享表数据质量；收益：无权限快照同步、静默漏召回问题。

### ADR-9 报告：数字与文字分离（不变）
统计数字全部 SQL 聚合产出，模型只写解读文字。报告快照落 `sbp_ai_voice_report_snapshot`，同周期幂等可重算。

### ADR-10 数据库：共库 public schema + `sbp_ai_` 前缀隔离（变更）
AI 与 GSI **共用 `service_brain` 库、同 public schema**，AI 表一律 `sbp_ai_[模块名]_[业务名]`（模块名：`system` / `kb` / `voice`；v1.1 起**不再设过渡域**）。理由：跨域 JOIN 与运维视图最直接、命名即边界。治理约束（强制）：
1. AI 侧不使用迁移工具，表由应用启动期各域 bootstrap 幂等建表（checkfirst，只补缺表），存量库结构变更走手工 SQL 并随发布评审；AI 只建/改 `sbp_ai_` 前缀对象，GSI 的 Flyway 脚本不得触碰 `sbp_ai_` 前缀对象；
2. AI 侧无迁移版本表，`flyway_schema_history` 归 GSI 管理，双方 CI 互检脚本越界；
3. AI 数据库账号仅对自有表 DDL/DML、对 8 张共享表指定字段只读；
4. 与 v2 手册"ai_knowledge schema"表述的差异，在账号开通时与 GSI/DBA 书面确认（契约本身注明"实际部署 schema 在开通账号时确认"）。

### ADR-11 知识版本：发布单元 + revision 原子切换（不变）
`publication_id` 为知识检索版本容器，`revision` 单调递增；写入完成向量化后返回回执，GSI 切指针，检索原子切换到新 revision；失败保留旧快照。防旧版本迟到事件污染（`revision` 并发校验，409）。

### ADR-12 命名合规：交付物品牌口径（不变）
对外交付物不出现商标/授权争议名称，基座统一称「自研基座」；只列国际通用开源组件与甲方认可的云服务。模型名属技术选型事实（ChatGPT 5.6），如法务有顾虑按 ADR-3 的口径表述。

### ADR-13 审计：对接接口纳入统一日志审计 + 安全头校验扩展（新增）
业务要求：对接接口必须走当前系统的日志审计，且审计需扩展以校验 HTTP 安全头。设计：
1. **全量纳入**：20 个 `/v1/*` 接口全部进 `sbp_ai_system_api_log`（不再跳过），2xx 与 4xx/5xx 一视同仁，被安全校验拒绝的请求同样落审计；
2. **扩展鉴权维度**：既有表新增 `auth_mode`（jwt/hmac）、`client_id`、`request_id` 列，HMAC 调用的 `username` 填 `client_id`；
3. **安全头校验留痕**：新增 `security_check` JSONB 列，记录四头存在性、时间窗偏差、nonce 状态、签名比对结果、失败错误码；签名值只留摘要，nonce 全量留存供重放取证；
4. **顺序约束**：先签名校验、后审计落库，但**被拒请求也要审计**——校验器返回结构化失败信息，中间件兜底落库，避免"拒绝即无痕"；
5. **隔离性**：审计写入独立会话异步执行，失败不影响主请求。
详设见 §六与 `04-项目模块说明与表结构设计.md`。

### ADR-14 幂等与防重放：持久化台账（不变+扩展）
nonce 表（`sbp_ai_system_nonce`）与幂等表（`sbp_ai_system_idempotency`）落共享库，多实例/重启后依然有效。幂等键分三类 scope（任务/请求/事件），同 ID 异正文 409（DR-05）。

## 五、接入层设计

### 5.1 双路由体系

| 路由 | 鉴权 | 审计 | 用途 |
| --- | --- | --- | --- |
| `/v1/*`（20 接口） | HMAC 四头（ADR-13） | 全量（FR-AUD-01） | GSI 契约调用 |
| `/api/v1/*` | JWT + RBAC（自研基座） | 全量（基座既有） | 管理台（日志审计、监控、规则配置等） |

> `/api/v1/gsi/*` 是管理面下的 **GSI 业务只读查询**（8 张共享表、13 条 GET），登记在 `DOMAIN_CONTROLLERS` 的 `/gsi` 域。代码位于 `app/modules_gsi/`，按「模块名/业务名」组织，模型使用独立 `SbpBase.metadata`，不参与启动建表，不提供写操作。

### 5.2 签名校验流程（/v1）

```
请求 ─► ① 四头齐全？ ──否──► 401 SIGNATURE_REQUIRED（security_check: missing_headers[]）
        │是
        ├─► ② client_id 在白名单？（环境变量配置，密钥不入库）──否──► 401 SIGNATURE_INVALID
        ├─► ③ |now − timestamp| ≤ 5min？──否──► 401 SIGNATURE_EXPIRED（记偏差 ms）
        ├─► ④ nonce 首次出现？（INSERT sbp_ai_system_nonce，唯一约束）──否──► 409 NONCE_REUSED
        ├─► ⑤ HMAC-SHA256(原始路径+查询串, 原始体摘要, 四头值) == X-AI-Signature？
        │       ──否──► 401 SIGNATURE_INVALID（security_check: signature=failed）
        ├─► ⑥ authorization.expires_at ≥ now（≤120s）？──否──► 401（过期）
        └─► ⑦ 通过 → 注入 request_id / client_id → 进入业务路由（后续统一异常处理）
```

关键点：校验器输出结构化结果（通过/失败原因/明细），供审计中间件落 `security_check`；被拒请求同样完成审计（ADR-13-4）。签名原文用**原始路径（含查询串）与原始请求体字节**，任何中间件不得提前消费 body 或重排 JSON。

### 5.3 幂等与错误体

- 写接口（#03/#05/#06/#20/会话写）与生成（#14）：以 `job_id`/`request_id` 为幂等键，`body_hash` 防同 ID 异正文；
- 生成/写操作超过 60 秒：HTTP 已返回，操作继续，结果进 `sbp_ai_system_request_log`，#15 可查（`operation`/`status`）；
- 错误体统一 `{code, message, retryable, request_id}`，覆盖 v2 新增错误码（`SCOPE_REQUIRED`/`GOVERNANCE_SCOPE_DENIED`/`SOURCE_CHANGED`/`RESULT_EXPIRED`/`AUTHORIZATION_UNAVAILABLE` 等）。

## 六、审计架构（重点）

### 6.1 现状与差距

自研基座已有统一接口日志：`sbp_ai_system_api_log` + 路由类审计中间件（`backend/app/core/router_class.py`），记录操作人、路径、方法、查询串、请求体、响应码、响应体、耗时、IP、UA，支持方法白名单与跳过路径。**差距**：① 无 HTTP 安全头维度；② `/v1` 对外契约调用此前未纳入；③ 无 HMAC 身份（`client_id`）与契约追踪 ID。

### 6.2 目标架构

```
请求 ─► 签名校验器 ─（结构化结果：pass/fail + 明细）─┐
                                                      ▼
业务处理 ─► 响应 ──────────────────────► 审计中间件（横切）
                                            │ 组装记录：
                                            │  username = client_id（HMAC）/ 用户名（JWT）
                                            │  auth_mode / request_id
                                            │  security_check = {四头存在性, 时间窗偏差ms,
                                            │                    nonce_state, 签名比对, 失败码}
                                            ▼
                                    异步落库 sbp_ai_system_api_log（独立会话）
                                    失败 ─► 应用日志 + 补偿（不阻断业务）
```

### 6.3 设计要点

1. **被拒也留痕**：签名失败请求不进业务路由，但校验器结果由审计中间件兜底落库，`response_code` 记 401/409，`security_check` 记失败明细——安全事件的取证不依赖业务日志；
2. **敏感值处理**：`X-AI-Signature` 只留摘要（前 8 + 后 4 位），nonce 全量留存（重放取证），请求/响应体沿用脱敏与截断策略（FR-AUD-06）；
3. **查询能力**：按时间 / `client_id` / 路径 / `request_id` / 校验结果组合检索（P1，管理台提供）；
4. **与业务日志双源关联**：`request_id` 同时出现在审计表与应用日志，UC-12 靠二者还原完整调用链。

## 七、编排层设计

### 7.1 图清单

| 图 | 触发 | 节点（→ 为顺序，‖ 为并行） |
| --- | --- | --- |
| 知识链-解析 | #01 | 提取 → 分片 → 产物组装（模型仅做辅助抽取，FAQ 不走模型） |
| 知识链-写入 | #03/#05 | 基线校验 → 内容哈希 → 增量向量化 → revision 递增 → 回执 |
| 会话问答链 | #14 | 授权计算 → 召回（关键词 ‖ 向量）→ RRF → rerank → 上下文组装 → 生成 → 引用回执 |
| 质检链 | 内部接口/队列 | 预处理 →（硬规则 ‖ 语义 ‖ 知识一致性 ‖ 工单一致性）→ 汇总计分 → 入库 |
| 报告链 | 周期任务 | 数据聚合（SQL）→ 解读生成（模型）→ 快照落库 |
| 重复治理链 | #16/#17 | 候选召回 → 相似度计算 → 分组/预览（不落正式库） |

### 7.2 状态与降级

- 每节点独立超时预算与重试上限（幂等节点才可重试）；
- 质检链四类判定并行，单类失败 → `该类未判定`，其余照常（FR-QC-11）；
- 召回为空 → 直接终止生成，返回 `no_evidence`（P3 原则）；
- 图状态落库（任务状态机 + 中间结果），重启可恢复或明确失败（FR-AGT-05）。

## 八、能力层设计

| 能力 | 设计 |
| --- | --- |
| 检索 | 关键词（`to_tsvector`/pg_trgm）+ 向量（HNSW 余弦）双通道 → RRF 融合 → rerank 精排；权限条件下推 SQL（ADR-8） |
| 生成 | 非流式；引用编号与分片一一对应；校验基准为 AI 侧已授权完整切片正文 |

| 规则引擎 | 关键词/正则/枚举/字段校验/阈值五类判定方式；版本与生效时间 |
| 语义判定 | 受控输出（JSON Schema）；结论必附证据片段；失败按未判定处理 |
| 一致性比对 | 知识一致性：召回→逐项比对→差异清单；工单一致性：七字段逐项比对 |
| 计分 | 维度分+总分，权重配置化；缺陷标签映射一级分类树（未映射拒绝入库） |
| 报告 | SQL 聚合数字 + 模型文字；四层快照；Findings 聚类带跟踪状态 |

## 十、数据架构（概览）

| 域 | 表（详见 04 文档） |
| --- | --- |
| system | `api_log`（扩展）、`nonce`、`idempotency`、`request_log`、`prompt_template`、（P1）`auth_cache` |

| kb（向量层） | `vector_collection`、`vector_embedding`（由 `core/rag/vector_store.py` 原生 SQL 建表，非 ORM 模型） |
| gsi（外部只读） | `sys` 5 张（org / org_member / audience_team / audience_team_member / user）+ `km` 3 张（doc / doc_publication / doc_record） |

> 合计 24 张（22 张 ORM 表 + 2 张通用向量层表）。原 `integration（过渡）` 域的 `integration_chunk` 已随模块删除（2026-11-02 v1.1），未做数据迁移——由 `sbp_ai_kb_chunk` 直接承接。向量层 2 张为 v1.2 新增，取代原先由 `langchain-postgres` 自动创建的 `langchain_pg_*`（表名硬编码、不满足 `sbp_ai_` 前缀规范）。
>
> GSI 只读的 8 张表**不计入**上述 24 张：结构由 GSI 侧 Flyway 维护，AI 侧 `app/modules_gsi/` 只做只读映射（类名 `Sbp` 前缀，独立 metadata），不进入各域 bootstrap 建表；只读接口挂 `/api/v1/gsi`。

- 所有 **AI 自有**表由启动期各域 bootstrap 幂等建表（checkfirst，只补缺表），命名 `sbp_ai_[模块]_[业务]`，公共字段沿用基座 ModelMixin（`id`/`uuid`/`created_time`/`updated_time`；**不提供软删字段**，删除一律物理删，留痕由业务用 `status` 表达）；GSI 只读表不在此列；
- 向量列 `vector(1024)` + HNSW（余弦），与业务列同表（ADR-5）；
- 共享表只读清单与字段见 04 文档 §三；AI 侧代码统一在 `app/modules_gsi/`，类名 `Sbp` 前缀，独立 metadata、不建表；
- 生命周期：解析产物 90 天、请求台账 90 天、会话默认 6 个月、nonce 7 天、审计 ≥ 1 年（可配置，DR-07）。

## 十一、集成架构

- **契约冻结**：以 v2.1 手册为准（20 接口/18 路径），字段级差异以契约比对脚本验收（FR-INT-01）；契约遗留问题（切片回写、chunk_id、授权双轨、重发布路径等）**接口复核暂缓（POC 先行）**，在 POC（T0.4 疑点清单）与联调期与 GSI 对齐（需求文档 §十二）；

- **上线检查单**（NFR-S-04）：反代不改写路径、DELETE 正文不丢、四头透传、共享表账号只读生效、审计落库正常。
