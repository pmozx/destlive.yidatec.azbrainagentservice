## 五、测试结论

### 5.1 契约符合性

| 检查项 | 结论 | 备注 |
|--------|------|------|
| 03.1 返回 201 + 写入回执 | ✅ 符合 | success/revision/accepted_chunk_count/searchable 齐全 |
| 03.2 返回 200 + 完整基线 | ✅ 符合 | chunks 含 chunk_id，metadata/content_hash 一致 |
| 03.3 返回 200 + 修订回执 | ✅ 符合 | revision 单调递增，指针切换到新 record_id |
| 03.4 返回 200 + 删除回执 | ✅ 符合 | deleted=true, searchable=false |
| 首发防覆盖（409 STALE_REVISION） | ✅ 符合 | publication_id 重复时拒绝 |
| content_hash 校验（409 STALE_REVISION） | ✅ 符合 | 摘要不一致时拒绝 |
| base_record_id 并发校验（409 STALE_REVISION） | ✅ 符合 | 基线过期时拒绝 |
| 删除后不可读（404 NOT_FOUND） | ✅ 符合 | 正文物理删除，墓碑不可查 |
| 错误体格式统一 | ✅ 符合 | error.code/message/retryable + request_id |
| chunk_id 自动分配 | ✅ 符合 | 按 `record_id:seq` 规则确定性生成 |

### 6.3 content_hash 计算规则

规则实现只有一份：`backend/app/modules/kb/publication/schema.py` 的 `canonical_content_hash()`
（字段固定为 `seq` / `heading` / `content` / `page_from` / `page_to`，按 `seq` 排序后
`json.dumps(ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 取 SHA-256；
`chunk_id` 由 AI 分配，不参与计算）。

测试脚手架不再自带副本：请求文件里的 `"content_hash": "__COMPUTED_AT_RUNTIME__"` 由
`tests/contract/client.py` 的 `resolve_content_hash()` 调测试辅助接口
`POST /v1/test/content-hash`（body 传含 `chunks` 的 JSON，返回 `content_hash` 与 `chunk_count`）
取回真值后替换，避免「改了 chunks 却忘记改摘要」，也避免测试侧与服务端各算一份摘要。

> 该接口与 `/v1/test/signed-headers` 同一开关（`CONTRACT_TEST_ENABLE=true`），生产环境必须关闭；
> 新增后需重启服务才能在 `/v1/test/*` 下看到。
