| 姊妹篇 | `05_duplicates_prepare_twin.json` | `pub-test-dup-twin-001` | `63858256ba974edd` | `rec-dup-twin-v1` | 3 条：前 2 条与主篇**逐字相同**，第 3 条换成 References | 造 `doc_exact` 分组、`chunk` 分组与 D06 的 2/3 |

两条铺场都走 03.1 写入口（`POST /v1/knowledge/entries`），固定 `request_id`，重跑时幂等台账按原响应回放 201。

> 姊妹篇的标题与主篇完全相同（`流量历时曲线对造林的响应`）：`doc_exact` 的分桶键就是**规范化标题**，标题不同就不会进同一个分组。
> 停用篇用 `faq` 类型而不是再写一篇文档：`#20` 只需要一条「已生效且可停用」的知识，混进文档范围会干扰 `doc_exact` / `chunk` 分组的成员数。

`scope` 基线（除 #20 外所有用例都带同一份清单，只换 `scope_id`）：

| 字段 | 主篇 | 姊妹篇 |
|------|------|--------|
| `resource_type` | `document` | `document` |
| `publication_ids` | `["0876a2b0-2788-4816-a1fd-7f26a2bfd061"]` | `["pub-test-dup-twin-001"]` |
| `entry_mode` | `manual` | `manual` |
| `content_hash` | `__HASH_MAIN__`（运行时实算） | `__HASH_TWIN__`（运行时实算） |

`resources` 恒为 2 项、`drafts` 恒为 `[]`：

- `scope_digest` 只覆盖 `resources` 与 `kinds`（都对成员排序），**不含 `scope_id` 与时间戳**，所以翻页 / 详情 / 预览可以各带新签发的 `scope`，只要清单不变就仍指向同一份快照；
- `drafts` 留空是刻意的：`GovernanceScope` 要求草稿必须挂在 `resources` 里某个身份上、且 `record_id` / `content_hash` 完全一致，**草稿无法用来提供「第二篇内容」**——要第二篇就得真铺一篇正式内容，这也是姊妹篇存在的理由。

### 1.3 D06「恰好 2/3」的构造与相似度矩阵

D06 的 `duplicate_ratio = 命中的不同 source_seq 数 / total_chunks`，`total_chunks` 取候选自身的切片数（剔空白）。要得到契约示例值 `0.6666666666666666`，候选必须是 3 片、且**恰好 2 片**命中。

候选选择有个反直觉的坑：**不能拿主篇当候选**。按同一口径（`0.6×2-gram Dice + 0.4×包含度`，阈值 `0.65`）实算主篇切片之间与姊妹篇切片的相似度，主篇第 3 片（Methods）与姊妹篇第 1 片高达 **0.7141**，会让占比变成 3/3：

| 候选 = 主篇某片 ↓ / 目标 = 姊妹篇 ↓ | twin1 | twin2 | twin3 |
|---|---|---|---|
| main1（Abstract） | **1.0000** | 0.6563 | 0.5634 |
| main2（1. Introduction） | 0.6563 | **1.0000** | 0.5933 |
| main3（Methods） | **0.7141** | 0.6247 | 0.5418 |

改成**姊妹篇当候选**，每个 source_seq 取「与该片最相似的目标」是否 ≥0.65：

| 候选切片（source_seq） | 与主篇三片的最大相似度 | 是否命中 |
|---|---|---|
| twin1 = Abstract（与主篇 Abstract 逐字相同） | 1.0000 | ✅ |
| twin2 = 1. Introduction（与主篇同段逐字相同） | 0.6563 | ✅ |
| twin3 = References（主篇没有这段） | 0.5933 | ❌ |

→ `duplicate_chunks=2`、`total_chunks=3`、`duplicate_ratio=0.6666666666666666`。

> 上面 9 个数值是 2026-11-10 用实现里的 `text_similarity()` 直接跑出来的，不是手算估计。
> **脆弱点**：`twin2 × main1 = 0.6563`，只比阈值高 0.0063。改动铺场正文（换行、全半角、多一个空格）就可能掉到 0.65 以下，占比变成 1/3。实测若得到 1/3，先核对 `05_duplicates_prepare_twin.json` 的切片 2 是否与主篇 `04_knowledge_search_prepare_entry.json` 的切片 2 逐字一致，而不是直接判实现缺陷。

## 二、接口契约与字段约束

### 2.1 请求正文

公共字段（六个接口全部必填）：

| 字段 | 类型 | 约束 |
|------|------|------|
| `request_id` | string | 本次操作 ID；写操作同时是幂等键 |
| `tenant_id` | string | 当前固定 `gsi-default`；与内容归属比对，不符 403 |
| `user_id` | string | GSI 登录用户的数字主键字符串 |
| `scope` | object | 治理范围，不是座席消费授权；结构见下 |

`scope` 结构：

| 字段 | 类型 | 约束 |
|------|------|------|
| `scope_id` | string | 范围追踪标识，非空 |
| `issued_at` / `expires_at` | integer | Unix 毫秒；`expires_at > issued_at` 且跨度 ≤120 秒，已过期 401、跨度超限 400 |
| `scope.resources[]` | array | 授权治理内容清单，最多 1000 项（`DUP_MAX_SCOPE_ITEMS`），超限 413 `PAYLOAD_TOO_LARGE`；同一 `(resource_type, resource_id)` 不能重复 |
| `scope.resources[].resource_type` | string | `document` / `faq` |
| `scope.resources[].resource_id` | string | GSI 文档或 FAQ 主键（不是检索命中的 `hit_id`） |
| `scope.resources[].record_id` | string | 必须是当前生效快照 ID，否则 409 `SOURCE_CHANGED` |
| `scope.resources[].content_hash` | string | 必须与库内 revision 行一致，否则 409 `SOURCE_CHANGED` |
| `scope.resources[].publication_ids` | array | 该内容对应的发布单元集合；草稿为 `[]` |
| `scope.resources[].entry_mode` | string | `ai` / `manual`（用于 FAQ 分类） |
| `scope.drafts[]` | array | GSI 侧尚无正式内容的草稿；每项必须挂在 `resources` 的某个身份上且 `record_id` / `content_hash` 一致 |

各接口差异：

| 接口 | 路径 | 专有字段 |
|------|------|----------|
| #16 保存前查重 | POST `/v1/knowledge/duplicates/check` | `candidate{resource,title,summary,content,chunks[]}`；`kinds`（留空=五类全查）；`score_profile`（本期固定 `gsi-duplicate-v1`） |
| D06 切片查重 | POST `/v1/knowledge/duplicates/chunk-check` | `candidate_resource`（`scope.resources[]` 同构），**必须与其中一项六字段全一致** |
| #17 分组查询 | POST `/v1/knowledge/duplicates/groups/query` | `kinds`、`result_id`（首查省略）、`cursor`（首查省略）、`limit`（1–100，默认 20） |
| #18 分组详情 | POST `/v1/knowledge/duplicates/groups/{group_id}/query` | 路径 `group_id` + `result_id` |
| #19 合并预览 | POST `/v1/knowledge/duplicates/merge-preview` | `result_id`、`group_id`、`keep_hit_id`、`actions[]{target_hit_id,action,merged_answer_html}`、`prompt_text`、`model_key` |
| #20 停用 | POST `/v1/knowledge/entries/{publication_id}/deactivate` | `publication_id`（必须与路径一致）、`record_id`（当前生效快照）、`revision`（必须大于当前）、`reason` |

四条「看起来可以商量、其实不行」的约束：

1. **`kinds` 留空是「五类全查」**，不是「不检测任何类型」——后者会返回一份没有分组的成功结果，正是「失败显示未发现重复」；
2. **`candidate_resource` 要六字段全一致**（`resource_type` / `resource_id` / `record_id` / `content_hash` / 排序后的 `publication_ids` / `entry_mode`）：只对上 `resource_id` 但 `record_id` 不同，等于拿另一个版本的正文算占比；
3. **`actions` 必须覆盖组内每个成员**且 `keep_hit_id` 必须属于该分组；切片组与非 FAQ 组不能 `merge_answer`；
4. **`cursor` 是本侧签发的偏移量**：非法游标直接 400，不能静默从头再来（否则前端会重复看到第一页）。

### 2.2 响应正文（HTTP 200）

| 接口 | 关键字段 |
|------|----------|
| #16 | `request_id`、`is_duplicate`、`similarity`、`score_profile`、`matches[]{hit_id,hit_kind,resource,title,snippet,similarity,reason,chunk_id?,source_seq?}` |
| D06 | `request_id`、`candidate_resource`、`complete`（恒 `true`）、`evaluated_resources`、`total_chunks`、`duplicate_chunks`、`duplicate_ratio`、`matches[]{source_seq,target_resource,target_seq,source_content,target_content,similarity}` |
| #17 | `request_id`、`result_id`、`expires_at`、`score_profile`、`groups[]{group_id,kind,title,similarity,score_method,reason,items[],suggested_keep_id}`、`next_cursor`、`total_groups`、`coverage{requested_resources,evaluated_resources,complete}` |
| #18 | `request_id`、`result_id`、`group`（同上，且 `items[].full_text` 补齐）、`evidence[]{left_hit_id,right_hit_id,basis,left_quote,right_quote,explanation}` |
| #19 | `request_id`、`preview_id`、`preview_hash`、`title`、`answer_html`、`summary`、`source_hit_ids[]`、`conflicts[]{field,description,hit_ids[]}`、`warnings[]` |
| #20 | `request_id`、`publication_id`、`record_id`、`revision`、`deactivated=true`、`searchable=false` |

三条投影口径：

1. **`full_text` 只出现在 #18 / #19**：列表响应省略它，避免分组响应随成员数膨胀；
2. **`complete` 只有 `true`**：失败一律显式报错（403 / 409 / 413），不用 `complete=false` 或空 `matches` 伪装「查完了没重复」；
3. **`coverage.evaluated_resources` 必须等于 `requested_resources`**：#17 取实际加载条目数，D06 取 `scope.resources` 声明数（**含候选自身**，所以本套用例恒为 2）；两者不等说明有人被静默跳过。

### 2.3 拒绝顺序（谁先拦）

| 顺序 | 校验点 | 失败表现 |
|------|--------|----------|
| 1 | 签名鉴权（公共 5 头） | 401 `UNAUTHORIZED` |
| 2 | 正文 Schema（枚举 / 必填 / `seq` 唯一 / 草稿挂靠 / 候选在范围内） | 400 `INVALID_REQUEST` |
| 3 | `scope` 时效（跨度 ≤120s、未过期） | 400 / 401 |
| 4 | 容量（`scope.resources` > 1000 项） | 413 `PAYLOAD_TOO_LARGE` |
| 5 | 来源校验（租户 / 类型 / ID 归属，快照与摘要） | 403 `FORBIDDEN` / 409 `SOURCE_CHANGED` |
| 6 | 结果快照（`result_id` 归属、过期、`kinds` / `score_profile` / `scope_digest` 一致） | 404 `NOT_FOUND` / 409 `RESULT_EXPIRED` |
| 7 | 业务（检测 / 分页 / 详情 / 预览 / 停用） | 200 |

> 容量校验刻意放在 Pydantic 之外：写进 Schema 会被归一成 400，把「数据太多」误报成「参数不对」，而契约明确要求 413。

### 2.4 判定口径

| 常量 | 值 | 含义 |
|------|-----|------|
| `SIMILARITY_THRESHOLD` | `0.65` | 相似度阈值；口径为 `0.6×2-gram Dice + 0.4×包含度` |
| `MAX_MATCHES` | `50` | #16 返回的整篇命中上限 |
| `CHUNK_CHECK_MAX_MATCHES` | `200` | D06 命中证据上限，**超限 413 `RESULT_TOO_LARGE`，不截断** |
| `RESULT_TTL` | 30 分钟 | 结果快照保留时长，过期 409 `RESULT_EXPIRED` |
| `DEFAULT_GROUP_PAGE` / `MAX_GROUP_PAGE` | 20 / 100 | #17 每页分组数 |
| `FULL_TEXT_LIMIT` | 4000 | #18 `full_text` 截断长度 |

分组类型共五类：`doc_exact`（规范化标题相同）、`doc_similar`（正文相似度 ≥0.65）、`chunk`（切片正文完全一致）、`faq_ai` / `faq_manual`（按 `entry_mode` 分）。`group_id` / `hit_id` 都由内容身份确定性推导，同一次输入必须得到同一批 ID——否则翻页、详情、预览三步对不上同一批对象。

### 4.3 脚本自带的自洽断言

|----------|----------|
| `05_duplicates_check.json` | `is_duplicate` 必须等于 `matches` 是否非空 |
| `05_duplicates_groups_query.json` | `coverage.requested_resources == coverage.evaluated_resources == 2` |
| `05_duplicates_chunk_check.json` | `complete=true`、`evaluated_resources=2`、`total_chunks=3`、`duplicate_chunks` 等于 `matches` 里不同 `source_seq` 的个数、`duplicate_ratio` 等于 `duplicate_chunks / total_chunks` |

另外三处**运行时注入**也是防呆：`__RESULT_ID__` / `__GROUP_ID__` / `__KEEP_HIT_ID__` / `__OTHER_HIT_ID__` 全部从 #17 首查响应里取（优先 `doc_exact` 组），取不到就让后续用例打印「跳过 + 原因」，而不是把 `__X__` 原样发出去换 400——那会看起来像「接口坏了」，掩盖真正的原因「没铺场」。

## 五、实现依据与已知风险

| 结论 | 依据 |
|------|------|
| 重复判定不用向量 | 向量不可用时只能返回「未发现重复」，正是契约禁止的失败表现；这里用「NFKC + 小写 + 去标点空白」后的 2-gram 字面口径，结果可复现、可解释 |
| 三步共用一份快照 | #17 首查把结果与治理行在同一事务里落库，翻页 / 详情 / 预览都必须带 `result_id`，且校验 `kinds` / `score_profile` / `scope_digest` 一致——换了清单就只能重查，不能拿旧快照算新范围 |
| 详情要复核成员未变 | #18 用实时来源补齐 `full_text`，成员被修订则 409：预览里展示的全文必须是当前生效内容，否则审批基于旧内容 |
| 预览不写正式库 | #19 只产出草稿态结果；`preview_hash` 排除随机 `preview_id` 与生成时间，同一组输入重复调用应得到同一个 hash，便于去重与审计 |
| #20 与 03.4 删除的差别 | 删除物理清除切片；停用只停召回、保留正文与向量供审计（`deactivated=true` + `searchable=false`）。重复调用按幂等台账回放同一份回执 |

**已知风险（执行时需留意）**：

1. `twin2 × main1 = 0.6563` 逼近阈值（见 §1.3）：铺场正文被改动会让 D06 变成 1/3，先核对正文再判缺陷；
2. 主篇若被 `run_knowledge_tests` 的修订用例改过版本，`__HASH_MAIN__` 与库内 revision 会对不上 → 409 `SOURCE_CHANGED`，需要重跑主篇铺场（换 `request_id`）；
3. 结果快照只保留 30 分钟：手工分步执行（先跑 `chunk_check` 再跑 `groups`）超过半小时会 409 `RESULT_EXPIRED`，不是接口异常；
4. `#20` 停用后 `pub-test-deact-001` 不可再检索，重跑脚本时该发布单元若仍存在会命中幂等回放而非重新写入；确需重建请换 `publication_id` 与 `request_id`。

## 六、结论

1. **契约口径已固化**：6 条路径 9 个用例的请求字段、`scope` 结构与容量/时效约束、响应条件必返字段、拒绝顺序与错误码映射均已逐条对照手册落进请求数据与脚本断言。
2. **0.65 阈值下的确定性用例**：D06 的 2/3 由真实相似度矩阵反推构造（候选选姊妹篇而非主篇），不是凑数；矩阵与脆弱点已写入 §1.3。
3. **实测待执行**：本报告不含实测结论。执行 §4.1 的命令后，按 §4.2 补录并由 `responses/` 快照留证。
